# 26: 历史邮件回放与 T0 切换

Status: ready-for-agent
Blocked by: 13, 16

规格：[第一期：报表与台账](../spec.md)

**What to build:** 上线第一天报表就有 90 天基线，且历史工单与实时工单口径一致。管理员命令：选定 T0 → T0 前启动 `watch` → 近 90 天邮件（收件与「已发送」）按 `internalDate` 升序单线程回放 → T0 后开启实时处理。回放复用实时流水线，只把「当前时间」注入为邮件时间：归并、关闭、重开按当时时间判断；工单编号日期取首封来信日期；回放模式下关闭一切提醒与通知。历史来信照常计算首次回复与 SLA；T0 时仍未回复的来信进入「待回复」并受 14 天规则约束。回放可断点续跑、重跑幂等。

- [ ] 集成测试：AC-P1-13（编号日期取首封来信日期；按邮件时间关闭与重开；无提醒、无通知）
- [ ] 集成测试：回放重跑不产生重复工单与消息
- [ ] 集成测试：T0 时未回复的历史来信所在工单，在最近一封来信 + 14 天后按规则关闭（PRD 6.1 起算口径）
- [ ] 集成测试：回放与 T0 后实时来信交界处不丢不重
- [ ] 操作手册写明切换步骤与回滚方式

## Comments
- 2026-10-05（待办 08）：实时收信走 `channel/gmail-sync.ts`（同步 → 入库 → 「来信已接收」→ `ticket/merge.ts` 归并），回放复用这条路即可：编号日期取来信的 `received_at`（internalDate），客户、店铺、渠道都在入库时定；入库的 `created_at` 与状态变更记录的时间取事务的「当前时间」（时钟），回放时注入为邮件时间。数据库约束按写入先后（UUIDv7）取最近一条状态变更，时钟拨回过去不受影响。邮箱的增量游标由 watch 建立（`channel.mailbox_sync`），T0 前先 watch、再回放 T0 之前的邮件，与规格的顺序一致。worker 的吞吐是每个队列空闲 2 秒轮询一次（ADR 0008 修订），回放大量邮件时要单线程直接驱动流水线或调 pg-boss 的批量与连续取。
- 2026-10-05（待办 10）：识别在入库时（`channel/recognition.ts`），回放走同一条路，平台通知与营销照常只入库归档。非生产环境的「重放来信」（`reset-inbound`，ADR 0013 修订）只是清空工具，不是本待办的 T0 回放。

- 2026-10-06（待办 31）：回放模式的开关在 `core` 的运行时：回放命令用 `startRuntime(…, { replay: true, clock })` 组装运行时，事务带 `tx.replay`，站内通知的写入（`sendNotification` / `notifyMembers`）在回放里不写、返回空列表，要发钉钉工作通知的调用方按返回的接收人发，回放里自然不发。标记跟着运行时、不跟着任务：回放期间排进队列的任务必须在回放的运行时里跑完（任务处理器从 `JobContext.runtime` 取运行时），实时 worker 在 T0 前不消费这些队列；若要并行，需把标记带进任务载荷（ADR 0008「待办 31 落地」修订）。测试工具已有 `t.runJobs({ replay: true })`，AC-P1-13 的「无通知」可以照 `apps/server/test/notifications.int.test.ts` 的回放用例写。

- 2026-10-07（待办 13）：订单回补的入口是部署子命令 `node deploy/deploy.mjs <环境> order-backfill [--store <店铺名>]…`（`docs/部署说明.md` 第 15 节，已写明在选定 T0、回放邮件之前执行，回补做完再回放）。切换手册里第一步引用它即可；判断「做完」看 P18 两张卡的回补行为「已完成」或「未开通 read_all_orders」，或 `order` 的 `orderBackfills` 全部 `completed`。回补与回放无关的运行时开关：回补任务不发通知，回放模式不影响它。

- 2026-10-07（待办 14）：按订单归并的「30 天内重开」按来信到达时间（`received_at`）与关闭时刻比，回放时自然按当时判断；关联订单要查镜像、镜像没有时去平台补拉，所以要先做订单回补再回放（部署说明第 15 节已写）。回放里补拉失败时归并任务照常重试，最后一次尝试不关联订单建单（`JobContext.lastAttempt`）；单线程回放若自己调 `mergeInbound`，要给出 `lastAttempt`。
- 2026-10-07（待办 16）：回放「已发送」照样走实时的路：入库发 `channel.outbound_synced`，`ticket/replies.ts` 识别；回复先于来信时记进 `ticket.pending_reply`，等多久按 `tx.now`（回放时是邮件时间）算 24 小时。时限扫描是 `ticket/time-limits.ts` 的 `scanTimeLimits(运行时, 当前时间, 日志)`，接收显式时间：按 internalDate 升序回放时，每推进到一封邮件的时间先扫一次（或每过一分钟扫一次），7 天、14 天关闭与 SLA 到期就按当时判断，状态变更的时刻也是那个时间（30 天重开按它比）；T0 之后交给 worker 的每分钟扫描。扫描本身不发提醒与通知（第一期没有 SLA 提醒）。注意 Fake Gmail 的示例回放会按整天平移到当前日期（ADR 0009「待办 16 落地」），只是开发与演示用，与上线回放无关。

- 2026-10-07（待办 15）：来信的店铺按收件地址识别（`channel/recognition.ts` 的 `storeForMail`：写给落到的店铺邮箱的按它，否则 Delivered-To、To、Cc 里第一个登记过的进线邮箱，一个收件地址都没有时按落到的邮箱），收件地址都没登记的进未归属店铺队列，入队通知走 `org` 的 `notifyMembers`，回放模式下不发（11.4「历史回放时不产生通知」）。历史回放的来信同样会进队列；T0 前回放出来的未归属来信由客服主管上线后指定，或先在 P18 登记好店铺（登记后自动归位，归并时仍按原到达时间算 SLA）。
