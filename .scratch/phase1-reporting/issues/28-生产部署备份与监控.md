# 28: 生产部署、备份与监控

Status: ready-for-agent
Blocked by: 03, 05, 09, 11, 12, 20

规格：[第一期：报表与台账](../spec.md)

**What to build:** 生产环境可以安全地部署、坏了能恢复、出事有人知道。生产部署由打标签触发，带环境保护与人工批准，调度到生产运行器标签；生产迁移前自动备份。PostgreSQL 镜像内置 WAL-G：每日物理基础备份 + `archive_command` 连续归档 WAL 到 NAS；每天凌晨 `pg_dump` 逻辑备份与附件卷备份经 restic 加密去重同步到 NAS（保留 30 份日备份与 12 份月备份）。恢复演练脚本与手册，必须包含「从基础备份恢复到其后指定时点」。worker 每分钟自检（队列积压、失败任务、各数据源最近同步时间、外部调用错误率、配额），异常发钉钉群机器人；宿主机独立检查 worker 存活与心跳（进程退出、心跳停都告警）。日志 pino JSON，Docker json-file 轮转保留 30 天。静态密钥放 `.env`（600），主密钥离线保管说明。

- [ ] 打标签 → 人工批准 → 部署到生产；未批准不部署
- [ ] 在开发测试环境演练一次按时间点恢复并记录耗时（目标 RTO 4 小时）
- [ ] 人为停掉 worker 或让心跳停止，钉钉群机器人收到告警
- [ ] 自检发现某数据源超过阈值未同步时告警
- [ ] 备份保留策略生效（可用脚本验证）
- [ ] 运维手册：备份、恢复、密钥、告警处理

## Comments
- 2026-10-05（待办 20 留下的衔接）：生产环境的汇率客户端默认真实现，经出站代理读欧洲央行（`www.ecb.europa.eu`）、备用 Frankfurter（`api.frankfurter.dev`），放行清单已写进 `docs/部署说明.md` 第 6 节；第一次部署时 worker 启动即同步，会下载约 8 MB 的全量历史。自检的「各数据源最近同步时间」里，汇率要按最近一次**同步成功**的时间判断、阈值 1 天（PRD 6.9）——不能按 `core.exchange_rate` 的最近写入判断，欧洲央行周末与假日不公布，那几天同步成功也没有新行。20 号待办没有单独记同步状态：可以读 pg-boss 里 `core.sync_exchange_rates` 最近一次完成的时间，或由本待办给同步加一行状态记录（照 `channel.mailbox_sync` 的写法）；每日同步任务 `core.sync_exchange_rates` 两个来源都失败时任务失败、30 分钟后重试 3 次，重试用完仍失败的应当告警。
- 2026-10-06（待办 27 留下的衔接）：售后登记表导入是镜像里各环境都用的一次性命令 `node dist/import-aftersales.mjs`，部署脚本子命令 `import-aftersales` 对 `ENVIRONMENTS` 里的任何环境都可用（不像 `reset-inbound` 拒绝生产）。生产环境加入部署脚本后，`node deploy/deploy.mjs production import-aftersales <登记表> [--dry-run]` 即可用；届时把 `docs/部署说明.md` 第 10 节第 4 步里「在那之前用 docker compose run …」的写法删掉。真实登记表的导入是上线前事项（待办 32）。导入（含试运行）在一个事务里，期间新建登记会等，安排在上线前或无人登记的时段。

- 2026-10-06（待办 05）：worker 自检可读钉钉通讯录的同步状态（`org.dingtalk_sync`：最近成功、连续失败次数与最近的错误；`org` 的 `dingtalkConnection`）与每月的钉钉调用量——发出的工作通知在 `core.work_notification`（`sent_at`、钉钉任务 ID `task_id`），标准版每月 5,000 次（通讯录读取与访问凭证不计），接近配额时告警（ADR 0010）。钉钉群机器人告警是另一个通道（群的 Webhook），与工作通知无关。生产环境的环境文件要有 `DINGTALK_*` 四项（生产默认真实接口，缺了 api 与 worker 拒绝启动，`docs/部署说明.md` 第 11 节）。

- 2026-10-06（待办 12，协调者要求）：订单通知队列（SQS）的「拉取失败」（连续 3 次）与「积压」（等待拉取的通知 ≥ 10 条）在产品上只写在 P18 亚马逊卡的一行，不出横幅、不发通知（协调者 Q7）；系统级告警要纳入 worker 自检：读 `order.order_queue`（`consecutive_failures`、`backlog`、`checked_at`——超过几分钟没检查说明拉取源没在跑）。生产环境的环境文件按 `docs/部署说明.md` 第 14 节：`SP_API_CLIENT_*`、`AMAZON_SQS_*` 不是启动条件，资质到位后填入、重新部署，再用 `sp-api-token` 子命令录入每个卖家的刷新令牌；主密钥随备份单独离线保管，换了主密钥要重录刷新令牌。SP-API 配额（令牌桶剩余）的监控可读进程内的 `SpApiQuota.available`，或看 `integration.call_record` 里 `sp_api` 的 429。

- 2026-10-07（待办 13）：worker 新增三个任务——`order.sweep_page`（回补与对账的一页，失败 1 分钟起退避重试 3 次、过期 1 小时）、`order.sweep_resume`（每 10 分钟续跑）、`order.reconcile`（每天 03:30 夜间对账）。回补与对账的失败不进连接状态、不出横幅，只记在 `order.order_sweep.last_error`；worker 自检可把「对账 `started_at` 超过 1 天仍未 `completed_at`」与 `last_error` 纳入告警。部署子命令 `order-backfill` 已进 `deploy/deploy.mjs`（生产上线前执行一次）。

- 2026-10-14（待办 18）：生产部署注意两点。① 实时推送 `/api/live` 是 SSE 长连接：caddy 对它不压缩（`deploy/web/Caddyfile` 的 `@compressible`，压缩会把推送攒着不发），反向代理与负载均衡都要流式转发、不缓冲，空闲超时要长于 25 秒（心跳间隔）。② 每个 api 进程另占一条数据库连接做 LISTEN（`createChangeFeed`，不在连接池里），核算 PostgreSQL 连接数时算上；api 扩多个实例时各自监听即可。监控可以看 `pg_stat_activity` 里 `application_name = 'forcome-api-listen'` 的连接是否在。
