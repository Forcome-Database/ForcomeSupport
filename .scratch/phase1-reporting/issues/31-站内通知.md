# 31: 站内通知

Status: claimed
Blocked by: 04

规格：[第一期：报表与台账](../spec.md)

**What to build:** 需要人处理的事件能在系统里看到并标记已读，按 PRD 11.1 Notification、11.4 与全局状态 G10。`core` 提供站内通知：写入接口（接收人、类型、关联对象、内容、时间）、按接收人查询、标记已读与全部已读；其他模块只经事件或 `core` 的服务调用写通知，不直接写表。第一期的通知类型（11.4）：渠道连接异常与恢复（管理员、客服主管，钉钉除外）、钉钉同步失败（管理员）、未归属店铺来信（客服主管）、登记新店铺后来信自动归位（客服主管）、成员停用后售后单进入改派队列（客服主管）；需要同时发钉钉工作通知的由调用方另行发送（待办 05 的能力）。前端顶栏铃铛显示未读数，点开 360px 面板：页签「全部 · 未读」，每条带类型图标、标题、对象与时间，未读带圆点；点一条跳到对象并标为已读；「全部已读」；没有通知时空状态。新通知经 SSE 推送（待办 18 的 `NOTIFY` 通道，若尚未落地则先轮询）。历史回放模式下不产生通知（待办 26）。

- [x] 集成测试：写入后接收人可查到，其他人查不到；标记已读与全部已读生效
- [x] 集成测试：回放模式下调用写入不产生通知
- [x] 单元测试：通知类型与接收人对照 11.4
- [x] Playwright：铃铛未读数 → 打开面板 → 点击一条跳转并变为已读

### 实现记录（2026-10-06，claude02）

**业务口径（2026-10-06 经协调者 ask 提问，等回复；先按建议实现）**

- Q1 空状态说明：原型 G10 ②「审批、渠道异常、未归属店铺来信等需要你知道的事会出现在这里。」第一期没有审批类通知（11.4 审批类都是「二起」）。建议第一期去掉「审批、」。现在按建议，`notification-copy.test.ts` 暂按「原型完整版去掉开头的『审批、』」核对；确认后回写原型 G10 与 PRD，测试改回逐字核对。
- Q2 打不开目标页的通知：渠道连接异常 / 恢复发给客服主管，但 P18 只对管理员开放。建议同 P27 v2.20「对象按查看者能否打开目标页决定可不可点」：打不开时点一条只标为已读、不跳转，对象编号不用主色（原型里周敏的「P18 · Gmail」是主色）。
- Q3 跨天时间写法：原型只画了当天（「10:14」）。建议当天写「时:分」、之前写「月-日 时:分」、不在今年写全年份（与 P27 时间列同一写法）。
- Q4 接收人与店铺范围：建议关联对象属于店铺的类型（登记新店铺后来信自动归位、改派队列）只发给店铺范围包含该店铺的接收人；渠道连接、钉钉同步、未归属来信按角色发给全部；范围收窄后范围外店铺的旧通知不再显示（同 P27 v2.21，R-ST-06）。
- Q5（评审时补问）「全部已读」不可用时的悬停说明：原型没画；设计规范要求禁用写原因。建议悬停写「没有未读通知」。

**交付了什么**

- `contracts/notifications.ts`：第一期六种通知类型 `notificationTypes` 与定义 `notificationTypeDefinitions`（11.4 的事件、接收人角色、是否同时发钉钉工作通知、是否按店铺发）；关联对象与通知内容 `notificationObjectSchema`、`notificationContentSchema`；接口模式（列表带未读数与服务端当前时刻 `now`、未读数、页签 `all | unread`、最多 50 条）；时间写法 `notificationTimeWords`（复用 P27 的 `auditTimeWords`）；示例通知接口的响应。
- `core`：通知表 `core.notification`（迁移 0018，每个接收人一行，接收人只存成员 ID，带关联对象、店铺、已读时间，未读部分索引）；`core/notifications.ts` 的写入 `sendNotification(tx, { recipientIds, …内容 })`（时间取 `tx.now`，按店铺发的类型必须给店铺，回放模式下不写、返回空列表）、按「看通知的人」`NotificationViewer { memberId, stores }` 的 `listNotifications`、`countUnreadNotifications`、`markNotificationRead`（看不到的返回 false → 404）、`markAllNotificationsRead`（只标看得到的）；运行时与事务的回放标记 `Runtime.replay` / `tx.replay`；示例通知加载步骤 `core.notifications`（原型 G10 周敏的四条第一期通知）。
- `org`：`notifyMembers(tx, 内容)`——按 11.4 取在职、有接收人角色之一的成员（多角色只一条，按店铺发的类型再看店铺范围），调 `core` 写入，返回发给了谁；面板接口 `createNotificationRoutes`（`GET /api/notifications?view=`、`/unread-count`、`POST …/{id}/read`、`…/read-all`，只针对当前成员）；示例通知接口 `org/dev-notifications.ts` 的 `POST /api/dev/notifications`（与开发登录同一个开关，非生产环境才挂）；共用的 OpenAPI 响应写法 `org/openapi.ts`。
- 前端：顶栏铃铛与面板 `components/notification-bell.tsx`（文案 `notification-copy.ts`）；查询、角标写法、类型图标、跳转目标、标为已读的缓存 `lib/notifications.ts`；`lib/api.ts` 的通知接口与后台请求头 `backgroundRequest`；新组件 `ui/tabs.tsx`、`ui/scroll-area.tsx`，共用件 `components/icon-tile.tsx`（P18 渠道卡改用）与 `lib/pages.ts` 的 `canOpenPage`（页面把关、P27 对象链接、通知跳转共用）；令牌 `--text-10`（数字角标）。

- 测试工具：`t.runJobs({ replay: true })`（`run-jobs.ts`，拉取与任务在回放的运行时里跑）。

**关键取舍**

- **表在 `core`、按 11.4 取接收人在 `org`**：`core` 不能依赖业务模块，取接收人要读成员与角色，所以写入接口（接收人、类型、关联对象、内容、时间）在 `core`，`org` 的 `notifyMembers` 取人后调它；业务模块只调 `notifyMembers`（第二期按对象定接收人的直接调 `sendNotification`），不碰表。面板接口与 P27 一样在 `org`（要会话与店铺范围）。
- **回放标记放在运行时**：回放（26）复用实时流水线，只换时钟；在 `Runtime` 上加 `replay`、事务带出 `tx.replay`，写入处一处判断，调用方不用各自记得。代价是标记不随任务走：回放期间排的任务必须在回放的运行时里跑完（ADR 0008 修订写明，26 的 Comments 也写了）。
- **店铺范围两道**：按店铺发的类型在发送时按范围筛接收人；查询、未读数与标为已读再按接收人当前的范围过滤（P27 v2.21 同一口径）。
- **示例通知接口**：产生通知的业务（05、09、11、12、15、23）都还没有，e2e 又要在长期运行的开发测试环境里可重复执行（每次要产生新通知），所以加了与开发登录同一个开关的 `POST /api/dev/notifications`，走业务调用方同一个 `notifyMembers`。它不是只为测试写的示范接口（冒烟也要用），按环境挂载，生产环境没有（`app.test.ts` 核对）。业务调用方上线后可删。
- **先轮询**：SSE（18）还没有，铃铛未读数与打开的面板每 30 秒拉取一次；未读数轮询与面板开着时的定时拉取带后台请求头（不续期会话），打开面板、切换页签、点「重试」后的第一次取列表是人的操作（`fetchByUser` 登记，e2e 记录请求头核对）。
- **时间以服务端为准**：列表带回服务端当前时刻 `now`，按它判断「当天」，演示时刻（`CLOCK_START`）与测试时钟都对得上。
- **先改缓存再提交**：点一条、全部已读立即反映在面板与角标上，失败时 G5 失败浮层（`showError`，同一件事一条）并重新拉取；成功后撤掉之前的失败浮层；401 走会话结束。
- **e2e 不破坏演示状态**：「全部已读」用例用刘洋与只发给管理员的钉钉同步失败，开发测试环境里周敏的示例通知（未读 3）不会被每次冒烟标掉；其余用例只点自己发的那条（带时间戳），未读数只核对相对变化。
- **Node 24**：照 README「开发」，便携 Node 24.21.0 复制到本会话临时目录、只在会话命令里前置 PATH，pnpm 10.34.6 经 corepack；没有改系统配置。

**自己写而没用现成库的部分**

- 通知的存储与查询（一张表、几条 drizzle 查询）：第三方通知服务（Novu、Knock 等）要外部服务或另起一套服务与库，不能和业务数据在同一事务里写入，也不符合内网零入站（ADR 0003）；需求只是按人存、按人查、标已读，表加查询最简单。前端的轮询、缓存与乐观更新用已装的 TanStack Query，页签与滚动区用 shadcn/ui（Radix）。
