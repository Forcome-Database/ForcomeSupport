# 35: 163 企业邮箱 IMAP 收信

Status: ready-for-agent
Blocked by: 34

规格：[第一期：报表与台账](../spec.md)（「163 企业邮箱收信」实现契约由 34 补）

**What to build:** 按 34 定下的 PRD、ADR 0015 与规格，让店铺进线邮箱可以是 163 企业邮箱，收信与 Gmail 走同一条流水线：入库 → 店铺与来源识别 → 归并成工单 → 回复识别与 SLA → 时限扫描 → 报表。第一期只收信（收件箱与「已发送」），不发信。后端与对 P18 的接口在本票；P18 界面在 36。

- **服务商抽象**：进线邮箱带服务商（Gmail / 163 企业邮箱）；收信层按邮箱分派到 Gmail 或 IMAP 实现。Gmail 现有行为不变（回归测试全过）。`gmail_*` 命名的列、唯一键、回放清单、`pending_reply` 索引等，按 ADR 0006（加列分三步、手写 SQL 用 `--custom`）改成与服务商无关或补上 IMAP 的标识，取舍写回 ADR 0015。
- **IMAP 客户端**：先用现成的——`imapflow`（Nodemailer 作者维护，支持 IDLE、SPECIAL-USE、UID 增量）+ 已装的 `postal-mime` 解析原文；真实现与 Fake 照 ADR 0009 的框架（店铺 `adapterMode`、`CLIENT_MODE_*`，生产拒绝 Fake）。网易登录前可能要求 IMAP `ID` 命令（RFC 2971），按 imapflow 的 `clientInfo` 处理并写进 ADR。
- **同步**：收件箱与「已发送」各一组 UIDVALIDITY + UID 游标；IDLE 常驻（复用常驻拉取的独占选主）+ 每 5 分钟轮询兜底；UIDVALIDITY 变化按到达时间区间补拉；水位只在入库后推进；同步记录的 `last_success_at`、`synced_through`、连续失败与连接状态口径与 Gmail 相同（6.9），所以 33 号的「按时关闭要求邮箱同步到到期时刻」对 163 同样成立。
- **历史回放与 T0**（26 号的命令）：163 邮箱按到达时间列近 90 天（`SEARCH SINCE/BEFORE` 再按 INTERNALDATE 筛），切换前只监听不入库，与 Gmail 同口径。
- **凭据**：授权码按邮箱用 `CREDENTIAL_MASTER_KEY` 加密存库（现有 `sealSecret`，AAD 带邮箱），接口只写不读；改授权码记审计（不记内容）；连接失败（认证失败、IP 限制、超时）归类到连接状态与通知（11.4「渠道连接异常 / 恢复」，文案按 34 定的写法），区分「授权码错误」这类需要管理员处理的错误。
- **P18 接口**：登记 / 修改进线邮箱的服务商、IMAP 服务器与端口、授权码；测试连接（不保存也能测，或保存后测，按 34 原型）；渠道卡数据（163 邮箱数、连接状态、最近同步）。权限照 P18（只有管理员），店铺范围与审计照现有写法。
- **示例数据与 Fake**：Fake IMAP 与 Fake Gmail 用同一套示例回放（示例来信按 34 的示例数据分到 163 邮箱），本机开发库、e2e 库、开发测试环境（`deploy:staging --reset-inbound`）都能看到 163 邮箱的来信变成工单。
- **部署**：`NO_PROXY` 模板与 `docs/部署说明.md` 加网易企业邮箱域名直连；开发测试环境默认 Fake。
