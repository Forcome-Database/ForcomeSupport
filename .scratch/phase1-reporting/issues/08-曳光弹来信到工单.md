# 08: 曳光弹：来信到工单

Status: resolved
Blocked by: 07

规格：[第一期：报表与台账](../spec.md)

**What to build:** 打通最细的一条收信路径：Fake Gmail 里放一封客户来信，几秒后它作为「待回复」工单出现在 P04。Gmail 客户端的最小形态（Pub/Sub pull + `history.list` 拉取收件，真实与 Fake 同一接口）；消息入库，对「邮箱 + Gmail 消息 ID」唯一约束去重（E-15），并按 RFC `Message-ID` 跨邮箱判重：同一封邮件已在其他店铺邮箱入库时只记「同时发送到」，不再归并（R-TK-07）；按收件邮箱识别店铺；发「来信已接收」事件，`ticket` 按 R-TK-02（同一客户渠道身份有未关闭的无订单工单则追加，否则新建）归并；建立最小客户对象（渠道身份）。第一期工单迁移表以纯函数落地（照 PRD 6.1 第一阶段迁移表；本张只需「新来信 → 待回复」与追加，其余迁移在后续待办补齐，但表结构与触发方、关闭原因字段一次定好）。P04 显示最简列表（工单号、主题、渠道与店铺、客户、状态、最近来信）。

**关键取舍**

- 邮件本身归 `channel`（`channel.message`：接入的事实），消息在工单里的归属与状态归 `ticket`（`ticket.ticket_message`，按邮件 id 唯一）；「来信已接收」以发布方命名、处理器在 `ticket`，依赖方向 `ticket → channel` 单向，跨模块不设外键（ADR 0005 修订，细化 09-24 修订的「消息归 ticket」）。
- 推送是环境级的全局客户端，邮箱按店铺选；Fake 邮箱被 watch 后才发推送、回放的来信在 watch 之后送达，与真实的 Gmail + Pub/Sub 一样「先 watch 才有推送」。测试里灌完店铺先 `t.runJobs()` 一次让邮箱开始监听。
