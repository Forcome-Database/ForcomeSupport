# 05: 钉钉同步与扫码登录

Status: claimed
Blocked by: 04, 31

规格：[第一期：报表与台账](../spec.md)

**What to build:** 成员与部门自动来自钉钉，成员用钉钉扫码登录。钉钉客户端（真实 + Fake，按环境变量切换）：Stream 长连接接收通讯录事件、每小时全量对账（常驻连接用 advisory lock 选主）；成员与部门只读同步。登录页按 G11（扫码二维码、2 分钟过期刷新）；扫码登录换出与开发登录同一种会话；被拒按 G12 三种原因（未分配角色、已停用、会话过期）。钉钉离职自动停用：立即失效会话、不能再登录（改派售后单见待办 23）。同步失败时保留上次数据、登录与权限不受影响；P18 钉钉卡超过 2 小时未同步显示「同步延迟」、连续 3 次失败显示「连接异常」，只给管理员发站内提醒（待办 31），不出全站横幅（E-32、6.9）。钉钉工作通知发送能力（内容带对象编号与时间，同一人 5 分钟内合并）一并落在 `core`，供后续通知使用。钉钉内免登不在第一期。

### 实现记录（2026-10-06，claude02）

**业务口径（原型与 PRD 没写，已用编排命令问协调者，先按建议实现；回复后若有改动另行返工）**

- Q1 钉钉同步失败给管理员的站内提醒：连续失败的第 1 次「钉钉同步失败」/「通讯录同步失败，成员与部门保持上次结果，登录与权限不受影响」，连续第 3 次（转连接异常）「钉钉连接异常」/「通讯录连续 3 次同步失败，成员与部门保持上次结果，登录与权限不受影响」，对象「P18 · 钉钉」；之后不重复，恢复后不发（11.4 没有钉钉恢复这一类）。一次同步 = 一次整点对账（失败不重试，见 Q6 附带的技术调整）。
- Q2 钉钉工作通知写法：一条——「【Forcome Support】标题」/ 说明 /「对象 · 月-日 时:分」；同一人 5 分钟内的合成一条——「【Forcome Support】N 条新通知」，之后每条「· 标题：说明（对象 · 月-日 时:分）」。合并方式：第一条进来开 5 分钟窗口，到点合成一条（验收项要求「5 分钟内的两条合并为一条」，所以第一条不能先单独发）。
- Q3 钉钉离职停用后又回到通讯录：恢复在职、角色与店铺范围清空（等同新成员），审计「钉钉恢复在职」；管理员停用的不随通讯录恢复。
- Q4 审计：只记「钉钉离职停用」「钉钉恢复在职」（对象类型「成员」、操作人「系统」）；通讯录新增与改名、换部门、换邮箱不记，钉钉卡的状态变化不记。
- Q5 扫码登录失败的浮层（G5 写法）：「登录失败：扫码结果已失效」+「请重新扫码。」；「登录失败：登录已过期」+「请重新扫码。」；「登录失败：暂时连不上钉钉」+「请稍后重新扫码；仍不行请联系管理员。」；换会话时的过渡画面「正在登录…」。
- Q6 取不到二维码：「加载二维码失败：<原因>」+「立即重试」；钉钉的扫码登录框加载不出来同 Q5 的「暂时连不上钉钉」并带「立即重试」。
- Q7 钉钉认得出、但不在本组织通讯录里的人扫码：按「未分配角色」显示（会看到管理员姓名；评审时提出）。
- 已确认的口径（协调者转达的用户 2026-10-04 口径）：钉钉应用已有，凭据由用户上线时自己填 .env；开发测试一律用 Fake。

**交付了什么**

- `integration`：钉钉客户端 `dingtalk`（全局，`CLIENT_MODE_DINGTALK`）——通讯录全量读取与按 ID 取人、取部门，扫码登录用授权码换出扫码人（`identifyByAuthCode`：unionid 与本组织的用户 ID，已离职的没有用户 ID），文本工作通知，Stream 通讯录事件的拉取、确认与断开。真实现（`integration/dingtalk.ts`）经出站 HTTP 客户端工厂（新增 `postJson`）调旧版 `oapi.dingtalk.com` 与新版 `api.dingtalk.com`，访问凭证缓存、`errcode` 翻译；Stream（`dingtalk-stream.ts`）用 undici 的 WebSocket 经进程共用的出站连接（`outboundDispatcher`，遵守 `NO_PROXY`），回应 ping、遇 disconnect 重连、事件转成任务后再回执。Fake 钉钉：通讯录、事件（可 silent）、一次性授权码（离职的人也能扫）、发出的工作通知、故障注入，从示例数据回放通讯录（`dingtalk-replay.ts`：8 位示例成员 + 两家生产厂负责人 `factory-head-<厂代码>`）。全局真实现一个进程只建一次，真实现拿到钉钉凭据。
- `core`：凭据 `DINGTALK_CLIENT_ID` / `_SECRET` / `_AGENT_ID`（钉钉用真实接口时必填，缺了拒绝启动；`defaultClientMode`）；钉钉工作通知 `core.work_notification`、`queueWorkNotifications`、每分钟的 `core.send_work_notifications`（同一人最早一条等满 5 分钟后合成一条、带对象与时间、失败下一分钟再试、满 5 次放弃、发出后才记已发）；独占常驻拉取的选主（`feeds.ts`：会话级咨询锁、持锁连接心跳、断开即交还并断开长连接）；`createCoreJobHandlers` 移到 `job-handlers.ts`。
- `org`：成员表加钉钉用户 ID、unionid、钉钉部门 ID、邮箱、停用原因与时间、同步时间，部门表 `org.department`，同步状态 `org.dingtalk_sync`（迁移 0019）；通讯录写入 `directory.ts`（`syncMember` 按用户 ID 再按 unionid 认人：新人无角色无范围、资料随钉钉、离职停用并删会话、回到通讯录恢复在职但清空角色、管理员停用的不恢复、用户 ID 换了人旧成员解绑停用、换新 ID 回来按离职后又回来处理、取来之后被更新过的不写）；同步 `dingtalk-sync.ts`（Stream 常驻拉取 `org.dingtalk_stream` 独占、事件任务 `org.dingtalk_event`、每个整点与启动时的全量对账 `org.dingtalk_reconcile`（失败不重试，每次算一次同步）、同步状态、失败第 1 / 3 次提醒管理员、P18 钉钉卡的 `dingtalkConnection`）；扫码登录 `dingtalk-login.ts`（`POST /api/auth/dingtalk/start`、`/login`，开发工具 `POST /api/dev/dingtalk/scan`）；登录共用 `sign-in.ts`（被拒响应体、换会话与审计，开发登录一起用）；`notifyMembers` 按 11.4 一并排入钉钉工作通知；审计「钉钉离职停用」「钉钉恢复在职」；示例成员加载步骤补钉钉用户 ID、恢复被钉钉停用或清空角色的示例成员。

**关键取舍**

- **通讯录里的人都同步成成员**（PRD 11.1 Member「状态随钉钉在职状态」、G11「由管理员在本系统分配角色后才能进入」）：新人没有角色、店铺范围为空；P20 的「从钉钉添加」就是从这些人里选人分配角色（待办 06 留言）。另一种做法是另建通讯录镜像表、P20 添加时才建成员——多一张表、两处同步，且 G12「未分配角色」还得另判，不取。
- **对账先取全再写**：取的过程中任何一步出错、或取到 0 人（多半是权限范围没配好），什么也不写，成员与部门保持上次结果（E-32「登录与权限不受影响」）。写库时只改快照开始之前同步过的行（`dingtalk_synced_at`），快照期间由事件更新过的不被旧快照覆盖或误停用；事件同理（取之前记时刻，取来之后被更新过的不写），同一个人的几个事件被几个 worker 并发处理时旧的不盖新的。
- **按 unionid 认人**：钉钉的用户 ID 组织内唯一但可以复用、离职后换不到；unionid 同一个人不变。离职的人扫码按 unionid 认出后显示「账号已停用」（G12，验收项 2 的真实接口路径）；重新入职换了新 ID 认作同一个人；同一个 ID 给了别人则不让新人接手旧成员的角色。
- **对账失败不重试**：每个整点一次、每次算一次同步，上次成功超过 2 小时先「同步延迟」、连续 3 次（约 3 小时）才「连接异常」，与 K20 的示例一致；最初的「10 分钟重试、最多 2 次」会让「同步延迟」几乎出不来（规格轴评审提出）。
- **工作通知 5 分钟窗口**：验收项要求「5 分钟内的两条合并为一条」，所以第一条进来后等满 5 分钟再合成发出（最多晚 5 分钟），不是先发第一条。11.4 渠道里有钉钉的类型由 `notifyMembers` 一并排入，业务调用方不另发（取代待办 31 留言里「调用方另发」）。
- **Stream 选主**：钉钉 Stream 一个应用只该有一条长连接，用会话级咨询锁选出持有者（ADR 0008 原定），持锁连接每 30 秒探活，断了就停拉、断开长连接、重新选主。Gmail 推送要不要独占留给 09。
- **扫码登录的 state**：只发给 `/api/auth/dingtalk` 的 httpOnly Cookie，登录时逐字节比对且只用一次，防跨站伪造登录；状态不进库（10 分钟有效，刷新二维码即换新）。
- **登录入口**：开启开发登录（非生产环境）时未登录仍去开发登录页，钉钉扫码登录页在 `/login`（演示与 e2e 直接打开）；生产环境未登录去 `/login`，7 天未操作过期的先显示 G12「已退出登录」。会话过期的原因只在过期后的第一个请求返回（服务端随即删会话），前端记一次标记（`takeSessionExpired`）。
- **示例数据**：生产厂负责人（刘厂长、周厂长）只进 Fake 通讯录（夹具里只有姓名），对账后作为没有角色的成员出现在开发登录列表（写「未分配角色」），e2e 用他们测 G12「未分配角色」。夹具与原型数据不改。
- **开发测试环境联调真实钉钉后的恢复**：示例成员不在真实通讯录里会被按钉钉离职停用，切回 Fake 后灌示例数据这一步把被钉钉停用或清空角色的示例成员恢复成示例数据（只在非生产环境）。
- **迁移 0019 原地重生成**：评审后加 `dingtalk_union_id` 时 0019 还没有任何持久库执行过（核对：本机开发库 `forcome` 有 18 条迁移记录、开发测试环境 19 条即 0000–0018，只有每次重建的 `forcome_e2e` 跑过），所以删掉重生成，没有另开 0020。
- **CorpId 第一期去掉**：扫码登录用 unionid 判断是不是本组织的人，用不到 CorpId；第二期钉钉内免登（`dd.requestAuthCode` 要 corpId）时再加。
- **Node 24**：照 README「开发」，便携 Node 24.21.0 复制到本会话临时目录、只在会话命令里前置 PATH，pnpm 10.34.6 经 corepack；没有改系统配置。

**自己写而没用现成库的部分**

- 钉钉服务端接口（`integration/dingtalk.ts`，约 250 行，多是参数与返回的 zod 解析）：官方 `@alicloud/dingtalk` 只覆盖新版接口（通讯录部门与成员、工作通知、unionid 换 userid 都在旧版 oapi），且自带一套 HTTP 栈，不走本系统的代理分流、超时与错误翻译（ADR 0003、0009）。
- Stream 长连接（`dingtalk-stream.ts`，约 150 行）：官方 `dingtalk-stream` 在回调里同步回执（不能等转成任务后再确认）、连接失败只在内部重试不报给调用方（连接状态与退避要由常驻拉取掌握）、日志写 console、WebSocket（ws）不读代理变量；协议只有注册、连 WebSocket、回 ping、回执几步。
- 常驻拉取的选主（`core/feeds.ts`，约 80 行）：pg-boss 的单例任务管不了常驻长连接；会话级咨询锁是 PostgreSQL 自带的，ADR 0008 原定做法。
- 工作通知的合并与发送（`core/work-notifications.ts`）：通知服务（Novu 等）要外部服务、不能与业务数据同一事务写入，且钉钉的发送本来就要自己调；合并只是一条按人分组的查询。
- 示意二维码（`lib/dingtalk-login.ts` 的 `demoQrModules`，固定种子的 mulberry32）：只在 Fake 时画、不能扫，照原型 `qr_svg()` 的样子；二维码库（qrcode 等）画的是真码，这里不需要真码，也不该引入新依赖。
