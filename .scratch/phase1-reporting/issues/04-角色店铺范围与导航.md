# 04: 角色、店铺范围与导航

Status: resolved
Blocked by: 02

规格：[第一期：报表与台账](../spec.md)

**What to build:** 用开发登录以任一角色进入系统时，只看到自己该看到的东西。服务端会话（PostgreSQL 存储，httpOnly、Secure，无操作 7 天过期）；6 个固定角色（坐席、客服主管、售后负责人、知识库负责人、管理员、生产厂对接人）。能力矩阵按 PRD 10.1 的细粒度能力写成 `contracts` 常量，每项标注上线阶段（第一期新增：标记来信无需回复、为未归属来信指定店铺、新建与编辑登记、设为已完成、补登与修改汇率、改派售后单负责人、查看财务字段、查看审计日志 P27），前端据此显示、后端据此强制；多角色权限取并集。店铺数据范围作为所有仓储查询的必需上下文参数（缺了编译不过，ADR 0010）。提供财务字段过滤工具（成本、承担比例、承担金额只对客服主管、售后负责人返回），供后续接口、导出、下钻与审计输出复用。外壳按 PRD 4.1 第一阶段表：导航与默认首页按角色（多角色导航取并集，默认首页按 坐席/客服主管 → 售后负责人 → 知识库负责人/管理员 取第一个）；顶栏不显示店铺切换、全局搜索与导航角标；头像菜单含「审计日志」「密度」「退出登录」。只有生产厂对接人角色的成员第一期登录返回无权限（G12）。直接访问无权页面显示 G2（按钮「返回首页」），越权访问写审计（E-24）。顶栏密度切换（舒适 / 紧凑），偏好存服务端。

**关键取舍**

- 导航与默认首页由后端按能力矩阵算好放进 `/api/me`：前端只照它显示，同一份计算可以经主接缝做集成测试；页面把关用前端 `src/lib/pages.ts` 登记的能力与 `contracts` 的 `can`，同一份矩阵。
- 能力矩阵一项对应 PRD 10.1 的一行（捆在一行里的几个动作权限相同，强制时等价）；K17 由常量直接渲染，所以文案取原型 K17 的写法。单元测试直接读 `prd_d.md` 的 10.1 表与原型 `build_settings.py` 的 MATRIX 逐格核对，任一边改了就失败。
- 越权访问审计（E-24）只针对数据：页面店铺筛选或详情所属店铺不在范围内时记 `access.denied` 并 403；能力不足的 403 不记审计——PRD E-24 的定义是「访问未授权店铺或他厂单据」，界面不给没有能力的人入口，从链接进入无权页面时 G2 是前端画面、不调接口。
- 「缺了编译不过」：仓储查询把带品牌的 `StoreScope` 作为必需参数；成员的范围只由 `org` 构造（lint 强制），系统操作用 `SYSTEM_STORE_SCOPE`，详情接口经 `access.findOwned` 取对象并校验归属，处理器不直接碰不受限的范围。`updateWithVersion` 仍按 id 更新，口径写进 ADR 0010 修订。
- 公共工具还没有业务接口使用，集成测试用测试里定义的示范接口与示范表（`startTestHarness({ routes })`）当第一个使用者，经主接缝验证店铺范围（SQL 条件）、越权审计（列表与详情）、财务过滤；与待办 02 把示范 Fake、示范任务放在测试里是同一个做法，生产代码里没有示范接口。示例数据里没有的成员（多角色、店铺受限、已停用）用 `t.addMember`（经 `org` 的 `createMember`），05、06 上线后可改走钉钉 Fake 与 P20。
- 财务字段：在输出结构里标记，过滤按结构递归、不认识的一律不放行（未声明的键去掉，联合等结构里的财务字段报错）；可见性只认 `finance.view` 的完整权限（`canViewFinance`），生产厂对接人的「本厂部分」只在第二期工厂工作台的专用输出里给，兼任坐席也看不到。评审发现最初用 `can` 判断会让「坐席 + 生产厂对接人」看到财务字段，已修并加测试。
- 会话：续期按 1 分钟节流；带 `x-forcome-background: 1` 的后台请求（31 的轮询、18 的推送后重新拉取）不续期，否则开着页面就永不过期。迁移清掉待办 02 的旧会话：02 的 Comments 原说「已开的会话不失效」，但会话改成外键引用成员、迁移时成员表还是空的，只能请已登录的人重新登录一次。

**自己写而没用现成库的部分**

- 能力矩阵与导航（约 60 行逻辑加常量）：CASL、casbin 是通用的 RBAC / ABAC 引擎，表达不了「上线阶段」与 K17 要显示的「○ 范围说明」「部分能力文字」；PRD 的矩阵是固定表格，常量加几个函数就够。
- 财务字段过滤（约 100 行）：zod 没有字段级的可见性过滤，`.omit()` 要逐个结构列键、不递归，也不能把值换成「已隐藏」；这里用 zod 自带的 registry 标记字段，按结构递归。
- 店铺范围类型与查询条件（约 40 行）：drizzle 没有行级范围的助手，PostgreSQL RLS 已由 ADR 0010 否决。
- 会话与 Cookie（约 80 行，Cookie 读写用 `hono/cookie`）：Lucia 已停止维护，better-auth 等是完整的认证框架（自带用户表与登录方式），与「只有钉钉扫码加开发登录、成员来自钉钉」的 ADR 0010 设计冲突。
- `EmptyState`（约 40 行）：shadcn 的 Empty 只是一组带默认样式的 div、没有行为，要逐项改成原型 `empty()` 的尺寸，等于重写，所以直接照 `empty()` 写，`LoadError`、G2、G12 共用。
- 下拉菜单用 shadcn CLI 生成后改样式（生成时 CLI 误加了一个名为 `cn` 的 npm 依赖，已撤销，改用仓库的 `@/lib/utils`）。
