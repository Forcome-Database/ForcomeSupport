# 第一期：报表与台账

Status: ready-for-agent
Type: spec

依据：`docs/技术方案.md` v1.2 第 11.1 节（第一期实现契约 11 条、实施切片 11 片）；ADR 0003、0005–0011、0013；PRD v2.10（D-22、D-23）；`.scratch/tech-plan/map.md`。业务术语以 PRD 1.4 为准，项目级术语见 `CONTEXT.md`；规则、页面、状态、验收编号沿用 PRD。

## Problem Statement

FSH 的客服与售后现在没有一个统一、可信的数据面：

- 管理层要看工单量、首次回复时长、亚马逊 SLA 达标率与售后成本，只能从海帆、积加、各平台后台人工导出再拼表，口径不一、费时、总是滞后。
- 售后单散落在各人手里的登记表里，字段不齐、币种混杂（USD、CAD、MXN），当月到底花了多少钱、谁承担多少说不清，也无法按责任类型拆解。
- 4 个店铺邮箱（2 个亚马逊买家消息、2 个 Shopify 客服）里的来信没有按店铺、订单归并成工单，没人能回答「这张订单客户来过几次信、我们回了没有、回得够不够快」。
- 成员与权限没有统一来源，店铺之间的数据可见范围、成本等财务字段的可见范围都靠人记。

第一期要先把「数据」这一层建起来：让来信、订单、回复、售后成本自动进系统，报表替代人工导出，台账成为售后单唯一的登记处。回复仍由海帆和人工在原渠道发出，本系统第一期不发信、不调模型、不接积加。

## Solution

交付一套内网可用的生产系统（第一期），包含：

- **登录与组织**：成员与部门从钉钉通讯录同步，钉钉扫码登录；6 个固定角色、店铺数据范围、财务字段可见性由后端强制；按角色进入默认首页（坐席与客服主管 P04，售后负责人 P13，知识库负责人与管理员 P17）。
- **收取与归并**：同步 4 个邮箱的收件与「已发送」，自动识别店铺、站点、来源（客户 / 平台通知 / 生产厂 / 其他供应商 / 营销），抽取订单号并在本地订单镜像中校验，按 R-TK-01/02 归并成工单；识别不出店铺的来信进入「未归属店铺」队列，由客服主管指定店铺。
- **订单镜像**：亚马逊经 SP-API（非受限角色）、Shopify 经 Admin API 准实时同步到本地，上线前回补 90 天，夜间对账近 7 天，镜像缺失时按订单号补拉。
- **工单（只读 + 两个写操作）**：P04 工单列表、P05 工单详情按第一期生命周期（待回复 / 等客户 / 已解决 / 已关闭）自动推进；唯一的写操作是客服主管「指定店铺」与坐席、客服主管对单封来信「标记无需回复」。
- **首次回复与 SLA**：把「已发送」里的我方回信归到工单，按 R-SL-08 计算每封来信的首次回复与 SLA 结果。
- **登记台账 P13**：售后单统一登记（新建登记、补登、改状态），按处理方式的必填矩阵计算当月登记完整率，多币种按欧洲央行汇率折算并冻结美元金额，导出 Excel。
- **报表 P17**：工单量、首响中位数、SLA 达标率（亚马逊）、售后成本，以及「每日工单量」「售后成本按责任类型」两张图；按店铺、站点筛选；可下钻到 P04、P13；导出。
- **设置**：P18 渠道与店铺（连接状态、店铺表、审计日志查看）、P20 团队与权限（成员、角色、店铺范围、停用）。
- **历史导入与上线切换**：近 90 天邮件按邮件时间回放、售后登记表一次性导入、选定 T0 切换到实时。
- **运维落地**：WAL 归档与每日备份、恢复演练、worker 自检与宿主机存活检查、开发测试与生产两套环境、真实环境验收矩阵。

外部资质（SP-API、Shopify `read_all_orders`、钉钉应用、Google 全域委派等）到位之前，全部功能用 Fake 开发与验收，到位后逐个店铺切换。

验收：报表替代人工导出；当月售后单登记完整率 ≥ 98%。

## User Stories

### 登录、组织与权限

1. 作为 FSH 成员，我想用钉钉扫码登录，这样不用再记一套账号密码。
2. 作为 FSH 成员，我想登录后直接进入我这个角色的默认首页（坐席与客服主管 P04、售后负责人 P13、知识库负责人与管理员 P17），这样一进来就是我最常用的页面。
3. 作为 FSH 成员，我想只看到第一期存在、且我有权限的导航入口，这样不会点进空页面或无权限页面。
4. 作为 FSH 成员，我想从链接直接访问无权页面时看到明确的「无权限」状态（G2），这样知道不是系统坏了。
5. 作为 FSH 成员，我想 7 天不操作才需要重新登录，这样日常使用不被频繁打断。
6. 作为管理员，我想成员与部门自动从钉钉通讯录同步（Stream 实时 + 每小时全量对账），这样组织变化不需要在两边维护。
7. 作为管理员，我想在 P20 从钉钉通讯录添加成员并必填角色与店铺数据范围，这样新成员登录后立即只看到授权店铺的数据（AC-ST-06）。
8. 作为管理员，我想给一个成员分配多个角色、权限取并集，这样兼岗的同事不需要两个账号。
9. 作为管理员，我想在 P20「角色权限」页签看到只读的完整权限矩阵（K17），这样能向业务方解释谁能做什么。
10. 作为管理员，我想手工停用成员时，如果他还负责进行中的售后单，系统先提示改派（AC-ST-02 第一期改写），这样不会有售后单无人负责。
11. 作为管理员，我想钉钉离职的成员被自动停用、会话立即失效，负责的进行中售后单进入客服主管的改派队列（AC-ST-05 第一期改写），这样离职交接不会漏单。
12. 作为管理员，我想钉钉同步失败时保留上次同步的成员与部门、登录不受影响，并收到站内提醒（E-32），这样同步故障不会把所有人锁在门外。
13. 作为客服主管或售后负责人，我想在所有页面、导出、下钻与审计输出里都能看到成本、承担比例、结算相关金额，这样我能管住钱。
14. 作为坐席、知识库负责人或管理员，我不应看到成本、承担比例与结算金额（包括报表聚合、导出与下钻），这样财务数据只在授权范围内流转。
15. 作为任意成员，我想只看到授权店铺的工单、售后单、台账与报表数据（R-ST-06），访问其他店铺的数据时看到无权限并被记入审计（E-24）。
16. 作为任意成员，我想在顶栏切换舒适 / 紧凑两档密度，偏好保存在服务端，刷新或重新登录后保持（AC-ST-04）。

### 渠道与店铺

17. 作为管理员，我想在 P18 看到亚马逊 SP-API（含订单通知队列 SQS 状态）、Shopify、Gmail、钉钉四张连接卡，每张卡显示最近同步时间与连接状态（已连接 / 同步延迟 / 连接异常 / 未连接），这样一眼知道数据是否在流动。
18. 作为管理员，我想积加与易仓卡显示「第二阶段接入」、不显示 17TRACK 卡，这样不会误以为它们已接通。
19. 作为管理员，我想对每个渠道点「测试连接」，这样外部资质开通后能马上验证。
20. 作为管理员，我想在右侧抽屉新增、编辑店铺（店铺名、平台、站点、默认站点、进线邮箱、平台标识、签名与覆盖项），并在字段下方看到店铺名重复、平台标识为空、邮箱格式错误的报错（K8、AC-ST-01）。
21. 作为管理员，我想每个店铺可以选择使用真实适配器还是 Fake，这样外部接口开通后能逐个店铺切换。
22. 作为管理员与客服主管，我想某个渠道连续 3 次失败时全站顶部出现红色横幅（G4），并收到站内通知与钉钉工作通知（E-01、E-02），这样能尽快处理。
23. 作为管理员，我想在 Gmail 断开时看到恢复指引（检查全域委派与邮箱状态，K7），恢复后系统自动补拉，这样不丢来信。
24. 作为管理员或客服主管，我想在 P18「查看审计日志」查看全部审计记录（操作人、角色、对象、动作、前后值、时间、来源 IP），其他角色只能看到自己的操作记录（PRD 10.2）。

### 收取与归并

25. 作为客服主管，我想 4 个店铺邮箱的新来信在几分钟内出现在系统里（Pub/Sub pull 常驻 + 每 5 分钟 `history.list` 兜底），这样工单列表反映的是当下。
26. 作为客服主管，我想同一封邮件无论被推送几次都只进系统一次（E-15），这样工单量不会虚高。
27. 作为客服主管，我想系统按收件邮箱识别店铺，并按唯一口径识别站点（亚马逊按发件域 amazon.com / .ca / .com.mx，Shopify 按订单收件国家，无订单时取店铺默认站点），这样报表与筛选按站点统计是可信的（AC-TK-14）。
28. 作为客服主管，我想平台通知与营销邮件按发件人规则自动归档、不建工单，这样工单量只反映真实客户诉求。
29. 作为客服主管，我想生产厂与其他供应商的来信照常建工单并标注来源，但不计入工单量与 SLA，这样既不漏信又不污染客服指标。
30. 作为客服主管，我想系统从来信里抽取订单号（亚马逊 `3-7-7` 格式；Shopify 按订单名在该店铺内匹配）并在该店铺的订单镜像中校验，镜像没有时按需补拉，这样工单能关联到真实订单。
31. 作为客服主管，我想来信抽不到订单号时，系统按客户邮箱在该店铺反查订单，唯一命中才关联，命中多笔或为零按客户维度归并，这样不会错关联。
32. 作为客服主管，我想带订单号的来信按 R-TK-01 归并：同店铺同订单有未关闭工单则追加（AC-TK-01），有 30 天内关闭的则重开为「待回复」（AC-TK-03），否则新建（AC-TK-04）。
33. 作为客服主管，我想无订单号的来信按 R-TK-02 归并：同一客户渠道身份有未关闭的无订单工单则追加，否则新建；同一客户两笔不同订单生成两张工单（AC-TK-02）。
34. 作为客服主管，我想并发到达的同一订单来信不会各建一张工单，这样不会出现重复工单。
35. 作为客服主管，我想识别不出店铺的来信进入 P04 上只对我可见的「未归属店铺」来信队列，并收到提醒，SLA 按原到达时间照常计时（AC-TK-09、E-13）。
36. 作为客服主管，我想在未归属店铺队列里为一封来信指定店铺，系统随即按 R-ST-02 重新识别站点、关联订单并归并成工单，SLA 保留原到达时间，并可在 5 秒内撤销（AC-TK-11 第一期改写）。
37. 作为客服主管，我想 Gmail 连接中断恢复、或增量游标过期时，系统按时间区间全量补拉，补拉完成前「最近同步成功时间」不前移，这样报表不会谎报数据新鲜度。

### 订单镜像

38. 作为客服主管，我想亚马逊订单（状态、商品行、MFN/AFN、承诺时效、城市/州/国家、MFN 单号）经 `ORDER_CHANGE` 通知与每 3–5 分钟的增量兜底同步到本地，这样工单详情的订单卡是准实时的。
39. 作为客服主管，我想 Shopify 订单（含客户邮箱、收件地址、履约单号）每 1–2 分钟增量同步，这样 Shopify 来信能按邮箱反查订单。
40. 作为管理员，我想上线前开始回补近 90 天订单（Shopify 61–90 天依赖 `read_all_orders`，申请不下来则回补 60 天并在报表注明），并每天夜间对账近 7 天，这样历史来信也能关联到订单。
41. 作为管理员，我想 SP-API 调用按「卖家 × 接口」共享令牌桶限流、增量同步优先、回补与对账让路，这样不会因配额耗尽导致实时同步停摆。
42. 作为坐席，我想在 P05 的订单卡上看到平台镜像的订单信息，这样不用切到卖家后台。

### 工单生命周期

43. 作为客服主管，我想新来信在无可追加或重开的工单时新建「待回复」工单，这样每个客户诉求都有落点。
44. 作为客服主管，我想系统识别到我方回复、且没有其他未回复的应回复来信时，工单自动转「等客户」。
45. 作为客服主管，我想「等客户」或「已解决」的工单收到新的应回复来信时回到「待回复」。
46. 作为客服主管，我想「等客户」或「已解决」的工单 7 天无来信自动关闭（AC-TK-07）。
47. 作为客服主管，我想「待回复」工单 14 天无新来信自动关闭、原因「未识别到回复」，其中未回复的来信 SLA 计未达标（AC-TK-13），这样工单不会永远挂着。
48. 作为坐席或客服主管，我想在 P05 的来信卡上把单封来信「标记无需回复」，5 秒内可撤销，该来信不计入 SLA；当工单全部未回复来信都被标记后，工单转「已解决」。
49. 作为客服主管，我想工单的每次状态变化都有记录（时间、事件、触发方），这样 P05 的状态流转与报表的工单量都有据可查。

### 首次回复与 SLA

50. 作为客服主管，我想系统同步 4 个邮箱的「已发送」，按 Gmail 线程与 `In-Reply-To`、`References` 把我方回信归到工单，这样海帆与人工发出的回复也能被统计。
51. 作为客服主管，我想同一工单内我方一封回复结束它之前所有未回复来信的计时，起点为 Gmail `internalDate`（R-SL-08）。
52. 作为客服主管，我想带 `Auto-Submitted` 或自动回复标记的我方邮件不算回复。
53. 作为客服主管，我想亚马逊来信按 24 自然小时计 SLA，Shopify 与邮件按内部目标 24 小时（不计入平台考核）。
54. 作为客服主管，我想在 P04、P05 看到每封来信的 SLA 结果或剩余（R-SL-03 的显示格式与颜色），但第一期不产生任何 SLA 提醒。
55. 作为客服主管，我想报表注明「只统计经店铺邮箱发出的回复」，这样不会误解指标覆盖范围（Q-26）。

### 工单页

56. 作为坐席、客服主管、售后负责人或知识库负责人（只读），我想在 P04 按店铺、渠道、站点、状态、最近来信时间（默认近 30 天）筛选工单，筛选条件保存在地址栏，这样可以分享与回退。
57. 作为上述角色，我想筛选无结果时看到空状态与「清除筛选」（I10）。
58. 作为上述角色，我想点击 P04 的行进入 P05，第一期所有工单都在 P05 查看。
59. 作为上述角色，我想在 P05 看到全程记录（客户来信、我方回复为消息卡，系统事件为事件行，按日期分组，可切换「全部 · 仅消息 · 仅事件」）、SLA 结果、状态流转与订单卡。
60. 作为上述角色，我想 P04、P05 上不出现意图、情绪、标签、负责人、批量条、草稿、回复框、AI 摘要、审批与售后操作、合并等第一期不存在的元素，这样界面不会误导。
61. 作为坐席或客服主管，我想数据变化时页面自动刷新（SSE 推送后重新拉取），这样不用手动刷新。

### 登记台账

62. 作为售后负责人或客服主管，我想在 P13 点「新建登记」打开右侧抽屉，按处理方式（调整安装方式 / 寄配件 / 退款或部分补偿）列出适用字段，这样只需填与这张单相关的内容。
63. 作为登记人，我想来源工单可以不填，负责人默认为我本人，售后负责人可改负责人。
64. 作为登记人，我想选择责任类型后三组承担比例（产品成本 / 快递物流 / 其他费用）按种子数据的默认值预填，可修改，比例为 0–100 的整数、FSH 与工厂两侧自动互补。
65. 作为登记人，我想责任为物流问题时必须填写索赔对象（承运商或易仓）与索赔状态。
66. 作为登记人，我想以原币（USD / CAD / MXN）填写产品成本、运费、额外赔偿、其他与退款或补偿金额，系统按费用发生日取汇率折算并冻结美元金额；没有发生的费用项填 0 视为已填。
67. 作为售后负责人，我想修改某条记录的汇率，修改被记入审计。
68. 作为登记人或售后负责人，我想随时把售后单设为「已完成」而不要求字段齐全，系统记录完成时间；缺失的适用字段在列表中标黄「待回填」。
69. 作为售后负责人，我想对已完成的单行内补登缺失字段、修改状态，所有修改记入审计。
70. 作为售后负责人或客服主管，我想取消售后单时必须填写原因，已产生的费用照常保留并计入成本（AC-AS-16）。
71. 作为售后负责人，我想进行中、尚未寄出的单在快递单号等列显示「—」而不是「待回填」、也不出现补登（AC-AS-22）。

73. 作为售后负责人，我想按日期、店铺、处理方式、责任筛选台账，并看到合计行（产品成本、运费、额外赔偿、FSH 承担、工厂承担），首列与合计行在横向滚动时固定。

## Implementation Decisions

### 范围与架构

- 第一期涉及模块：`org`、`channel`、`order`、`ticket`、`aftersales`（仅台账）、`report`、`core`、`integration`（Gmail、钉钉、SP-API 订单、Shopify 订单、汇率）。**不接**积加、17TRACK、模型，**不开**公网入口，不建工厂工作台。
- 模块化单体（ADR 0005）：pnpm workspace，前端一个应用、后端一个应用（`api`、`worker`、`migrate` 三个入口）、共享包 `contracts`（zod 模式、状态枚举中英对照、能力矩阵）、`calendar`（工作日历纯函数）、`config`。模块只经各自入口导出的服务互调，不跨模块读写表；唯一例外是 `report` 用只读数据库角色直读各模块的表。边界在 CI 用 lint 强制。
- 跨模块联动在业务事务内发领域事件（插入 pg-boss 任务，任务表即发件箱，ADR 0008），由 worker 处理。第一期的关键事件：`channel`「来信已接收」→ `ticket` 归并；`channel`「我方发信已同步」→ `ticket` 回复识别；`org`「成员已停用」→ `aftersales` 改派队列。
- 后端 Node 24 + Hono（`@hono/zod-openapi`，接口直接用 `contracts` 的 zod 模式声明）+ Drizzle + PostgreSQL 18，一个模块一个 schema（ADR 0006）。前端 Vite + React 19 单页应用，TanStack Router（筛选条件经 zod 校验放在 URL）/ Query / Table，react-hook-form，shadcn/ui + Tailwind v4，shadcn Charts（ADR 0007）。界面只做中文、只做浅色，两档密度。
- 部署：Docker Compose（`caddy`、`api`、`worker`、`migrate`、自建 `postgres` 镜像内置 WAL-G），无 Redis、无对象存储。所有外部调用主动连出：境外经固定代理，境内（钉钉）经 `NO_PROXY` 直连（ADR 0003）。**第一期就需要内网 HTTPS**（内网子域名 + DNS-01 证书），会话 Cookie 为 `Secure`。
- 部署流水线：GitHub + Actions 云端跑类型检查、lint（含边界）、单元测试、集成测试（真实 PG 18 + Fake），至少 1 名人工评审；内网自托管运行器按两类任务部署（开发测试 / 生产，生产需打标签 + 人工批准）（ADR 0013）。

### 数据约定

- 主键 UUIDv7；业务编号另设一列，由 `core` 在事务内生成：工单 `T-日期-4 位当日序号`（日期取首封来信日期，回放同样适用），售后单 `S-创建日期-4 位全局递增序号`。
- 时间一律 `timestamptz`（UTC）；日界与工作日历按 `Asia/Shanghai`。
- 金额 `numeric(12,2)` + 币种；每条金额另存汇率、汇率日期、汇率来源、冻结的美元金额（四舍五入到分）。
- 主表带 `version` 列做乐观锁；不做软删除，作废与取消用状态表示。
- 审计：服务层在写事务内记录操作人、角色、来源 IP、完整前后值；系统操作记为「系统」；登录、登出、导出也记；只读查询不记，越权访问（E-24）除外。
- 实时推送：数据变化时 `NOTIFY`，api 监听后经 SSE 推「某对象变了」，前端让对应缓存失效。

### 各模块职责与对外接口（第一期）

**`core`**
- 审计写入与查询（按 PRD 10.2 可见范围过滤）；业务编号生成；配置读取；可注入时钟（归并、关闭、重开、SLA、扫描任务、回放都接收显式「当前时间」）；站内通知（最小形态：渠道连接异常、未归属店铺提醒，含已读状态）；钉钉工作通知发送（内容带对象编号与时间，同一人 5 分钟内合并）。
- 汇率：每日任务读取欧洲央行 `eurofxref-daily.xml`（补数与历史用 90 天或全量历史文件），以 EUR 交叉计算 USD/MXN、USD/CAD 并入库；Frankfurter 作备用；对外提供「按日期取汇率（缺失取最近可用日并返回实际日期与来源）」。

**`org`**
- 钉钉 Stream 通讯录事件 + 每小时全量对账，同步成员与部门（只读）；钉钉扫码登录换出服务端会话（PostgreSQL 存储，httpOnly、Secure，无操作 7 天过期）。
- 6 个固定角色；能力矩阵是 `contracts` 中的常量，前端据此显示、后端据此强制；可多角色，权限取并集。
- 店铺数据范围：所有仓储查询必须接收带授权店铺列表的上下文参数，缺了编译不过；不用 RLS（ADR 0010）。
- 财务字段过滤：成本、承担比例、FSH/工厂承担金额只对客服主管、售后负责人返回；其余角色在接口输出、报表聚合、导出、下钻、审计输出中一律过滤。
- 成员停用两条路径：手工停用前检查该成员负责的进行中售后单，有则拒绝并提示先改派；钉钉离职自动停用时立即失效会话，负责的售后单进入客服主管的改派队列（「待分配」只是归属标记，不改业务状态）。
- 默认首页按角色（多角色时按 坐席/客服主管 → 售后负责人 → 知识库负责人/管理员 的顺序取第一个）；密度偏好存服务端。
- 开发登录：只在非生产环境由环境变量开启，生产构建禁用。

**`channel`**
- 店铺（Store）与进线邮箱配置（P18）：店铺名唯一、平台标识必填、邮箱格式校验；每个店铺配置默认站点与「真实 / Fake」适配器选择。
- Gmail 客户端：服务账号 + 全域委派，4 个邮箱；Pub/Sub pull 常驻 + 每 5 分钟 `history.list` 兜底；「已发送」也同步；每天续订 `watch`（不按标签过滤）；游标过期按 `internalDate` 区间全量补拉，补拉完成前「最近同步成功时间」不前移；水位只在持久化成功后推进。常驻连接用 advisory lock 选主。
- 去重：消息表对「邮箱 + Gmail 消息 ID」唯一约束，冲突即视为重复（E-15）。
- 来源识别：可配置的发件人规则表（亚马逊通知发件地址、Shopify 系统邮件、已登记生产厂邮箱、`List-Unsubscribe` 等头），判定 客户 / 平台通知 / 生产厂 / 其他供应商 / 营销。平台通知与营销归档、不建工单；生产厂与其他供应商照常进入归并并带来源标记。规则表与已登记生产厂邮箱随种子数据提供。
- 店铺与站点识别：按收件邮箱识别店铺；站点唯一口径——亚马逊按发件域，Shopify 按订单收件国家，无订单时取店铺默认站点。识别不出店铺 → 未归属店铺来信队列（尚未归并成工单）。
- 订单号抽取：亚马逊正则 `\d{3}-\d{7}-\d{7}`；Shopify 按订单名（如 `#1063`）在该店铺内匹配；抽取结果交 `order` 校验。
- 完成后发「来信已接收」「我方发信已同步」事件。
- 渠道连接状态（6.9）：已连接 / 同步延迟（Gmail、订单 10 分钟，钉钉 2 小时）/ 连接异常（连续 3 次失败）/ 未连接；连接异常触发全站横幅与通知。

**`order`**
- 本地订单镜像：平台订单、商品行、发货与单号快照；以平台订单号为关联键，Shopify 另存订单名（店铺内唯一）。
- 亚马逊：SP-API Orders v2026-01-01，只用非受限角色；`ORDER_CHANGE` → SQS 长轮询 + 每 3–5 分钟 `lastUpdatedAfter` 增量兜底；每个「卖家 × 接口」共享令牌桶，增量优先、回补与对账让路，配额以响应头为准。
- Shopify：Admin GraphQL，每 1–2 分钟 `updated_at` 增量；令牌 24 小时过期、每 20 小时提前刷新（动态凭据用主密钥 AES-GCM 加密存库）。
- 回补 90 天（Shopify 61–90 天依赖 `read_all_orders`，否则 60 天并由报表注明）；每天夜间对账近 7 天。
- 对外接口：「在某店铺内按订单号 / 订单名查订单（镜像没有则按需补拉）」「在某店铺内按客户邮箱反查订单」「各数据源最近同步成功时间」。
- 说明：亚马逊非受限角色读不到买家邮箱，邮箱反查实际只对 Shopify 生效。

**`ticket`**
- 客户（Customer，最小形态）：渠道身份（邮箱或亚马逊中转地址）；第一期不做身份合并。
- 归并（R-TK-01、R-TK-02）：在事务内按「店铺 + 订单号」或「店铺 + 客户渠道身份」取 `pg_advisory_xact_lock` 后再查再写；归并任务幂等，同一封消息重跑结果不变。
- 第一期工单生命周期（PRD 6.1 第一阶段迁移表，D-22、D-23），写成纯函数迁移表，状态只能经迁移表改变：

  | 当前状态 | 事件 | 目标状态 |
  |---|---|---|
  | （无） | 新来信，无可追加或重开的工单 | 待回复 |
  | 已关闭（30 天内） | 同一订单来信 | 待回复（重开） |
  | 待回复 | 识别到我方回复，且没有其他未回复的应回复来信 | 等客户 |
  | 待回复 | 全部未回复来信都被「标记无需回复」 | 已解决 |
  | 待回复 | 14 天无新来信 | 已关闭（原因「未识别到回复」，未回复来信 SLA 计未达标） |
  | 等客户、已解决 | 新的应回复来信 | 待回复 |
  | 等客户、已解决 | 7 天无来信 | 已关闭 |

  工单负责人第一期为空。每次迁移写一条状态变更记录（时间、事件、触发方）。
- 「应回复来信」= 来源为客户、且未被标记无需回复的来信；生产厂与其他供应商来信归入工单但不是应回复来信。
- 回复识别（R-SL-08）：把「我方发信已同步」按 Gmail 线程、`In-Reply-To`、`References` 归到工单；带 `Auto-Submitted` 或自动回复标记的不算回复；一封回复结束它之前该工单内所有未回复应回复来信的计时。
- SLA：每封应回复来信保存到达时间（`internalDate`）、SLA 截止（亚马逊 24 自然小时；Shopify 与邮件按内部目标 24 小时，店铺可覆盖）、首次回复时间、SLA 结果（达标 / 未达标 / 未到期）。关闭时仍未回复的来信计未达标。第一期不产生 SLA 提醒。
- 两个例外写操作（均记审计）：
  - **指定店铺**：仅客服主管，对未归属店铺队列中的来信；指定后按 R-ST-02 重新识别站点、关联订单并归并，SLA 保留原到达时间；5 秒内可撤销。
  - **标记无需回复 / 撤销**：坐席与客服主管，按单封来信；该来信不计入 SLA；工单状态按迁移表变化；5 秒内可撤销，撤销后恢复计时与状态。
- 时限扫描（每分钟，接收显式当前时间）：14 天待回复关闭、7 天等客户 / 已解决关闭。
- 查询接口：P04 列表（店铺、渠道、站点、状态、最近来信时间筛选，排序）；P05 详情（时间线、SLA 结果、状态流转、订单卡）；未归属店铺队列（仅客服主管）。

**`aftersales`（台账）**
- 售后单（AfterSales）与第二期同一张表；创建路径枚举含「手工登记」「历史导入」；第一期简化状态 进行中 / 已完成 / 已取消（第二期映射到正式状态）。
- 权限：客服主管与售后负责人可新建登记；只有售后负责人可补登与修改状态；登记人或售后负责人可设「已完成」（不要求字段齐全，记完成时间）；取消原因必填，已产生费用保留；坐席只读（不含财务字段）。
- 必填矩阵（✓ 适用必填，— 不适用、不计入完整率；费用项没有发生时填 0 视为已填）：

  | 字段 | 调整安装方式 | 寄配件 | 退款或部分补偿 |
  |---|---|---|---|
  | 店铺、订单号、客户 | ✓ | ✓ | ✓ |
  | 处理方式、责任类型 | ✓ | ✓ | ✓ |
  | 配件 × 数量、发货方（易仓 / 生产厂） | — | ✓ | — |
  | 承运方式、寄出日期、快递单号 | — | ✓ | — |
  | 退款或补偿金额（原币） | — | — | ✓ |
  | 产品成本、运费、额外赔偿、其他（原币） | ✓ | ✓ | ✓ |
  | 承担比例（三组） | ✓ | ✓ | ✓ |
  | 索赔对象与状态 | 责任为物流问题时 ✓ | 同左 | 同左 |
  | 报备、结算批次、比例协商、工厂承担金额 | — | — | — |

  「适用字段是否齐全」是一个纯函数（输入售后单，输出缺失字段列表），前后端共用；列表中「待回填」标黄只对已完成的单生效，进行中的单缺字段显示「—」。
- 登记完整率 = 当月（按完成时间，`Asia/Shanghai`）已完成售后单中适用字段齐全的数量 ÷ 当月已完成售后单数量；历史导入不计入。
- 承担比例三组（产品成本 / 快递物流 / 其他费用），每组一个 FSH : 工厂，0–100 整数、两侧互补；责任类型的默认比例来自种子数据（R-AS-02）。工厂承担金额 = 产品成本 × 产品成本组工厂比例 + 运费 × 快递物流组工厂比例 +（额外赔偿 + 其他）× 其他费用组工厂比例；FSH 承担 = 费用合计 − 工厂承担。
- 汇率：手工登记取费用发生日的汇率；售后负责人可改汇率并记审计。
- 种子数据：责任类型默认三组比例、SKU 与生产厂对应、已登记生产厂邮箱（维护页面随第二期 P23、P24）。
- 导出：exceljs 服务端同步生成，按当前筛选与字段权限，记审计。

**`report`**
- 直查业务表（SQL 视图 + 索引，只读角色）；以后变慢再改物化视图。时效目标 T+0、15 分钟内。
- 指标定义：
  - **工单量** = 期间内新建或重开的客户工单数（不含生产厂、其他供应商来源），按新建或重开时间归期。
  - **首响中位数** = 期间内到达的客户来信到首次回复的时长中位数（只含已回复）。
  - **SLA 达标率（亚马逊）** = 期间内到达的亚马逊应回复来信中，达标数 ÷（已回复数 + 已超期未回复数）；未到期且未回复的不计。
  - **售后成本** = 全部非待确认售后单的已发生费用（产品成本 + 运费 + 额外赔偿 + 其他，美元冻结值），已取消的单按已产生部分计入，按费用发生日归期。P13 合计与 P17 售后成本共用同一个 SQL 视图（AC-RP-01）。
- 日界 `Asia/Shanghai`；站点用工单的站点字段。
- 图表只有「每日工单量」（按渠道堆叠）与「售后成本按责任类型」（本月，不随时间筛选）。
- 「更新于」= 该视图所用数据源中最旧的一次同步成功时间。
- 下钻：生成带筛选条件的 P04 / P13 地址；按目标页权限决定是否可下钻。
- 财务字段过滤同 `org`；店铺范围过滤必须在每个视图查询上显式施加（报表绕过了仓储层的编译期保护，评审与测试单独检查）。
- 导出同台账口径，记审计。

**`integration`**
- 所有外部调用经同一个 HTTP 客户端工厂（undici `EnvHttpProxyAgent`，gRPC 与钉钉 Stream 读同一组代理环境变量并遵守 `NO_PROXY`）；按「系统 × 接口」限流；每次外部调用写一条调用记录（系统、动作、店铺、耗时、状态码、请求与响应摘要），供排错与 P18 连接状态使用。
- 每个客户端（Gmail、钉钉、SP-API 订单与 SQS、Shopify 订单、汇率）都配 Fake，能模拟成功、失败、超时、游标过期与断线恢复；按店铺配置选择真实现或 Fake。统一动作接口（ADR 0009）第一期不用，不实现。

### 历史导入与切换

- 顺序：订单回补 → 选定 T0，T0 前启动 `watch` → 近 90 天邮件按 `internalDate` 升序单线程回放 → T0 后开启实时处理。
- 回放复用实时的同一条流程，只把「当前时间」注入为邮件时间；归并、关闭、重开按当时时间判断；提醒与通知在回放模式下关闭。
- 售后登记表：一次性命令行导入，不用模型；字段映射表拿到真实表格后定；缺失字段标「历史导入」；原表无原币时直接按美元导入并标注；按原登记日期取汇率。

## Testing Decisions

### 什么是好测试

- 只测外部行为：给定输入（来信、订单、时间、用户操作），断言接口输出、报表数字、状态与审计记录；不断言内部函数调用、表结构细节或任务排队方式。
- 测试用 PRD 的业务语言命名，并在名称或注释里标注规则 / 验收编号（如 R-TK-01、AC-TK-03）。
- 时间一律经可注入时钟控制，不依赖真实时间、不 sleep。
- 优先用示例数据夹具（原型 `data.py` 转成的 JSON）作为种子，与 Playwright、Fake 回放共用，这样 AC-RP-01 等「按原型数据验收」的条目能直接复现（例如台账合计与报表售后成本都为 $188.79）。

### 测试接缝（已与用户确认）

1. **主接缝（唯一的集成接缝）**：后端 HTTP 接口，在测试进程内直接调用 Hono 应用 + 真实 PostgreSQL 18 + 全部外部客户端用 Fake + 可注入时钟 + 测试里同步把 worker 任务跑到空闲。典型写法：往 Fake Gmail / Fake 订单源里放数据 → 推进时钟 → 跑完任务 → 以某个角色身份调接口，断言工单、SLA、台账、报表视图与审计。绝大多数行为（归并、生命周期、回复识别、SLA、店铺范围、财务字段过滤、完整率、售后成本一致性、汇率回退、历史回放、成员停用）都在这一层验证。
2. **辅助接缝一：纯函数单元测试**（`contracts`、`calendar` 与各模块的纯函数）：工单迁移表全部迁移与非法迁移、工作日历、订单号抽取、来源规则匹配、站点判定、必填矩阵与「适用字段是否齐全」、承担金额计算、汇率交叉计算。ADR 0008 要求迁移表单元测试全覆盖。
3. **辅助接缝二：Playwright 端到端**：在开发测试环境（全部 Fake + 开发登录 + 示例数据夹具）上跑第一期 AC 子集，合并后自动运行。

不为模块内部服务单独设接缝；不做像素级截图比对，视觉对照原型人工验收。

### 需要覆盖的场景

- **越权**：每个列表 / 详情 / 报表 / 导出接口都要有「未授权店铺不可见」「无财务权限角色看不到成本与比例」的测试；报表视图的店铺范围过滤单独测。
- **并发**：同一订单两封来信并发归并只产生一张工单；同一 Gmail 消息重复投递只入库一次。
- **Fake 故障注入**：Gmail 游标过期后的区间补拉与「最近同步成功时间」不前移；连续 3 次失败进入连接异常并产生通知；汇率主源失败走备用、再失败取最近可用日。
- **幂等**：归并任务对同一封消息重跑结果不变；历史回放重跑不产生重复工单。
