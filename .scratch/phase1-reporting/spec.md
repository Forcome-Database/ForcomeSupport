## Problem Statement

FSH 的客服与售后现在没有一个统一、可信的数据面：

- 管理层要看工单量、首次回复时长、亚马逊 SLA 达标率与售后成本，只能从海帆、积加、各平台后台人工导出再拼表，口径不一、费时、总是滞后。
- 售后单散落在各人手里的登记表里，字段不齐、币种混杂（USD、CAD、MXN），当月到底花了多少钱、谁承担多少说不清，也无法按责任类型拆解。
- 4 个店铺邮箱（2 个亚马逊买家消息、2 个 Shopify 客服）里的来信没有按店铺、订单归并成工单，没人能回答「这张订单客户来过几次信、我们回了没有、回得够不够快」。
- 成员与权限没有统一来源，店铺之间的数据可见范围、成本等财务字段的可见范围都靠人记。

第一期要先把「数据」这一层建起来：让来信、订单、回复、售后成本自动进系统，报表替代人工导出，台账成为售后单唯一的登记处。回复仍由海帆和人工在原渠道发出，本系统第一期不发信、不调模型、不接积加。

## Solution

交付一套内网可用的生产系统（第一期），包含：

- **登录与组织**：成员与部门从钉钉通讯录同步，钉钉扫码登录（G11、G12）；6 个固定角色、店铺数据范围、财务字段可见性由后端强制；按角色进入默认首页、只显示第一阶段导航（PRD 4.1 第一阶段表）；站内通知铃铛面板（G10）；P27 审计日志（所有角色从头像菜单进入，按 10.2 过滤）。
- **收取与归并**：同步 4 个邮箱的收件与「已发送」，去重（R-TK-07）并识别店铺、站点、渠道（亚马逊 / Shopify / 邮件，R-TK-08）、来源（客户 / 平台通知 / 生产厂 / 其他供应商 / 营销），抽取订单号并在本地订单镜像中校验，按 R-TK-01/02 归并成工单；识别不出店铺的来信进入「未归属店铺」来信队列，由客服主管指定店铺，或在管理员登记新店铺后自动归位。
- **订单镜像**：亚马逊经 SP-API（非受限角色）、Shopify 经 Admin API 准实时同步到本地，上线前回补 90 天，夜间对账近 7 天，镜像缺失时按订单号补拉。
- **工单（只读 + 两个写操作）**：P04、P05 第一阶段版（I16–I18）按第一阶段生命周期（PRD 6.1 第一阶段迁移表）自动推进；写操作只有客服主管「指定店铺」与坐席、客服主管对单封来信「标记无需回复」。
- **首次回复与 SLA**：把「已发送」里的我方回信归到工单，按 R-SL-08 计算每封应回复来信的首次回复与 SLA 结果。
- **登记台账 P13**（第一阶段版，S13–S15）：售后单统一登记（新建登记、编辑登记、补登、设为已完成、取消、改派负责人），按 R-AS-08 必填矩阵计算当月登记完整率，多币种按欧洲央行汇率折算并冻结美元金额，导出 Excel。
- **报表 P17**（第一阶段版，K19）：工单量、首响中位数、SLA 达标率（亚马逊）三个指标，「每日工单量」「售后成本按责任类型」两张图（后者卡头总额即售后成本）；按店铺、站点筛选；按与指标同口径的条件下钻到 P04、P13；导出。
- **设置**：P18 渠道与店铺第一阶段版（K20：连接状态、店铺表与抽屉）、P20 团队与权限（成员、角色、店铺范围、停用与改派）。
- **历史导入与上线切换**：近 90 天邮件按邮件时间回放、售后登记表一次性导入、选定 T0 切换到实时。
- **运维落地**：WAL 归档与每日备份、恢复演练、worker 自检与宿主机存活检查、开发测试与生产两套环境、真实环境验收矩阵。

外部资质（SP-API、Shopify `read_all_orders`、钉钉应用、Google 全域委派等）到位之前，全部功能用 Fake 开发与验收，到位后逐个店铺切换。

验收：报表替代人工导出；登记完整率口径可计算，上线后第一个完整自然月达到 ≥ 98%（PRD 3.2）。

## User Stories

### 登录、组织与权限

1. 作为 FSH 成员，我想用钉钉扫码登录，这样不用再记一套账号密码。
2. 作为 FSH 成员，我想登录后直接进入我这个角色的默认首页（坐席与客服主管 P04、售后负责人 P13、知识库负责人与管理员 P17），这样一进来就是我最常用的页面。
3. 作为 FSH 成员，我想只看到第一期存在、且我有权限的导航入口（PRD 4.1 第一阶段表），顶栏不出现店铺切换与全局搜索，这样不会点进空页面或无权限页面。
4. 作为 FSH 成员，我想从链接直接访问无权页面时看到明确的「无权限」状态（G2，按钮「返回首页」），这样知道不是系统坏了。
5. 作为 FSH 成员，我想 7 天不操作才需要重新登录；被拒绝登录时看到原因（未分配角色、已停用、会话过期，G12）。
6. 作为管理员，我想成员与部门自动从钉钉通讯录同步（Stream 实时 + 每小时全量对账），这样组织变化不需要在两边维护。
7. 作为管理员，我想在 P20 从钉钉通讯录添加成员并必填角色与店铺数据范围，这样新成员登录后立即只看到授权店铺的数据（AC-ST-06）；第一期不能分配「生产厂对接人」，只有该角色的成员登录显示无权限（AC-P1-21）。
8. 作为管理员，我想给一个成员分配多个角色、权限取并集，这样兼岗的同事不需要两个账号。
9. 作为管理员，我想在 P20「角色权限」页签看到只读的权限矩阵（K17，只列第一期已上线的能力），这样能向业务方解释谁能做什么。
10. 作为管理员，我想手工停用成员时，弹窗列出他负责的进行中售后单，要求我选择接手的售后负责人后再停用（AC-ST-02、K10），这样不会有售后单无人负责；没有可接手的售后负责人时不能停用并写明原因。
11. 作为管理员，我想钉钉离职的成员被自动停用、会话立即失效，负责的进行中售后单进入客服主管的改派队列，客服主管收到站内通知（AC-ST-05），这样离职交接不会漏单。
12. 作为管理员，我想钉钉同步失败时保留上次同步的成员与部门、登录不受影响，P18 钉钉卡显示同步延迟或连接异常，只有我收到站内提醒，不出全站横幅（E-32、6.9、AC-P1-22）。
13. 作为客服主管或售后负责人，我想在所有页面、导出、下钻与审计输出里都能看到成本、承担比例、结算相关金额，这样我能管住钱。
14. 作为坐席、知识库负责人或管理员，我不应看到成本、承担比例与结算金额（包括报表聚合、导出与下钻），这样财务数据只在授权范围内流转。
15. 作为任意成员，我想只看到授权店铺的工单、售后单、台账与报表数据（R-ST-06），访问其他店铺的数据时看到无权限并被记入审计（E-24）。
16. 作为任意成员，我想在顶栏切换舒适 / 紧凑两档密度，偏好保存在服务端，刷新或重新登录后保持（AC-ST-04）。
16a. 作为任意成员，我想在顶栏铃铛看到未读通知数，点开面板查看、点一条跳到对象并标为已读、一键全部已读（G10）。
16b. 作为任意成员，我想从顶栏头像菜单进入 P27 审计日志查看操作记录：客服主管与管理员看全部（店铺范围受限的客服主管只看授权店铺的对象记录与没有店铺属性的记录，PRD 10.2），其他人只看自己的；没有财务权限的角色看到成本、比例、结算金额的前后值为「已隐藏」（10.2、K18、AC-P1-20）。

### 渠道与店铺

17. 作为管理员，我想在 P18 看到亚马逊 SP-API（订单同步、SQS 状态 正常 / 积压 N 条 / 拉取失败、回补进度）、Shopify（订单同步、回补窗口）、Gmail（4 个邮箱，收件与「已发送」）、钉钉四张连接卡，每张卡显示最近同步时间与连接状态（已连接 / 同步延迟 / 连接异常 / 未连接）；状态按店铺计算，卡片显示最差的状态并列出异常的邮箱或店铺，店铺表「状态」列显示该店铺各连接的状态（6.9、K20）。
18. 作为管理员，我想积加与易仓卡显示为灰色虚线「第二阶段接入」（没有同步时间与测试连接）、不显示 17TRACK 卡，卡片文案只写第一期的能力，这样不会误以为它们已接通。
19. 作为管理员，我想对每个已接入的渠道点「测试连接」，这样外部资质开通后能马上验证。
20. 作为管理员，我想在右侧抽屉新增、编辑店铺（店铺名、平台、站点多选、默认站点、进线邮箱、平台标识；第一期不显示签名与覆盖项），并在字段下方看到店铺名重复、平台标识为空、邮箱格式错误的报错（K8、AC-ST-01）。
21. 作为工程师，我想在开发测试环境里为每个店铺选择真实接口还是模拟数据（抽屉字段只在非生产环境显示，卡头标「模拟数据」），这样外部接口开通后能逐个店铺切换。
22. 作为管理员与客服主管，我想某个渠道（钉钉除外）连续 3 次失败时全站顶部出现红色横幅（G4，不可关闭，恢复后自动消失），并收到站内通知与钉钉工作通知（E-01、E-02），这样能尽快处理。
23. 作为管理员，我想在 Gmail 断开时看到恢复指引（检查全域委派与邮箱状态，K7），恢复后系统自动补拉，这样不丢来信。
24. 作为管理员，我想新增店铺后，未归属队列中收件地址与新店铺进线邮箱匹配的来信自动归位成工单，客服主管收到站内通知（E-13、AC-P1-16）。

### 收取与归并

25. 作为客服主管，我想 4 个店铺邮箱的新来信在几分钟内出现在系统里（Pub/Sub pull 常驻 + 每 5 分钟 `history.list` 兜底），这样工单列表反映的是当下。
26. 作为客服主管，我想同一封邮件无论被推送几次都只进系统一次（E-15）；同一封邮件同时发到多个店铺邮箱时只按最早收到（同步入库）的一封建工单，其余在消息上记「同时发送到」（R-TK-07），这样工单量不会虚高。
27. 作为客服主管，我想系统按收件邮箱识别店铺，并按唯一口径识别站点（亚马逊按买家消息中转域 marketplace.amazon.com / .ca / .com.mx——从平台域 amazon.com / .ca / .com.mx 直发的是平台通知，归档、不建工单；Shopify 按订单收件国家，无订单时取店铺默认站点），这样报表与筛选按站点统计是可信的（AC-TK-14）。
27a. 作为客服主管，我想系统识别渠道：亚马逊中转来信为「亚马逊」，Shopify 联系表单通知为「Shopify」（客户身份取表单里的回复邮箱），其余直接写到店铺客服邮箱的为「邮件」（R-TK-08）。
28. 作为客服主管，我想平台通知与营销邮件按发件人规则自动归档、不建工单，这样工单量只反映真实客户诉求。
29. 作为客服主管，我想生产厂与其他供应商的来信照常建工单并标注来源，但不计入工单量与 SLA，这样既不漏信又不污染客服指标。
30. 作为客服主管，我想系统从来信里抽取订单号（亚马逊 `3-7-7` 格式；Shopify 按订单名在该店铺内匹配）并在该店铺的订单镜像中校验，镜像没有时按需补拉，这样工单能关联到真实订单。
31. 作为客服主管，我想来信抽不到订单号时，系统按客户邮箱在该店铺反查订单，唯一命中才关联，命中多笔或为零按客户维度归并，这样不会错关联。
32. 作为客服主管，我想带订单号的来信按 R-TK-01 归并：同店铺同订单有未关闭工单则追加（AC-TK-01），有 30 天内关闭的则重开为「待回复」（AC-TK-03），否则新建（AC-TK-04）。
33. 作为客服主管，我想无订单号的来信按 R-TK-02 归并：同一客户渠道身份有未关闭的无订单工单则追加，否则新建；同一客户两笔不同订单生成两张工单（AC-TK-02）。

### 范围与架构

- 第一期涉及模块：`org`、`channel`、`order`、`ticket`、`aftersales`（仅台账）、`report`、`core`、`integration`（Gmail、钉钉、SP-API 订单、Shopify 订单、汇率）。**不接**积加、17TRACK、模型，**不开**公网入口，不建工厂工作台。
- 模块化单体（ADR 0005）：pnpm workspace，前端一个应用、后端一个应用（`api`、`worker`、`migrate` 三个入口）、共享包 `contracts`（zod 模式、状态枚举中英对照、能力矩阵）、`calendar`（工作日历纯函数）、`config`。模块只经各自入口导出的服务互调，不跨模块读写表；唯一例外是 `report` 用只读数据库角色直读各模块的表。边界在 CI 用 lint 强制。
- 跨模块联动在业务事务内发领域事件（插入 pg-boss 任务，任务表即发件箱，ADR 0008），由 worker 处理。第一期的关键事件：`channel`「来信已接收」→ `ticket` 归并；`channel`「我方发信已同步」→ `ticket` 回复识别；`org`「成员已停用」→ `aftersales` 改派队列。
- 后端 Node 24 + Hono（`@hono/zod-openapi`，接口直接用 `contracts` 的 zod 模式声明）+ Drizzle + PostgreSQL 18，一个模块一个 schema（ADR 0006）。前端 Vite + React 19 单页应用，TanStack Router（筛选条件经 zod 校验放在 URL）/ Query / Table，react-hook-form，shadcn/ui + Tailwind v4，shadcn Charts（ADR 0007）。界面只做中文、只做浅色，两档密度。
- 部署：Docker Compose（`caddy`、`api`、`worker`、`migrate`、自建 `postgres` 镜像内置 WAL-G），无 Redis、无对象存储。所有外部调用主动连出：境外经固定代理，境内（钉钉）经 `NO_PROXY` 直连（ADR 0003）。**第一期就需要内网 HTTPS**（内网子域名 + DNS-01 证书），会话 Cookie 为 `Secure`。服务器与公司域名到位前（2026-10-04 用户口径），先在本机用 Docker 部署开发测试环境，caddy 用内部 CA（`tls internal`）签发证书、员工浏览器安装导出的根证书，到位后切 DNS-01（ADR 0003 修订、`docs/部署说明.md`）。
- 部署流水线：GitHub + Actions 云端跑类型检查、lint（含边界）、单元测试、集成测试（真实 PG 18 + Fake），至少 1 名人工评审；内网自托管运行器按两类任务部署（开发测试 / 生产，生产需打标签 + 人工批准）（ADR 0013）。仓库暂不上 GitHub（2026-10-04 用户口径）：开发测试环境由本机部署脚本 `pnpm deploy:staging` 部署（构建镜像 → 先跑 `migrate` → 灌示例数据 → 起 `forcome-staging` Compose 项目 → 用根证书核对 HTTPS → Playwright 冒烟并输出报告）；部署工作流 `deploy-staging.yml` 照写，上 GitHub 后由 main 上 CI 通过触发、在开发测试运行器上调用同一脚本（ADR 0013 修订）。

### 数据约定

- 主键 UUIDv7；业务编号另设一列，由 `core` 在事务内生成：工单 `T-日期-4 位当日序号`（日期取首封来信日期，回放同样适用），售后单 `S-创建日期-4 位全局递增序号`。
- 时间一律 `timestamptz`（UTC）；日界与工作日历按 `Asia/Shanghai`。
- 金额 `numeric(12,2)` + 币种；每条金额另存汇率、汇率日期、汇率来源、冻结的美元金额（四舍五入到分）。
- 主表带 `version` 列做乐观锁，冲突时接口返回 409，前端按 G7「乐观锁冲突」提示（保留输入，「查看最新」或二次确认后「覆盖保存」）；不做软删除，作废与取消用状态表示。
- 审计：服务层在写事务内记录操作人、角色、来源 IP、完整前后值；系统操作记为「系统」；登录、登出、导出也记；只读查询不记，越权访问（E-24）除外。
- 实时推送：数据变化时 `NOTIFY`，api 监听后经 SSE 推「某对象变了」，前端让对应缓存失效。

**`channel`**
- 店铺（Store）与进线邮箱配置（P18、K8）：店铺名唯一（不分大小写）、平台标识必填、邮箱格式校验；站点多选、默认站点、进线邮箱可填多个（含别名，不分大小写、不能与其他店铺重复）；第一期不提供签名与覆盖项；「真实 / Fake」适配器选择只在非生产环境可设（非生产环境新建默认 Fake，生产环境提交 Fake 被拒）。新增店铺或为现有店铺增加进线邮箱后，对未归属队列中收件地址匹配的来信重新识别并归并（E-13、R-ST-02、AC-P1-16）：保存时在同一事务里发出「店铺已变更」事件（`channel.store_changed`，载荷带这次新登记的进线邮箱），15 号待办据此归位。P18 店铺表列出全部店铺（店铺配置是管理功能，不按管理员自己的数据范围过滤，ADR 0010 修订）。
- Gmail 客户端：服务账号 + 全域委派，4 个邮箱；Pub/Sub pull 常驻 + 每 5 分钟 `history.list` 兜底；「已发送」也同步；每天续订 `watch`（不按标签过滤）；游标过期按 `internalDate` 区间全量补拉，补拉完成前「最近同步成功时间」不前移；水位只在持久化成功后推进。常驻连接用 advisory lock 选主。
- 去重（R-TK-07）：消息表对「邮箱 + Gmail 消息 ID」唯一约束，冲突即视为重复（E-15）；另按 RFC `Message-ID` 跨邮箱判重：已在其他店铺邮箱入库的同一封邮件只记「同时发送到」，不再识别店铺与归并——以最早同步入库的一封为准，已归并后才收到的副本即使到达时间更早，也不改工单的店铺（PRD v2.14 R-TK-07，10-05 用户确认）。
- 渠道识别（R-TK-08）：亚马逊店铺邮箱的亚马逊中转来信为「亚马逊」；Shopify 店铺邮箱收到的 Shopify 联系表单通知为「Shopify」，客户渠道身份取表单里的回复邮箱；其余为「邮件」。落地（待办 10）：亚马逊中转来信 = 发件域是买家消息中转域 `marketplace.amazon.com` / `.ca` / `.com.mx`，客户渠道身份是中转地址；联系表单通知 = 发件地址 `mailer@shopify.com` 且能找到填表客户的邮箱——先取 `Reply-To`（Shopify 自己的 `no-reply@shopify.com`、`mailer@shopify.com` 不算，只留电话的客户 Reply-To 就是 `no-reply@shopify.com`），再取正文的 `Email:` 栏，姓名取 Reply-To 的显示名或正文的 `Name:` 栏；找不到客户邮箱的 `mailer@shopify.com` 来信按 Shopify 系统邮件归档、不建工单，但照样入库可查（协调者 2026-10-05 决定：联系表单的邮箱默认必填，没有邮箱的多为系统邮件，也无法回复）。识别结果（渠道、站点、来源、客户渠道身份）在 `channel` 入库时写进 `channel.message`，`ticket` 按客户渠道身份建客户与归并。
- 来源识别：可配置的发件人规则表（亚马逊通知发件地址、Shopify 系统邮件、已登记生产厂邮箱、`List-Unsubscribe` 等头），判定 客户 / 平台通知 / 生产厂 / 其他供应商 / 营销。平台通知与营销归档、不建工单；生产厂与其他供应商照常进入归并并带来源标记。规则表与已登记生产厂邮箱随种子数据提供。落地（待办 10，种子清单与优先级由协调者 2026-10-05 决定）：
  - 规则表 `channel.sender_rule`，三种匹配方式：精确地址；发件域，一律**精确等于**、不含子域（`amazon.com` 不命中 `marketplace.amazon.com`）；头字段（有这个头即命中，或头的值去空白、不分大小写后等于给定值）。直邮适用全部规则，地址与发件域规则看发件地址；经平台中转的来信（亚马逊买家消息、Shopify 联系表单）是客户经平台写来的，只适用按客户渠道身份登记的「生产厂」「其他供应商」地址与发件域规则，不套用「平台通知」「营销」规则，头字段也不看（头是平台加的）——例如客户用 `@amazon.com`、`@shopify.com` 邮箱填联系表单照常建工单（协调者 2026-10-05 决定）。归档的来信（平台通知、营销）照样完整存进 `channel.message`，可经 `channel` 的读服务 `listReceivedMail` 查到。
  - 优先级：精确地址 > 发件域 > 头；同一层级命中几条时，生产厂 > 其他供应商 > 平台通知 > 营销（规则冲突时宁可多一张工单，不悄悄归档）。没有命中为客户。
  - 种子（迁移 0009，所有环境相同）：平台通知——发件域 `amazon.com`、`amazon.ca`、`amazon.com.mx`（亚马逊平台通知）、`shopify.com`（Shopify 系统邮件）；营销——带 `List-Unsubscribe` 头，或 `Precedence` 为 `bulk` / `list` / `junk`。已登记生产厂邮箱：示例数据的 FQD、FZJ 三个邮箱只在非生产环境随示例数据灌入（加载步骤 `channel.sender_rules`）；生产环境的真实生产厂邮箱与其他供应商名单由业务提供后用迁移补（待办 32 跟踪）；其他供应商第一期不预置。
  - 工单的来源取首封来信的来源，追加不改；消息的来源存在 `channel.message.source`，经工单详情接口给出。
- 店铺与站点识别：按收件邮箱识别店铺；站点唯一口径——亚马逊按发件域，Shopify 按订单收件国家，无订单时取店铺默认站点。识别不出店铺 → 未归属店铺来信队列（尚未归并成工单；SLA 平台按发件域判断）。落地（待办 10）：亚马逊店铺按发件域（From）定站点——`amazon.com` / `marketplace.amazon.com` → US、`amazon.ca` / `marketplace.amazon.ca` → CA、`amazon.com.mx` / `marketplace.amazon.com.mx` → MX，精确等于，发件域不是这几个的取店铺默认站点；Shopify 店铺一律取店铺默认站点（按订单收件国家随 14），即使发件域是亚马逊的域。按发件域得出的站点不要求在店铺登记的站点里（R-ST-02 按发件域为唯一口径）。这几个域与联系表单的代发地址在 `contracts` 的 `amazonDomains`、`SHOPIFY_CONTACT_FORM_SENDER`，识别与 Fake 回放共用。
- 订单号抽取：亚马逊正则 `\d{3}-\d{7}-\d{7}`；Shopify 按订单名（如 `#1063`）在该店铺内匹配；抽取结果交 `order` 校验。
- 完成后发「来信已接收」「我方发信已同步」事件。
- 渠道连接状态（6.9）：已连接 / 同步延迟（Gmail、订单 10 分钟，钉钉 2 小时）/ 连接异常（连续 3 次失败）/ 未连接；按店铺计算，渠道卡取最差状态并列出异常的邮箱或店铺。连接异常触发全站横幅（不可关闭，恢复后自动消失）与通知；钉钉例外：只更新卡片状态并给管理员站内提醒，不出横幅（E-32）。SQS 状态：正常 / 积压 N 条 / 拉取失败。

**`order`**
- 本地订单镜像：平台订单、商品行、发货与单号快照；以平台订单号为关联键，Shopify 另存订单名（店铺内唯一）。
- 亚马逊：SP-API Orders v2026-01-01，只用非受限角色；`ORDER_CHANGE` → SQS 长轮询 + 每 3–5 分钟 `lastUpdatedAfter` 增量兜底；每个「卖家 × 接口」共享令牌桶，增量优先、回补与对账让路，配额以响应头为准。
- Shopify：Admin GraphQL，每 1–2 分钟 `updated_at` 增量；令牌 24 小时过期、每 20 小时提前刷新（动态凭据用主密钥 AES-GCM 加密存库）。
- 回补 90 天（Shopify 61–90 天依赖 `read_all_orders`，否则 60 天并由报表注明）；每天夜间对账近 7 天。
- 对外接口：「在某店铺内按订单号 / 订单名查订单（镜像没有则按需补拉）」「在某店铺内按客户邮箱反查订单」「各数据源最近同步成功时间」。
- 说明：亚马逊非受限角色读不到买家邮箱，邮箱反查实际只对 Shopify 生效。

**`ticket`**
- 客户（Customer，最小形态）：渠道身份（邮箱或亚马逊中转地址）；第一期不做身份合并。
- 归并（R-TK-01、R-TK-02）：在事务内按「店铺 + 订单号」或「店铺 + 客户渠道身份」取 `pg_advisory_xact_lock` 后再查再写；归并任务幂等，同一封消息重跑结果不变。
- 第一期工单生命周期：照 PRD 6.1「第一阶段工单生命周期」迁移表（9 行，含「已解决 → 待回复」撤销迁移与三种关闭原因）写成纯函数迁移表，状态只能经迁移表改变；ADR 0008 要求迁移表单元测试全覆盖。状态迁移看「未回复来信」（不论来源），SLA 与报表看「应回复来信」（来源为客户），口径见 PRD 1.4。工单负责人第一期为空。每次迁移写一条状态变更记录（时间、事件、触发方），工单另存关闭原因。
- 工单的「来源」取首封来信的来源；工单量只计由客户来信触发的新建与重开事件（按事件计，一张工单在期间内重开两次计两次），供 `report` 使用。
- 回复识别（R-SL-08）：把「我方发信已同步」按 `In-Reply-To`、`References`、Gmail 线程的顺序归到工单；带 `Auto-Submitted` 或自动回复标记的不算回复，消息照常入库并标「自动回复」；一封回复结束它之前该工单内所有未回复应回复来信的计时。乱序：回复找不到对应来信时任务延后重试（最长 24 小时），来信归并后再归属；晚到的来信若早于工单内已归属的回复，按 `internalDate` 判定为已被该回复结束计时。
- SLA：每封应回复来信保存到达时间（`internalDate`）、SLA 截止（亚马逊 24 自然小时；Shopify 与邮件内部目标 24 小时，第一期固定）、首次回复时间、SLA 结果（达标 / 未达标 / 未到期 / 无需回复）。关闭时仍未回复的来信计未达标。第一期不产生 SLA 提醒。
- 两个例外写操作（均记审计）：
  - **指定店铺**：仅客服主管；未归属来信对客服主管可见、不受店铺数据范围限制，可选店铺只限其授权店铺。前端先移出行并显示 5 秒撤销浮层，窗口结束后才提交；提交后按 R-ST-02 重新识别站点、关联订单并归并，SLA 保留原到达时间（PRD 6.1 说明、AC-P1-15）。
  - **标记无需回复 / 撤销**：坐席与客服主管，只对未关闭工单中的未回复来信；立即执行，该来信不计入 SLA，工单按迁移表变化，生成事件行；5 秒内撤销走迁移表的撤销迁移，恢复计时与状态（AC-P1-01）。
- 时限扫描（每分钟，接收显式当前时间）：14 天待回复关闭、7 天等客户 / 已解决关闭，都从工单内最近一封来信的到达时间起算（PRD 6.1）。
- 查询接口：P04 列表（状态、渠道、店铺、站点、来源、最近来信时间筛选；只供下钻用的 URL 参数：客户来信触发的新建或重开日期（事件级，不用工单来源）、来信到达日期、来信状态（已回复 / SLA 结果：达标、未达标、未到期）、渠道（PRD P17「指标口径」）；按 PRD P04「第一阶段」的默认排序）；P05 详情（时间线、SLA 结果、状态流转、订单卡、自动关闭预计）；未归属店铺来信队列（仅客服主管）。

**`aftersales`（台账）**
- 售后单（AfterSales）与第二期同一张表（字段见 PRD 11.1）；创建路径枚举含「手工登记」「历史导入」；第一期简化状态 进行中 / 已完成 / 已取消，已完成与已取消为终态（PRD 6.5「第一阶段台账状态」），第二期原样保留。
- 权限（PRD 10.1）：客服主管与售后负责人可新建登记；进行中的单由登记人或负责人编辑（客服主管只能编辑自己登记的）；登记人或负责人可设「已完成」（不要求字段齐全，记完成时间，5 秒内可撤销）；只有售后负责人可补登已完成的单与修改汇率；客服主管或售后负责人可取消（二次确认、原因必填，确认保留的已产生费用）与改派负责人；坐席只读（不含财务字段）。
- 负责人：必填，只能是有该店铺数据范围的售后负责人；登记人是售后负责人时默认本人，该店铺只有一位售后负责人时默认此人，否则必选（D-24）。
- 必填矩阵、登记完整率、售后成本、承担金额的口径全部照 PRD R-AS-08（矩阵含站点、费用发生日、负责人、责任理由、生产厂；「退款或部分补偿」的款项记在额外赔偿且须大于 0；没有单独的退款金额字段）。「适用字段是否齐全」是一个纯函数（输入售后单，输出缺失字段列表），放 `contracts`，前后端共用；列表中「待回填」标黄与「缺 N 项」只对已完成的单生效，进行中的单缺字段显示「—」。
- 登记完整率按 R-AS-08 计算（当月按完成时间、`Asia/Shanghai`；历史导入不计）；只随店铺数据范围与店铺筛选变化，不随日期筛选；当月没有已完成的单时完成数为 0（界面写「—」与「0 / 0」，PRD v2.18）。落地（待办 21）：缺失字段与完整率都在应用层按 `contracts` 的 `missingFields` 判断（台账每行由后端算好 `missing`，只对已完成的单），台账接口 `GET /api/aftersales/ledger` 带当月完整率 `completion { month, completed, complete }`，查询条件 `store`、`from` / `to`（费用发生日）与 `missing=1`（点完整率筛出：当月缺字段的已完成单，与完整率同口径，只随店铺、不叠日期条件）；筛选行界面随 22。状态只经 `aftersales/lifecycle.ts` 的迁移表改变（ADR 0008 修订）：`POST …/complete`、`…/undo-complete`（界面 5 秒，服务端多留 5 秒网络余量）、`…/cancel`（原因必填，`keptFees` 为确认保留的已登记费用项，存 `<费用项>_kept`）；编辑登记与补登 `PATCH /api/aftersales/{单号}`（进行中整张校验；已完成只补登空着的或按 R-AS-08 算缺的项；可同时改汇率）；详情 `GET /api/aftersales/{单号}`；谁能做按 `contracts` 的 `aftersalesActions`（ADR 0010 修订）。都带版本号（G7）并记审计（`aftersales.update` / `backfill` / `change_rate` / `complete` / `undo_complete` / `cancel`）。
- 承担比例三组（产品成本 / 快递物流 / 其他费用），每组一个 FSH : 工厂，0–100 整数、两侧互补；责任类型的默认比例来自种子数据（R-AS-02）。工厂承担逐行四舍五入到分，FSH 承担 = 该行费用合计 − 工厂承担，合计行为各行之和；已取消的单在行内按确认保留的部分显示各费用项与承担额，原登记额在悬停中显示（R-AS-08，D-27）。落地（待办 22）：`contracts` 的 `costShares`（big.js，ROUND_HALF_UP），台账每行、合计行、导出与登记抽屉的「FSH 合计 · 工厂合计」都按它；比例的写法 `ratioWords`（三组相同「三组均 FSH 0 / 工厂 100」，不同时逐组列出，悬停第一行「按费用项」）。
- 汇率：手工登记取费用发生日的汇率；售后负责人可改汇率并记审计。落地（待办 20）：费用项的整组列（原币、币种、冻结美元值、汇率、汇率日期、来源，`core` 的 `feeColumns` / `feeChecks`）；保存时按费用发生日取汇率（`aftersales/fees.ts` 的 `convertFees`），费用发生日及之前都没有汇率时在该金额上报「费用发生日及之前没有汇率，暂时不能折算美元」、不保存；改汇率 `PUT /api/aftersales/{售后单号}/rates`（能力 `aftersales.backfill`，只有售后负责人；冻结美元值重算，汇率日期为费用发生日、来源「手工修改」，记审计 `aftersales.change_rate`），界面入口在编辑登记抽屉（待办 21）。
- 种子数据：责任类型默认三组比例、SKU 与生产厂对应（用于按配件预填生产厂）、已登记生产厂邮箱（维护页面随第二期 P23、P24）。落地（待办 19）：默认比例在 `aftersales.responsibility_ratio`、两家生产厂在 `factory.factory`，都由迁移 0012 写入所有环境；SKU 与生产厂对应在 `factory.part`（生产厂与 SKU 归属按第二期规格归 `factory`），真实归属表要等业务提供（待办 32），在那之前只在非生产环境随示例数据灌入（加载步骤 `factory.parts`）——生产环境上线前必须补上，否则寄配件选不了配件、也不能按配件预填生产厂。
- 导出：exceljs 服务端同步生成后直接下载（不留存文件），按当前筛选与字段权限，记审计。落地（待办 22）：`GET /api/aftersales/ledger/export`，条件同列表（`ledgerQuerySchema`），与列表共用 `listLedger`；文件为台账 17 列（含默认隐藏的 4 列，不随列设置变化），坐席不含七个金额列（先 `stripFinanceFields` 再按权限取列），金额为美元数值，有财务权限时另有「承担比例」「原币与汇率」「取消时未保留」三列与末行合计，另有「缺失字段」一列；文件名 `登记台账_起止.xlsx`（筛出缺字段时 `登记台账_缺字段的已完成单_YYYY-MM.xlsx`）放 `Content-Disposition` 的 `filename*`，行数放 `X-Export-Rows`；审计 `ledger.export`（对象类型「导出」，后值写文件名、筛选条件、行数、是否含财务字段）。台账查询条件补上处理方式、责任、状态、负责人（`method`、`responsibility`、`status`、`owner`），费用发生日没给的一端取本月（按服务端时钟，响应 `range` 写这次按的起止、`defaultRange` 写默认的本月供界面判断是否默认，S13 补充小样）；每行另带生产厂、配件 × 数量、负责人姓名（隐藏列）与财务字段 `cost`（计入售后成本的四项、费用合计、两方承担）、`keptFees`（已取消单保留的项），响应另带合计行 `totals`（财务字段）；筛选行的负责人选项 `GET /api/aftersales/ledger/options`。

**`report`**
- 直查业务表（SQL 视图 + 索引，只读角色）；以后变慢再改物化视图。时效目标 T+0、15 分钟内。
- 指标定义：
  - **工单量** = 期间内由客户来信触发的新建与重开事件数（生产厂、其他供应商来信触发的不计），按新建或重开时间归期。
  - **首响中位数** = 期间内到达的客户来信到首次回复的时长中位数（只含已回复）。
  - **SLA 达标率（亚马逊）** = 期间内到达的亚马逊应回复来信中，达标数 ÷（已回复数 + 已超期未回复数）；未到期且未回复的不计。
  - 未归属店铺的来信计入「全部店铺」口径的首响与 SLA（平台按发件域判断），选定店铺时不计，归位后按所归店铺计；工单量只计已成工单的事件（PRD P17、D-27）。
  - **售后成本** = 全部非待确认售后单的已登记费用（产品成本 + 运费 + 额外赔偿 + 其他，美元冻结值），已取消的单只计取消时确认保留的部分，按费用发生日归期（R-AS-08；第一期没有待确认状态，即全部售后单，视图仍写 `status <> 待确认` 以便第二期复用）。P13 合计行「费用合计」与 P17「售后成本按责任类型」卡头总额共用同一个 SQL 视图（AC-RP-01）。落地（待办 22）：视图 `aftersales.aftersales_cost`（`aftersales/schema.ts`，迁移 0016），每张计入的单一行：`aftersales_id`、`store_id`、`fee_date`、`responsibility`、四项计入的美元值（已取消的单没保留的项为 0，没登记的为空）与 `total_usd`；P13 连同它取每行并在应用层求和，报表（25）经 `aftersales/schema.ts` 引用、在只读角色下按责任类型求和，查询都要显式施加店铺范围（视图的 `store_id`）。
  - **对比**：近 7 天对比之前 7 天，本月对比上月同期，自定义对比之前等长区间。
- 日界 `Asia/Shanghai`；站点用工单的站点字段。
- 指标卡只有工单量、首响中位数、SLA 达标率（亚马逊）三张；图表只有「每日工单量」（按渠道堆叠：亚马逊 / Shopify 与邮件）与「售后成本按责任类型」（条形图，本月，不随时间筛选，卡头总额即售后成本）。
- 「更新于」= Gmail、亚马逊订单、Shopify 订单中最旧的一次同步成功时间（台账为手工登记，不参与）；另返回两条注：只统计经店铺邮箱发出的回复；Shopify 回补窗口不足 90 天时的说明。
- 下钻：生成与指标同口径的 P04 / P13 地址（PRD P17「指标口径」）。工单量按「客户来信触发的新建或重开日期」下钻，P04 列出对应工单，芯片写事件数（与指标一致）与工单数；首响中位数按「客户来信到达日期 + 已回复」、SLA 达标率按「亚马逊来信到达日期 + 未达标」下钻，按封计，P04 列出含这些来信的工单；图例带渠道。P04 的下钻参数相应为：触发日期、来信到达日期、来信 SLA 结果、渠道；按目标页权限决定是否可下钻。
- 财务字段过滤同 `org`；店铺范围过滤必须在每个视图查询上显式施加（报表绕过了仓储层的编译期保护，评审与测试单独检查）。
- 导出同台账口径（同步生成直接下载），记审计。

**`integration`**
- 所有外部调用经同一个 HTTP 客户端工厂（undici `EnvHttpProxyAgent`，gRPC 与钉钉 Stream 读同一组代理环境变量并遵守 `NO_PROXY`）；按「系统 × 接口」限流；每次外部调用写一条调用记录（系统、动作、店铺、耗时、状态码、请求与响应摘要），供排错与 P18 连接状态使用。
- 每个客户端（Gmail、钉钉、SP-API 订单与 SQS、Shopify 订单、汇率）都配 Fake，能模拟成功、失败、超时、游标过期与断线恢复；店铺级客户端（Gmail、订单）按店铺配置选择真实现或 Fake，全局客户端（钉钉、汇率）按环境变量选择；生产环境不允许 Fake。统一动作接口（ADR 0009）第一期不用，不实现。

### 历史导入与切换

- 顺序：订单回补 → 选定 T0，T0 前启动 `watch` → 近 90 天邮件按 `internalDate` 升序单线程回放 → T0 后开启实时处理。

## Testing Decisions

### 什么是好测试

- 只测外部行为：给定输入（来信、订单、时间、用户操作），断言接口输出、报表数字、状态与审计记录；不断言内部函数调用、表结构细节或任务排队方式。
- 测试用 PRD 的业务语言命名，并在名称或注释里标注规则 / 验收编号（如 R-TK-01、AC-TK-03）。
- 时间一律经可注入时钟控制，不依赖真实时间、不 sleep。
- 优先用示例数据夹具（原型 `data.py` 转成的 JSON）作为种子，与 Playwright、Fake 回放共用，这样 AC-RP-01 等「按原型数据验收」的条目能直接复现（例如台账合计与报表售后成本都为 $188.79）。夹具转换规则：工单状态取 `P1_STATUS` 并补 `P1_EXTRA_TICKETS`（`p1_tickets()`）；台账取 `p1_ledger_rows()`（丢弃待确认的 S-20260911-0022，补 `LEDGER_EXTRA` 的订单号、费用发生日、完成时间等）；Fake 汇率固定为演示汇率 1 USD = 18.00 MXN、1.36 CAD；P05 第一期时间线取 `P1_OLIVER`。AC-P1-14（每日工单量 73）需要专门的验收夹具：示例数据夹具里 09-10 只有 7 张工单，报表数字是示例值。

### 测试接缝（已与用户确认）

1. **主接缝（唯一的集成接缝）**：后端 HTTP 接口，在测试进程内直接调用 Hono 应用 + 真实 PostgreSQL 18 + 全部外部客户端用 Fake + 可注入时钟 + 测试里同步把 worker 任务跑到空闲。典型写法：往 Fake Gmail / Fake 订单源里放数据 → 推进时钟 → 跑完任务 → 以某个角色身份调接口，断言工单、SLA、台账、报表视图与审计。绝大多数行为（归并、生命周期、回复识别、SLA、店铺范围、财务字段过滤、完整率、售后成本一致性、汇率回退、历史回放、成员停用）都在这一层验证。
2. **辅助接缝一：纯函数单元测试**（`contracts`、`calendar` 与各模块的纯函数）：工单迁移表全部迁移与非法迁移、工作日历、订单号抽取、来源规则匹配、站点判定、必填矩阵与「适用字段是否齐全」、承担金额计算、汇率交叉计算。ADR 0008 要求迁移表单元测试全覆盖。
3. **辅助接缝二：Playwright 端到端**：在开发测试环境（全部 Fake + 开发登录 + 示例数据夹具）上跑第一期 AC 子集，合并后自动运行（暂不上 GitHub 期间由部署脚本在每次部署后运行；开发测试环境长期运行、数据会累积，用例要能重复执行）。

不为模块内部服务单独设接缝；不做像素级截图比对，视觉对照原型人工验收。

### 需要覆盖的场景

- **越权**：每个列表 / 详情 / 报表 / 导出接口都要有「未授权店铺不可见」「无财务权限角色看不到成本与比例」的测试；报表视图的店铺范围过滤单独测。
- **并发**：同一订单两封来信并发归并只产生一张工单；同一 Gmail 消息重复投递只入库一次；同一封邮件发到两个店铺邮箱只建一张工单（R-TK-07）；台账两人同时编辑同一张单时后保存者收到冲突（G7）。
- **乱序**：「已发送」的回信先于它所回复的来信入库时，来信归并后回复照样归属、计时正确。
- **撤销**：「标记无需回复」撤销走迁移表的撤销迁移；「指定店铺」在撤销窗口内撤销不产生工单。
- **Fake 故障注入**：Gmail 游标过期后的区间补拉与「最近同步成功时间」不前移；连续 3 次失败进入连接异常并产生通知（钉钉只提醒管理员、不出横幅）；汇率主源失败走备用、再失败取此前最近一个有汇率的日期。
- **幂等**：归并任务对同一封消息重跑结果不变；历史回放重跑不产生重复工单。
