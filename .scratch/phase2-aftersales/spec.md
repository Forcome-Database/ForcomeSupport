# 第二期：售后流程（实现契约）

Status: needs-triage
Type: spec

依据：PRD v2.11（D-21–D-25；各页「第二阶段」小节；状态 I19–I21、A1–A11、S1–S15、F1–F9、K6–K8、K10、K17、K22–K24；验收 13.7）；`docs/技术方案.md` v1.2 第 3、4、6–10 节与 11.2；ADR 0002、0003、0007–0010、0012、0013；第一期规格 `.scratch/phase1-reporting/spec.md`。业务术语以 PRD 1.4 为准，规则、页面、状态、验收编号沿用 PRD。

**本规格写到实现契约层**（决策 31）：定死第二期的范围、与第一期的衔接、各模块的接口与数据口径、先决条件。实现待办等第一期做到后半段（第 9 片之后）再拆，拆之前对照第一期的实现结果与真实环境验收矩阵修正本规格，并做一次 PRD、原型、规格、待办四方对照。口径以 PRD 为准，两处不一致时以 PRD 为准并回写本规格。

## Problem Statement

第一期之后，客服与售后仍然在系统外完成大部分工作：

- 回复仍由海帆和人工在各渠道发出，本系统只能事后从「已发送」反推；坐席无法在一处看到客户、订单、售后与审批的全貌，也没有编辑锁，可能重复回复。
- 补发、退款、改地址、取消要分别登录积加、卖家后台、Shopify 后台操作，审批靠口头或聊天，报备与动作分开审两次；执行结果要人工回填。
- 售后单在台账里只是「登记」：责任确认、生产厂询价与寄件、比例协商、月度结算都在系统外通过邮件和表格往来，工厂承担金额对不上账。
- 管理层只能看到第一期的数据面，看不到「每张售后单卡在哪、在等谁」。

第二期把这些流程搬进系统：回复从本系统发出，动作经审批后由接口执行，售后单按流程推进，生产厂在工厂工作台协同，结算按月出批次。AI 只承担翻译、摘要、抽取与售后评估，不起草回复、不做分诊（第三期）。

## Solution

交付第二期，包含（PRD 3.2「二」）：

- **收件箱与工单**（F-TK）：收件箱第二阶段版（I19，人工处理；需处理 = 有未回复来信的未关闭工单，与审批中可重叠；优先级默认普通、重复联系升级、客服主管可调）；回复发送（亚马逊买家消息与邮件，经 Gmail）；回复类型与重复联系计数；编辑锁；合并；手工新建工单；人工重开；SLA 实时计时与提醒；标签；原文与译文、对话摘要、客户历史摘要；客户档案与身份合并（P06）；人工提交审批（I20）；转售后确认（I21）。
- **审批**（F-AP）：审批单（动作 + 报备 + 绑定回复）、审批人与备用审批人、4 小时时限与剩 1 小时提醒、处理锁、执行与重试、绑定回复发送前校验（暂停待确认）、驳回与撤回、人工操作清单（P15、A1–A11）。
- **售后流程**（F-AS）：售后单两条创建路径、确认责任与处理方式（✦ AI 预选）、易仓有货 / 易仓无货 / 退款或部分补偿三条执行线、比例协商、内部结算批次（P07–P12、P14、S1–S12）；台账由流程自动写入（P13 完整版）。
- **工厂工作台**（F-FT）：两家生产厂成员、按 SKU 派发、四类任务、结构化表单、留言、钉钉提醒与催办、手机端（P21、F1–F9）；唯一公网入口。
- **集成**（F-CH-04 第二阶段部分、F-AP-02）：统一动作接口 9 个动作；积加（补发、库存、出库单、单号与运费、亚马逊收件人）、SP-API Feeds（退款、取消）、Shopify Admin API 写动作、Gmail 发信、17TRACK 轨迹；动作映射 P22；人工操作清单兜底。
- **模型接入层**：Vercel AI SDK 经 NewAPI；用途 `translate`、`summarize`、`extract`、`assess`；P25 模型；调用记录表；评测脚本骨架（ADR 0012）。
- **设置与运维**：P22 动作映射、P23 售后规则、P24 工厂账号、SLA / 标签库 / 模板（K22–K24）、店铺签名与覆盖项、P20 备用审批人与成员语言、P25 模型、P26 系统状态；钉钉内免登。
- **报表**：在第一期基础上增加标签筛选与「工厂承担与结算进度」卡（P17 第二阶段）。

验收：PRD 3.2「二」（售后单人工操作 ≤ 2 次；处理时长缩短 50%；亚马逊 SLA 达标 ≥ 99%）与 13.7。

## 与第一期的衔接

| 衔接点 | 第一期 | 第二期上线时 | 依据 |
|---|---|---|---|
| 工单状态 | 待回复 / 等客户 / 已解决 / 已关闭 | 最近 14 天内的待回复 → 转人工（原因「人工处理」）；更早的按第一期迁移表关闭；其余不变。迁移表换成 PRD 6.1 完整表，第二阶段不出现分诊中、待审草稿、待审批 | PRD 6.1、AC-P2-05 |
| 新来信入口 | 新建或重开为待回复 | 新建或重开进入转人工（人工处理） | D-25 ① |
| 工单负责人 | 为空 | 上线时全部为空，进入「未分配」；之后按 PRD 6.1「第二阶段」：坐席认领或回复即成为负责人，客服主管可改派 | 6.1、P04 |
| 回复识别 | 只从「已发送」反推 | 本系统发出的回复直接记为回复；「已发送」同步保留，系统外发出的回复同样结束 SLA 计时并按「坐席发送回复」迁移，消息标「系统外回复」 | R-SL-08、6.1「第二阶段」 |
| 售后单 | 手工登记，进行中 / 已完成 / 已取消 | 状态原样保留；进行中的手工登记单当前环节「手工登记 · 待补登」，仍用台账处理，不进入流程 | D-25 ⑤、AC-P2-06 |
| 创建路径 | 手工登记、历史导入 | 新增系统自动（第三期）、手工新建、路径 B；第二期起不再提供「新建登记」 | 11.1、P13 |
| 能力矩阵 | 第一期能力已上线 | 按 PRD 10.1 打开第二期能力的阶段标记，K17 随之显示；生产厂对接人可分配 | 第一期规格「第二期衔接」 |
| 来源规则表 | 平台通知、营销归档；生产厂、其他供应商建工单 | 原样保留；生产厂来信另提示改用工厂工作台（R-FT-06、E-27） | 7.3 |
| 订单镜像 | 平台直读 | 原样；亚马逊订单另经积加按需补充收件人（订购一个月内） | ADR 0011、6.1 |
| 店铺配置 | 签名与覆盖项不显示 | 覆盖项上线（签名、政策口径、模板、链接白名单、SLA 内部目标） | R-ST-04 |
| 外壳 | 第一阶段导航、无店铺切换与搜索 | PRD 4.1 第二阶段导航（不含知识库），顶栏店铺切换、全局搜索与导航角标上线 | 4.1 |
| 公网入口 | 不开 | 开通（工厂工作台、钉钉免登路径） | ADR 0003 |
| 站内通知 | 第一期 5 类 | 加入 PRD 11.4 全部第二阶段行 | 11.4 |

切换步骤：发版（迁移只向前）→ 运行一次性映射任务（工单状态、能力阶段标记）→ 开放公网入口 → 管理员在 P24 为两家生产厂分配对接人 → 逐个店铺把动作适配器从 Fake 切到真实（P22）→ 停用台账「新建登记」。每一步可单独回滚到上一步。

## Implementation Decisions

### 范围与架构

- 新增模块 `approval`、`factory`；`ticket` 全功能；`aftersales` 全流程；`integration` 增加统一动作接口、积加 / SP-API Feeds / Shopify 写 / 17TRACK 适配器与模型接入层；`report` 增加结算相关视图。模块边界与事件规则同第一期（ADR 0005）。
- 前端新增工厂工作台独立入口 `factory.html`（ADR 0007），与主应用会话 Cookie 隔离；工作台响应式、以手机为主（F9）。
- 部署：公网子域名 + DNS-01 证书；caddy 对公网只放行 `factory.html` 静态资源、`/api/factory/*` 与钉钉免登接口，并限频（ADR 0003）。

### 各模块实现契约

**`ticket`（全功能）**
- 状态机：PRD 6.1 完整迁移表写成纯函数（与第一期同一机制），第二阶段由配置关闭「分诊中、待审草稿、待审批」三个入口：新来信与重开直接进入转人工并记原因「人工处理」。第三期打开分诊时只改配置与迁移入口，不改表。
- 回复发送：经统一动作「回复客户」（Gmail，亚马逊发往中转地址），发信前生成并保存自己的 `Message-ID`，结果不明时按 `rfc822msgid:` 在「已发送」中查询确认再决定是否重试（技术方案 6.2）；失败按 E-04、I5 重试。发信记回复类型（R-TK-03，默认结论性回复），重复联系在客户来信时按「我方最近一封回复是否结论性回复」计数；次数为 1 升优先级，次数为 2 的转人工拦截随第三期风险信号。
- 编辑锁（R-TK-06）：数据库租约行（持锁人、加锁时间、最后一次用户操作时间），前端 30 秒心跳只证明在线，服务端按用户操作时间判断 5 分钟无操作释放；客服主管可强制接手（技术方案第 4 节）。
- 合并（R-TK-04、I11）、手工新建（AC-TK-16）、人工重开（已解决或关闭 30 天内，回到转人工）、关闭（原因必填，5 秒撤销）、标签（≤ 5，来自标签库）。
- SLA：在第一期字段上增加实时剩余与提醒：剩 2 小时置顶与红色胶囊、超时通知客服主管（E-21、I9）；R-SL-05 提示阈值 = 审批剩余时限 + 动作预计执行时长（Feeds 8 小时、积加补发 4 个工作小时）；SLA 保底进展回复（R-SL-06）默认关闭。
- 人工提交审批（I20）：工单服务收集面板输入后调用 `approval` 的「发起审批单」，同一事务内由 `aftersales` 创建路径 B 售后单（按 R-AS-02 预填责任，改判记理由，R-AS-03）；工单保持转人工（D-11）。第三期 AI 草稿带出的审批项走同一入口。
- 转售后确认（I21）：调用 `aftersales` 创建待确认售后单（路径 A，没有发起人），附故障描述、所选来信附件与已做排查；工单经迁移表转等内部；通知售后负责人（11.4）。
- 客户档案（P06）：渠道身份列表、合并与拆分（人工确认、记审计，R-ST-07）、累计消费、✦ 历史摘要（`summarize`）。
- 译文与摘要：来信入库后异步调用 `translate`（非中文来信）与 `summarize`（对话摘要、客户历史摘要），结果带「生成时间 · 依据」（R-AI-01）；模型不可用时界面显示「暂无译文」并可重试，不阻塞处理。

**`approval`（新增）**
- 审批单状态机：PRD 6.3（待审批、执行中、已执行、执行失败、已驳回、已撤回；「已超时」为标记；「暂停待确认」为已执行之后、绑定回复发出之前的子状态）与审批项状态（待审批 / 已批准 / 已驳回 / 已作废）；人工操作清单状态机 6.4。
- 审批人计算（R-AP-02）：含报备 → 客服主管；只含动作 → 客服主管或售后负责人；发起人不能自审；唯一有权审批的人是发起人时转备用审批人（P20 设置）。剩 1 小时同时提醒备用审批人，此后备用审批人可审批（R-AP-03）。
- 处理锁（R-AP-03、A10）：租约 10 分钟，规则同编辑锁；批准、驳回以持锁人为准。
- 执行（R-AP-04、R-AP-05）：批准后按审批项顺序调用统一动作，每项一个幂等键；结果 `pending` 的（Feeds、积加补单）由轮询任务回写；初次失败后最多重试 3 次（1、5、15 分钟），仍失败为执行失败，通知发起人，可重试或转人工操作清单。
- 绑定回复（R-AP-06）：全部动作成功后发送前校验「提交后是否有新来信或新风险信号」，有则进入暂停待确认，由发起人选择照常发送或放弃并改写（6.3、A11）。
- 驳回与撤回（R-AP-07）：三种来源分别处理（P08 确认时提交、路径 B、系统发起），撤回与驳回同等处理，5 秒撤销。
- 报备写入台账：报备金额（原币、汇率、美元）随提交写入售后单费用项，实际金额回传后按 R-FL-05 比较，超 10% 自动发起补充报备。

**`aftersales`（全流程）**
- 售后单状态机：PRD 6.5（待确认 / 进行中 / 已完成 / 已取消）+ 当前环节与等待方（环节与子状态取值见 6.5），进入当前环节时间用于「已等」；第一期手工登记单按 D-25 ⑤ 处理。
- 确认（P08、S1）：调用 `assess` 给出 ✦ 责任与处理方式建议（含看图），人工确认后生效；改判填理由（R-AS-03）；退回继续排查（AC-AS-25）。
- 执行线：易仓有货 → 统一动作「创建售后出库单」（积加补单 V2，`pending` 至「已推送易仓且未缺货」，超过 4 个工作小时生成人工操作清单；缺货或推单失败先生成「在积加取消原补单」清单，确认后切易仓无货，R-AS-04）；易仓无货 → `factory` 询价、报价、报备、寄件任务；退款或部分补偿 → 统一动作退款（亚马逊 Feeds、Shopify `refundCreate`）。客户改地址按 R-AS-05。终止售后单时确认保留的已产生费用（S6，同第一阶段 S15 ②）。
- 比例协商（6.6、R-AS-06）：轮次表，3 + 2 个工作日时限与催办，待升级后由售后负责人录入最终比例（S12 不可逆确认）；已入批次不能改（R-AS-07），批次后调整在下一批次冲销（E-26）。
- 内部结算（6.7）：每个生产厂每月至少一个批次，月末 cron 自动生成（月末自动批次以「生产厂 + 月份」为单例键，提前批次另编号），可提前生成，售后单按比例确认时间归月，批次记录冲销（E-26）；提前批次只收当时比例已确认的单；生成后推送对接人确认，双方确认为已结算；异议按 E-30。
- 第一阶段手工登记单：按 PRD 6.5「第一阶段手工登记的单在第二阶段」处理（承担比例以登记值为准，有工厂承担的进入上线当月的月末批次）。
- 台账：流程写入的金额与生产厂回填的报价、单号、实际运费直接写入（R-FT-03），报备还在审批中的金额按估算计入（R-AS-08）；P13 完整版（报备、协商、结算列，✦ 积加有单号预填与核对补登）；售后成本口径不变（R-AS-08）。

**`factory`（新增）**
- 生产厂、SKU 归属（P24，R-FT-07）、工厂任务状态机 6.8（询价 2、寄件 3、比例答复 3、结算确认 5 个工作日，截止按 R-CL-02）、自动催办与「卡住」（E-07）、留言线程（R-FT-04）。
- 隔离（R-FT-01、R-FT-02）：`/api/factory/*` 专用输出结构，生产厂 ID 只取自会话；寄件完成 30 天后隐藏收件人信息；越权记审计（F6、E-24）。
- 钉钉：新任务、催办、FSH 留言、报价被退回推送工作通知，点开在钉钉内免登进入对应任务（R-FT-05）。

**`integration`**
- 统一动作接口（ADR 0009）：9 个动作（查订单、查物流、查库存、回复客户、创建售后出库单、订单备注、退款、改地址（仅 Shopify）、取消），结果 `succeeded` / `pending` / `failed_retryable` / `failed_permanent` / `unknown`；「动作 × 平台 → 适配器」映射存库、P22 编辑；凭据只在 `integration` 内按店铺取用（R-ST-03）；能力缺口按步骤模板生成人工操作清单。
- 适配器：积加（补单 V2、配货单轮询、库存、运费、亚马逊收件人；仓库类接口每秒 2 次、补单与配货单列表每秒 1 次）；SP-API Feeds（订单调整 feed 退款、订单确认 feed 取消，处理报告每 5 分钟轮询；结果不明先查报告不重复提交）；Shopify Admin（`refundCreate` 带幂等键、改地址、取消、订单备注）；Gmail 发信；17TRACK（注册单号后每 4 小时一轮、工单打开时即时查询，每秒 3 次）。每个适配器配 Fake（成功、失败、超时、异步回执）。
- 模型接入层（ADR 0001、0012）：Vercel AI SDK；Claude 经 NewAPI 走原生 `/v1/messages`，GPT 走 Responses，其他兼容接口走 Chat Completions；按用途调用，第二期用途 `translate`、`summarize`、`extract`、`assess`，配置存库、P25 编辑；熔断按「用途 × 模型」统计并切备用；调用记录表（用途、模型、版本、上下文清单、用量、成本、耗时、校验结果、降级路径、完整请求与响应）；评测脚本骨架（vitest）。
- 调用记录同时供 P18 连接状态与 P26 系统状态使用。

**`org` 与设置**
- 生产厂对接人角色开始分配（P24 从钉钉添加，R-FT-08）；钉钉内免登（工作台与主应用，HTTPS）。

## Testing Decisions

沿用第一期的测试接缝与好测试标准（主接缝为进程内后端接口 + 真实 PostgreSQL + Fake + 可注入时钟）。第二期新增重点：

- 状态机：工单完整迁移表、审批单与审批项、人工操作清单、售后单、比例协商、工厂任务、结算批次，单元测试覆盖全部迁移与非法迁移（ADR 0008）。
- 动作执行：幂等（同一审批单重复提交只执行一次）、`pending` 回执、重试间隔、结果不明先查询、执行失败转人工操作清单；Feeds 与积加补单用 Fake 异步回执测试。
- 并发：编辑锁与处理锁的租约、强制接手、两人同时审批只执行一次（AC-AP-18）。
- 时限：审批 4 小时与剩 1 小时、生产厂任务截止与催办、人工操作清单 4 个工作小时、月末批次单例，全部用可注入时钟。
- 隔离：生产厂只见本厂任务与必要字段，寄件完成 30 天后隐藏收件信息；公网入口路径白名单（只能访问 factory 路径）。
- 验收：PRD 13.7 列出的条目（含 AC-P2-01–06），以及 Playwright 覆盖 SC-01、SC-04、SC-05、SC-06 四条关键路径。
