# 第二期：售后流程（实现契约）

Status: needs-triage
Type: spec

依据：PRD v2.38（D-21–D-29；各页「第二阶段」小节；状态 I1–I21、A1–A11、S1–S16、F1–F9、K3–K10、K17、K22–K24、G4、G10；验收 13.7）；`docs/技术方案.md` v1.2 第 3、4、6–10 节与 11.2；ADR 0001–0015（含各自的修订小节）；第一期规格 `.scratch/phase1-reporting/spec.md` 与第一期待办的 Comments；真实环境验收矩阵（第一期待办 29）。业务术语以 PRD 1.4 与 `CONTEXT.md` 为准，规则、页面、状态、验收编号沿用 PRD。

**本规格写到实现契约层**（决策 31）：定死第二期的范围、与第一期的衔接、各模块的接口与数据口径、外部接口的模拟方式、先决条件。口径以 PRD 为准，两处不一致时以 PRD 为准并回写本规格。

**补全记录（2026-10-24，开工前）**：本规格原写于 PRD v2.12、第一期开发之前。开工前做了三路对照：PRD v2.13–v2.37 的逐版变更、PRD 各页「第二阶段」小节与第 6 章状态机、第一期的实际实现与 ADR 修订（含 2026-10-24 真实 Shopify 店铺与 163 企业邮箱的联调）。由此补全约 40 处；其中七项业务口径经用户 2026-10-24 确认（均按建议），回写为 PRD v2.38 的 D-29。

## Problem Statement

第一期之后，客服与售后仍然在系统外完成大部分工作：

- 回复仍由海帆和人工在各渠道发出，本系统只能事后从「已发送」反推；坐席无法在一处看到客户、订单、售后与审批的全貌，也没有编辑锁，可能重复回复。
- 补发、退款、改地址、取消要分别登录积加、卖家后台、Shopify 后台操作，审批靠口头或聊天，报备与动作分开审两次；执行结果要人工回填。
- 售后单在台账里只是「登记」：责任确认、生产厂询价与寄件、比例协商、月度结算都在系统外通过邮件和表格往来，工厂承担金额对不上账。
- 管理层只能看到第一期的数据面，看不到「每张售后单卡在哪、在等谁」。

第二期把这些流程搬进系统：回复从本系统发出，动作经审批后由接口执行，售后单按流程推进，生产厂在工厂工作台协同，结算按月出批次。AI 只承担翻译、摘要、抽取与售后评估，不起草回复、不做分诊（第三期）。

## Solution

交付第二期，包含（PRD 3.2「二」）：

- **收件箱与工单**（F-TK）：收件箱第二阶段版（I19，人工处理；「需处理」= 有未回复来信、或关联售后单等待回复客户的未关闭工单（含转售后确认后转等内部但尚未回复的），与「审批中」可重叠；优先级默认普通、重复联系升级、客服主管可调）；回复发送（亚马逊买家消息与邮件，经店铺进线邮箱：Gmail 或 163 企业邮箱，D-28）；回复类型与重复联系计数；编辑锁；认领与改派（含批量）；手动转人工 / 转客服主管、标记解决、等外部；合并；手工新建工单；人工重开；关闭；SLA 实时计时与提醒；标签；原文与译文、对话摘要、客户历史摘要；客户档案与身份合并、拆分（P06）；人工提交审批（I20）；转售后确认（I21，✦ 抽取预填）；导出。
- **审批**（F-AP）：审批单（动作 + 报备 + 绑定回复）、审批人与备用审批人（受店铺数据范围限制，D-29 ②）、时限与剩 1 小时提醒（读 P23）、催办、处理锁、执行与重试、绑定回复发送前校验（暂停待确认）、驳回与撤回、人工操作清单与回填核对（P15、A1–A11）。
- **售后流程**（F-AS）：售后单的创建路径（转售后确认、P07 手工新建、路径 B；系统自动创建随第三期）、确认责任与处理方式（✦ `assess` 预选）、四条执行线（易仓有货、易仓无货、退款或部分补偿、调整安装方式）、索赔、比例协商（含重开）、内部结算批次（含异议）（P07–P12、P14、S1–S12）；台账由流程自动写入（P13 完整版）。
- **工厂工作台**（F-FT）：两家生产厂成员、按 SKU 派发、四类任务（含退回报价、无法供货）、结构化表单、留言、钉钉提醒与催办、手机端（P21、F1–F9）；唯一公网入口。
- **集成**（F-CH-04 第二阶段部分、F-AP-02）：统一动作接口 9 个动作；积加（补发、库存、出库单、单号与运费、亚马逊收件人、运费试算）、SP-API Feeds（退款、取消）、Shopify Admin API 写动作、邮件发信（Gmail API、163 企业邮箱 SMTP）、17TRACK 轨迹；动作映射 P22；人工操作清单兜底；每个外部接口都配 Fake（见「外部接口与 Fake」）。
- **模型接入层**：Vercel AI SDK 经 NewAPI；用途 `translate`、`summarize`、`extract`、`assess`；P25 模型；模型调用记录；熔断与备用；评测脚本骨架（ADR 0012）。
- **设置与运维**：P22 动作映射、P23 售后规则、P24 工厂账号、SLA / 标签库 / 模板（K22–K24）、店铺签名与覆盖项、P18 / P20 完整版（备用审批人、成员语言、停用时的工单与审批单）、P25 模型、P26 系统状态、P27 审批单对象；工作日历；钉钉内免登。
- **报表**：在第一期基础上增加标签筛选与「工厂承担与结算进度」卡（P17 第二阶段）。

验收：PRD 3.2「二」与 13.7。3.2 的三项指标：售后单人工操作次数 ≤ 2（第二阶段只计确认与报备审批两类人工确认环节，转售后确认与人工回复不计，验收时按售后单的确认与审批记录统计，不在 P17 显示，D-29 ①）；售后单处理时长（创建到单号回复客户）缩短 50%；亚马逊 SLA 达标率 ≥ 99%（P17 已有）。为此售后单记下确认、报备审批的人工操作与「单号回复客户」完成的时刻（见 `aftersales`「过程记录」）。

**切换步骤**（做成部署子命令，ADR 0013 的写法）：

1. 发版（迁移只向前；`CURRENT_PHASE = 2` 随发版生效，「新建登记」同时下线）。
2. 停 worker、写维护标记（同 `mail-replay` 的做法），执行一次性映射：待回复 → 转人工（经 `applyTransition`，不发通知）；第一期手工登记单写入「手工登记 · 待补登」与 6.5 的比例、结算边界；未关闭工单的来信附件回源补取（可在 worker 恢复后后台继续）。
3. 恢复 worker；开放公网入口。
4. 管理员在 P24 为两家生产厂分配对接人。
5. 外部接口按资质到位情况逐项接入真实实现（生产环境不接受 Fake，P18 v2.13）：资质未到位的动作在 P22 映射到「人工操作清单」，到位后改映射为接口。逐项放量靠 P22 映射，不靠数据来源开关。

第 1、2 步不可逆（迁移只向前，映射写状态变更）；第 3–5 步可分别撤回（关入口、改映射）。

## Implementation Decisions

### 范围与架构

- 补全模块：`approval`（已有空目录与空 schema）、`factory`（已有 `factory`、`part` 两张表）；`ticket` 全功能；`aftersales` 全流程；`channel` 增加发信、附件与 SMTP；`integration` 增加统一动作接口、各写动作适配器与 Fake、模型接入层；新增 `ai` 模块放用途调用（`translate`、`summarize`、`extract`、`assess`）与模型调用记录，接入层（模型客户端、配置、熔断）在 `integration`（技术方案 3.1）；`report` 增加结算相关视图。模块边界与事件规则同第一期（ADR 0005）。
- 前端新增工厂工作台独立入口 `factory.html`（ADR 0007），与主应用会话 Cookie 隔离；工作台响应式、以手机为主（F9）。
- 部署：公网子域名 + DNS-01 证书；caddy 对公网只放行 `factory.html` 静态资源、`/api/factory/*` 与钉钉免登接口，并限频（ADR 0003）。

### 外部接口与 Fake

每个外部接口做两层，业务代码只依赖接口（同第一期，`CONTEXT.md`「Fake」）：

- **Fake**：本机、测试与开发测试环境默认使用。按官方文档模拟真实行为——异步回执（Feeds 处理报告最长约 8 小时、积加补单的「已推送易仓且未缺货」）、限流（积加仓库类每秒 2 次、补单与配货单每秒 1 次；17TRACK 每秒 3 次；SP-API 按「卖家 × 接口」令牌桶）、错误码（余额不足、权限不够、超时、结果不明）、幂等（同一幂等键只执行一次）；测试可注入故障（成功、失败、超时、异步回执、结果不明）。开发测试环境里店铺的「数据来源」（P18，v2.13）同时决定该店铺第二期写动作用不用 Fake。
- **真实现**：照官方文档写，用替身服务器回放文档里的请求与响应测试（第一期 163 IMAP 的做法，`integration/imap-real.test.ts`）；资质到位后在开发测试环境对测试对象联调，结果记进真实环境验收矩阵。
- **依据的可靠程度**：SP-API、Shopify Admin API、Gmail API、17TRACK、NewAPI 文档完整；积加只有开放平台的接口文档，补单参数、「无需标发」、取消补发单等细节等积加答复（`.scratch/tech-plan/积加技术问题清单.md` 第 1–16 条）。积加 Fake 里文档没写明的行为标为假设（代码注释与本规格 Comments 各记一处），答复或沙箱到位后校正。
- **非生产环境的写操作守卫**（ADR 0013 修订 2026-10-24）：开发测试环境已经接了真实 Shopify 店铺与真实 163 企业邮箱。退款、取消、改地址、订单备注、创建售后出库单等写动作的真实现，发出前检查运行配置的写操作白名单（按店铺，可再细到订单），非生产环境默认只放行登记的测试店铺；不在白名单的以 `failed_permanent` 结束、记调用记录，不发请求。邮件发信沿用发信白名单（`mail-recipient-guard.ts`），Gmail 与 SMTP 的真实现发出前都调 `assertAllowed`。守卫放在离网络最近的一层。
- **测试对象**：Shopify 写动作在开发店铺（Shopify Partner 后台免费创建）上联调，不在营业中的店铺（如 Young Electric）上试；163 发信先对白名单内的自家地址实测。

### 各模块实现契约

**`ticket`（全功能）**

- 状态机：PRD 6.1 完整迁移表写成纯函数（与第一期同一机制，经 `applyTransition` 写状态变更），第二阶段由配置关闭「分诊中、待审草稿、待审批」三个入口，改道为转人工：新来信与重开（原因「人工处理」）、关联售后单需要回复客户（原因「售后待回复」，6.5「回复客户环节」）、P08 退回继续排查（原因「人工处理」）。第二阶段要实现的迁移（6.1 完整表与补充说明）：
  - 转人工下坐席发送回复（无审批项、没有挂未结束的审批单）→ 等客户 / 等内部 / 等外部（补充说明 5：有进行中的关联售后单且不在「回复客户」环节 → 等内部；发送时选「等外部」并写明在等谁 → 等外部；否则等客户）；挂着未结束的审批单时发回复只结束 SLA、不改状态（补充说明 1）。
  - 提交审批：转人工保持转人工；等客户、等内部、等外部、已解决 → 转人工，审批单挂在工单上（I20，D-27）；审批通过且执行成功、绑定回复发出 → 等客户或等内部；执行失败 → 保持转人工，工单标「执行失败」（AC-AP-12、E-05）；驳回或撤回 → 保持转人工。
  - 手动转人工 / 转客服主管（任一未关闭状态）；标记解决（转人工、等客户、等内部、等外部 → 已解决）；「识别为致谢」随第三期；标记无需回复及 5 秒撤销（同第一期，转人工、等内部 → 已解决；有进行中的关联售后单时为等内部，挂审批单时保持转人工）。
  - 转售后确认、以该工单为来源在 P07 手工新建售后单 → 等内部。
  - 已解决、等客户 7 天无来信 → 已关闭（R-TK-05）；等外部不自动关闭。
  - 合并 → 已合并；人工重开（已解决、已关闭 30 天内）→ 转人工；关闭（原因必填，5 秒撤销）。
  - 系统发起的审批单挂在售后单上，不改工单状态（补充说明 2）。
  - 工单量口径不变：只计客户来信触发的新建与重开（PRD 1.4）；人工重开与手工新建（AC-TK-16：手工新建为等客户、不计 SLA）不进报表视图 `customer_trigger_event`。
- 回复发送：经统一动作「回复客户」，由 `channel` 按进线邮箱的服务商发出（见 `channel`「回复发送」）。发信记回复类型（R-TK-03，默认结论性回复），重复联系在客户来信时按「我方最近一封回复是否结论性回复」计数；次数为 1 升优先级，次数为 2 升为紧急并提醒客服主管（11.4），转人工拦截随第三期风险信号；没有回复类型的我方回复（第一期识别到的、系统外发出的）不计为结论性回复。发送前只做回复检查的规则项（PRD 7.5「第二阶段」），回复框没有插入图片与链接按钮（R-CC）。发送失败按 E-04：1、5、15 分钟自动重试，回复保留，行内「发送失败」+ 倒计时（I5），用尽后通知发送人（11.4）；邮箱连接异常期间（6.9、E-02）回复进待发队列，恢复后按提交顺序发出。
- 编辑锁（R-TK-06）：数据库租约行（持锁人、加锁时间、最后一次用户操作时间），前端 30 秒心跳只证明在线，服务端按用户操作时间判断 5 分钟无操作释放；客服主管可强制接手（技术方案第 4 节）。
- 认领与改派：坐席认领或回复即成为负责人，客服主管改派；P04 批量条（改派、添加标签、合并、关闭）与导出（P04 第二阶段沿用完整版）。
- 合并（R-TK-04、I11）、手工新建（AC-TK-16，P06 也有「新建工单（预填该客户）」入口）、标签（≤ 5，来自标签库）、优先级（客服主管可调）。
- 关闭与 SLA：第二期有了人工关闭，已关闭工单收到的我方回信要按关闭时刻区分（第一期待办 16 的口径，`ticket/sla.ts` 注释）——关闭前已发出的回复照常结束 SLA，关闭后的回信不改已关闭工单的 SLA 结果；关闭时仍有未回复来信的计未达标（R-SL-07）。
- SLA：在第一期字段上增加实时剩余与提醒：剩 2 小时置顶与红色胶囊、超时通知客服主管与工单负责人（站内 + 钉钉工作通知，11.4，E-21、I9）；R-SL-05 提示阈值 = 审批剩余时限 + 动作预计执行时长（Feeds 8 小时、积加补发 4 个工作小时，按工作日历算）；SLA 保底进展回复（R-SL-06）依赖风险信号，随第三期。
- 人工提交审批（I20）：工单服务收集面板输入后调用 `approval` 的「发起审批单」，审批单含报备或寄件动作时，同一事务内由 `aftersales` 创建路径 B 售后单（按 R-AS-02 预填责任，改判记理由，R-AS-03）；寄件类动作的收件人取积加补充的亚马逊收件人，取不到时必填（E-34）；报备金额没有汇率时不能提交（E-20、R-FL-06）；面板里的库存经积加查询、快递费用取积加运费试算、产品成本取 SKU 成本表（见 `factory`「SKU 成本」）。
- 转售后确认（I21）：打开弹窗时调用 `extract` 从工单来信预填故障描述与涉及配件（✦，可改，D-29 ⑥；模型不可用时留空照常填写）；提交后调用 `aftersales` 创建待确认售后单（路径 A，没有发起人），附故障描述、所选来信附件、已做排查与涉及配件；工单经迁移表转等内部；通知售后负责人（11.4）。
- 客户档案（P06）：渠道身份列表、合并与拆分（人工确认，拆分二次确认，记审计，R-ST-07）、内部备注、累计消费（按订单镜像算；Shopify 应用没有 `read_all_orders` 时只含近 60 天，界面照 K19 的回补窗口写法注明）、✦ 历史摘要（`summarize`）、导出档案。
- 人工回复的译文与回译（R-LG-03、AC-AI-09）：坐席用中文写，发送前调用 `translate` 生成客户语言译文并回译成中文，坐席确认后发出；模型不可用时可改用客户语言直接写。
- 译文与摘要：来信入库后异步调用 `translate`（非中文来信）与 `summarize`（对话摘要、客户历史摘要），结果带「生成时间 · 依据」（R-AI-01）；模型不可用时界面显示「暂无译文」并可重试，不阻塞处理。
- P04、P05 对客户隐藏意图与情绪（第三期才有，第二阶段不显示）；P05 状态流转只含第二阶段出现的状态，导出记录 PDF。

**`channel`（发信、附件、SMTP）**

- **回复发送**（D-28、ADR 0015 修订 2026-10-24）：从工单的进线邮箱发出（亚马逊发往买家消息中转地址），按该邮箱的服务商分派：Gmail 经 Gmail API（`users.messages.send`，全域委派范围加 `gmail.send`）；163 企业邮箱经 SMTP（Nodemailer，SSL 465；登录名为邮箱地址、口令为同一个客户端授权码，网易境内服务直连、不经代理，ADR 0003）。
  - 发信前生成并保存自己的 `Message-ID`（域名取进线邮箱的域名），写 `In-Reply-To`（客户最近一封来信）、`References`（整条链）与 `Subject: Re: …`——网易网页版的回信只带 `References`（真实环境核对 2026-10-24），两个头都写才串得起来。
  - 结果不明时先在「已发送」中查询确认再决定是否重试（技术方案 6.2）：Gmail 按 `rfc822msgid:`；163 企业邮箱用 IMAP 在同步记录里记下的「已发送」文件夹（`imap_cursor.sentFolder`，网易为「已发送」）里 `SEARCH HEADER Message-ID <…>`。Gmail API 是否保留自定义 Message-ID、网易是否支持按头字段搜索，开通时实测（先决条件 4b）；不支持时改按发信记录的发送时刻与收件人在「已发送」里比对。
  - 网易是否把 SMTP 发出的信自动存进「已发送」，开通时实测：会存就靠第一期的「已发送」同步入库；不存时发信成功后用 IMAP `APPEND` 放进「已发送」，带 `\Seen` 与**发送时刻作为 `INTERNALDATE`**（R-SL-08 的回复时间取到达时间，不带会被改成补写时刻），写入后按 Message-ID 去重。`APPEND` 是 ADR 0015「只读」原则的唯一例外，另开一条可写连接、写完即关；失败不影响已发出的回复（记日志，下次同步前重试一次）。
  - 失败归类：按 E-04 一律 1、5、15 分钟重试；认证失败、客户端登录被关闭、IP 限制同时计入该邮箱的连接失败（6.9 的「登录」失败），连续 3 次即连接异常，期间回复进待发队列（E-02）；连接超时、4xx 只重试，不计连接失败。Gmail 发信的授权失败同样计入该邮箱的连接失败。
  - 发信白名单：Gmail 与 SMTP 的真实现发出前都调 `mailRecipientGuard.assertAllowed`（ADR 0013）。
  - 发信记录与同步的分工见「与第一期的衔接 · 回复识别」。
- **163 企业邮箱的 SMTP 配置**（K8）：进线邮箱表加 `smtp_host`、`smtp_port`；默认值按 IMAP 服务器推出（`imap.qiye.163.com` → `smtp.qiye.163.com`、`imaphz.qiye.163.com` → `smtphz.qiye.163.com`，端口 465），管理员可改；SMTP 服务器必填、端口 1–65535。「沿用已保存的授权码」（`contracts` 的 `reusesSavedAuthCode`）与表约束（`store_mailbox_imap_server_check`）扩到同时比较 SMTP 服务器与端口：任一改了都要重填授权码，防止把已保存的授权码发到别的主机。授权码的读取（`credential-vault.ts` 的 `readMailboxAuthCode`）开放给 SMTP 真实现，附加数据仍为「qiye163:地址」。行内「测试连接」第二期同时测 SMTP 登录（不发信），结果按 IMAP、SMTP 分别写；P18 的「校验」与测试结果写法回写 PRD。
- **附件**：来信入库时把附件存到附件卷（文件名、类型、大小、内容哈希；按哈希去重），`channel.message` 关联附件行；上线时对未关闭工单的来信按 `provider_message_id` 回源补取（163 在 UIDVALIDITY 变了之后取不到的记「附件不可用」）；附件卷纳入备份（ADR 0013 修订：第二期的附件卷挂到 `/backup-src`）。I21 选附件、P05 展示、`assess` 看图都读这里。

**`approval`（补全）**

- 审批单状态机：PRD 6.3（待审批、执行中、已执行、执行失败、已驳回、已撤回；「已超时」为标记；「暂停待确认」为已执行之后、绑定回复发出之前的子状态）与审批项状态（待审批 / 已批准 / 已驳回 / 已作废；作废见 R-AS-04 缺货切换）；人工操作清单状态机 6.4。已执行包括「人工操作清单回填完成视为成功」。
- 审批人计算（R-AP-02、D-29 ②）：含报备 → 客服主管；只含动作 → 客服主管或售后负责人；只取店铺数据范围包含该审批单店铺的成员；发起人不能自审；范围内除发起人外无人有权审批时转备用审批人（P20 设置，必须有审批权限，不受店铺范围限制）。剩 1 小时同时提醒备用审批人，此后备用审批人可审批（R-AP-03）。
- 时限与阈值读 P23（报备时限默认 4 小时、剩 1 小时提醒、超额补充报备阈值默认 10%）；修改只影响之后新建的审批单与售后单。
- 催办（P07 批量、P09、P14 入口）：向审批人发站内 + 钉钉工作通知，每张每小时最多 1 次（11.4）。
- 处理锁（R-AP-03、A10）：租约 10 分钟，规则同编辑锁；批准、驳回以持锁人为准。
- 执行（R-AP-04、R-AP-05）：批准后按审批项顺序调用统一动作，每项一个幂等键；结果 `pending` 的（Feeds、积加补单）由轮询任务回写；初次失败后最多重试 3 次（1、5、15 分钟），仍失败为执行失败，通知发起人，可重试或转人工操作清单；动作暂无接口（P22 映射为人工操作清单）时审批通过即生成清单。接口连接异常期间（E-01，连续 3 次失败）已批准的动作排队、不消耗重试次数，恢复后按顺序执行；R-AP-05 的重试只算接口连通时的失败。
- 绑定回复（R-AP-06）：全部动作成功后发送前校验「提交后是否有新来信」（第二阶段没有风险信号），有则进入暂停待确认，由发起人选择照常发送或放弃并改写（6.3、A11）；放弃并改写时改写的回复不再走审批，原来信与新来信的 SLA 都在改写回复发出时结束。待审批期间客户又来信时，审批卡显示非阻断提示「提交后客户又来信 N 封」（D-23 ⑦）。
- 驳回与撤回（R-AP-07）：三种来源分别处理（P08 确认时提交、路径 B、系统发起），撤回与驳回同等处理，5 秒撤销；驳回通知在 5 秒撤销期结束后才发；系统发起的审批单由关联售后单负责人撤回，通过、驳回、执行失败、超时的通知发给关联售后单负责人（11.4「发起人」在系统发起时取售后单负责人）；已驳回后可修改重新发起，路径 B 复用原售后单号。
- 人工操作清单回填（R-AP-08、E-18、AC-AP-09）：指派给发起人，4 个工作小时内回填；回填金额与审批金额不一致时不能直接提交，要填差异说明并由原审批人确认。
- 报备写入台账：报备金额（原币、汇率、美元，R-FL-06）随提交写入售后单费用项，实际金额回传后按 R-FL-05 比较，超过 P23 阈值自动发起补充报备。
- P15 页签：待我审批 / 我发起的 / 人工操作清单 / 已处理；执行日志。

**`aftersales`（全流程）**

- 售后单状态机：PRD 6.5（待确认 / 进行中 / 已完成 / 已取消）+ 当前环节与子状态（取值见 6.5，含 D-29 ④ 的「确认责任与处理方式 · 生产厂无法供货」）+ 等待方 + 进入当前环节时间（「已等」）；状态变更记录表。待确认的来源包括确认时提交的审批单、路径 B 的审批单被驳回或撤回后退回（路径 B 的单锁定给原发起人）；系统发起的报备被驳回时保持进行中，当前环节「报备审批 · 待重新提交」。
- **过程记录**：记下确认、报备审批的人工操作（操作人、时刻）与「单号回复客户」完成的时刻，供 3.2 两项指标在验收时统计（D-29 ①）。
- 确认（P08「第二阶段」、S1）：调用 `assess` 给出 ✦ 责任与处理方式建议（含看图），输入为转售后确认的故障描述、附件、已做排查、涉及配件与订单；人工确认后生效；改判填理由（R-AS-03）；暂存、取消售后单；退回继续排查后来源工单回到转人工、不生成草稿（AC-AS-25 的第二阶段期望）。P08 的产品成本取 SKU 成本表、快递费用取积加运费试算。
- 回复客户环节（PRD 6.5、D-27）：单号回传或确认为调整安装方式时，售后单当前环节转「单号回复客户」「发送指导」，等待方为来源工单负责人（未分配时为客服团队，通知发给客服主管，11.4），经 `ticket` 迁移把来源工单转人工（售后待回复）；来源工单发出正文含该快递单号的回复即完成「单号回复客户」、售后单转已完成（AC-P2-07）；发出任一我方回复即完成「发送指导」、转「等客户反馈」，客户确认解决或 7 天无来信转已完成，客户说未解决时售后负责人改为寄配件。
- 执行线：
  - 易仓有货 → 统一动作「创建售后出库单」（积加补单 V2，`pending` 至「已推送易仓且未缺货」，超过 4 个工作小时生成人工操作清单；缺货或推单失败先生成「在积加取消原补单」清单，确认后切易仓无货、原报备作废，R-AS-04、E-06）。
  - 易仓无货 → `factory` 询价、报价（可退回报价，E-29）、报备、寄件任务；生产厂无法供货时按 D-29 ④ 回到确认环节。
  - 退款或部分补偿 → 统一动作退款（亚马逊 Feeds、Shopify `refundCreate`）；付款成功、绑定回复发出即完成。
  - 调整安装方式 → 发送指导（见上）。
  - 改处理方式只在寄出前可用；客户改地址按 R-AS-05；终止流程时确认保留的已产生费用、撤回待审批的报备并取消生产厂任务（S6）。

4c. Gmail：全域委派加 `gmail.send` 范围；实测 Gmail API 发信是否保留自定义 Message-ID。
5. NewAPI 渠道与可用模型（Claude、GPT），以及嵌入与重排是否可用（第三期需要）。
6. 公网子域名与证书（DNS-01）；钉钉内免登配置（主应用与工作台）与 `DINGTALK_CORP_ID`；两家生产厂成员在钉钉的部门与人员。
7. SKU 与生产厂归属表、SKU 成本表（迁移写入，P24 维护）；责任比例与报备规则确认（P23）；标签库初始清单（Q-07）；进展回复模板（第 14 节）。
8. 海帆回信的 Q-26 结论（第一期待办 29）：决定并行期「系统外回复」识别的样本口径。

### 待确认与风险

- 积加补单的异步确认时长与「已推送易仓且未缺货」的判定字段，决定补发的 SLA 与 R-SL-05 提示阈值；积加 Fake 在答复前按假设实现。

- 钉钉标准版每月 5,000 次调用：第二期工作通知量（审批、SLA 超时、生产厂任务）明显增加，5 分钟合并能压一部分；P26 配额卡监控，接近上限时提醒管理员。
- 海帆与本系统并行期：两边都可能回复，回复识别要能区分系统发出与系统外发出（「已发送」同步保留）。
- 开发测试环境接着真实店铺与真实邮箱：写操作守卫与发信白名单缺一不可。
- 公网入口是唯一攻击面：路径白名单、钉钉免登、角色限定三者缺一不可（ADR 0003）。
