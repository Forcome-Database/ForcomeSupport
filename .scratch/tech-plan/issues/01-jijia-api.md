# 调研：积加开放接口能力与申请方式

## Question

积加 ERP 的开放接口实际能做什么、怎么申请？PRD D-17 规定订单、物流轨迹、库存、良仓售后出库单都经积加读写，这是第一期报表与二期售后自动化的前提。

需要查清：
- 能读哪些数据：订单（亚马逊、Shopify 聚合）、物流轨迹、良仓库存、出库单状态、快递单号、实际运费；字段、时效、分页与增量同步方式（时间戳、回调、Webhook）。
- 能写什么：创建良仓售后出库单的接口与参数；回传单号与运费的机制。
- 鉴权方式、频率限制、沙箱或测试环境、SDK。
- 开通流程：谁申请、需要什么资料、费用、周期。
- 找不到公开文档时，写明缺什么，并列出要问积加方的问题清单（供「事务：申请积加开放接口与 SP-API 开发者资质」使用）。

## 第一次调研结论（已重新打开）

详见分支 `research/jijia-api`（提交 923a9f0）的 `docs/research/积加开放接口.md`，含 17 条可直接发给积加方的问题。调研只用公开资料（开放平台文档数据接口），未实际调用业务接口。

- **订单**：可行。亚马逊、Shopify 与全渠道订单可按更新时间分页增量拉取；积加约 1 分钟抓亚马逊、5 分钟同步其他平台。
- **物流**：部分可行。有承运商、跟踪号、发货时间，亚马逊自发货单有预计送达；未找到轨迹事件查询接口。
- **良仓**：库存、出库单状态、单号、实际运费都有接口，但前提是良仓作为三方仓接入积加且状态与费用同步回积加，公开资料无法确认——待确认。
- **写入**：没有「创建海外仓出库单」接口；最接近的是「自发货订单新增 V2」（可设补单发货类型并指定发货仓）；「其他出库单」没有收件地址，不能用于给客户发货——待确认。
- **同步**：无 Webhook，只能轮询；多数接口限 1 次/秒。
- **接入**：appId + appKey 换 token（24 小时有效），可选签名；IP 白名单默认拒绝，服务器需要固定出口 IP；无官方 SDK，按其 OpenAPI 自行生成客户端。
- **开通**：由 FSH 的积加管理员激活，再联系积加销售开通正式接口；标注免费，平台费与周期未知。

**D-17 可行性**：读订单可行；读物流轨迹部分可行；读良仓库存 / 出库状态 / 单号 / 运费待确认；经积加创建良仓售后出库单待确认。

**对其他待办的影响**：
- 「讨论：第一期报表的数据来源与同步」：订单与发货数据 5–10 分钟增量同步够用；「物流停滞满 5 天」（R-IN 未收到与异常、E-33）需要另找轨迹来源，或退为只看发货时间加预计送达——另建「调研：物流轨迹来源」。
- 「事务：申请积加开放接口与 SP-API 开发者资质」：带上文档中的 17 条问题（补单能否自动推送良仓、库存不足的报错方式、单号与运费回传时效、沙箱与费用周期）。
- 「讨论：部署拓扑与数据合规」：出站代理必须提供固定出口 IP 以登记积加白名单。
- 「讨论：集成层设计与「MCP 形式」的含义」：积加适配器只能轮询，需要增量游标与限流（1 次/秒）。

## 第二次调研结论（已被第三次取代）

详见分支 `research/jijia-api`（提交 26da74e，在第一次 923a9f0 基础上更新）的 `docs/research/积加开放接口.md`，含完整接口目录（201 个公开接口、15 类）、补发闭环调用序列与 15 条待问积加方的问题。前提：良仓已作为三方仓接入积加（用户确认）。

- **没有三方仓接口分类**：公开接口中无「海外仓 / 三方仓」分类，也无「创建三方仓出库单」；积加 API 地图里「三方仓管理」「包裹单」「工单售后」均无对应接口。
- **补发的间接路径（积加帮助中心写明支持）**：①「自发货订单新增 V2」推一张补单（`REISSUE`）→ ② 积加按 FSH 的订单策略自动生成三方仓销售出库单并推送良仓 → ③ 良仓出库后状态与单号自动回传积加。
- **回传时效**：出库状态第 1 天每小时同步、第 2–4 天每 2 小时、第 5–30 天每天一次；实际运费每天 02:15 同步一次，最早次日可得。
- **库存不足**：创建接口不报错；订单进「缺货」异常，或良仓拒单后进「三方仓推单失败」，从配货单的缺货标识与错误信息读取（对应 PRD E-06、R-AS-04 的实现方式）。
- **良仓身份待确认**：积加公开的已对接三方仓名单 149 家里没有「良仓」；只有 65 家支持取回实际运费、33 家支持取回轨迹。名字最接近的是「乐仓 Lecangs」（乐歌海外仓），仅为推测。
- **用户点名的三个接口**：3004 查询 API 物流商列表（物流商基础资料，可筛「三方仓物流」，无轨迹）；1027 查询发货单列表（头程发货单，发往 FBA 或海外仓的备货，只有跟踪号与到港到仓日期，无轨迹事件与签收时间，与良仓售后出库无关）；3059 查询物流方式列表（头程物流方式基础资料，无轨迹、单号、运费）。积加 ERP 界面有付费「物流轨迹跟踪看板」（基于 718Track，每 3 小时更新，含签收时间与停留天数），但无开放接口——积加目前不能替代 17TRACK。

**可行性（更新）**
- 读订单：可行。
- 读物流轨迹：部分可行（只有单号、承运商、发货时间、预计送达，无轨迹事件与签收时间）→ 轨迹仍用 17TRACK（见「调研：物流轨迹来源」）。
- 读良仓库存、出库状态、单号：可行；实际运费：部分可行（次日可得，且取决于良仓对接是否支持取回运费）。
- 经积加创建良仓售后出库单：部分可行（走补单间接路径）。
- 补发主链「查库存 → 创建补单 → 积加推良仓 → 读状态与单号 → 读运费」在文档层面打通；轨迹与取消没有开放接口（轨迹接 17TRACK，取消由坐席在积加界面操作）。

**关键待问积加方**：① 良仓在 FSH 积加里对应哪个服务商、支持哪些能力；② 补单的来源渠道与来源单号怎么填才不与原亚马逊订单冲突，指定良仓仓库能否强制生效，明细金额能否全填 0；③ 补单如何配置为全自动流转、且不回写亚马逊发货通知；④ 能否开放轨迹看板或取消补发单的接口，有无 Webhook；⑤ 开放平台收费方式（错误码有「开放平台账户余额不足」，说明为预付余额计费）与开通周期。

## Answer

详见分支 `research/jijia-api`（第三版提交 ce6bde5）的 `docs/research/积加开放接口.md`；海外仓已更正为「易仓」。

**用户指定的 5 个接口**（均为仓库类，限流 2 次/秒，都不返回出库单、买家快递单号、运费或轨迹）
- 63 / 212 / 64：分别只列 FBA 仓、自营仓、供应商仓，与易仓无关。
- 1035 查询仓库信息列表：唯一能找到易仓仓库的接口，按三方仓类型查，返回仓库 ID、易仓仓库代码与服务商信息；还列有易仓接口凭证字段，是否脱敏待联调确认。
- 1449 查询入库单列表 V2：发往易仓的采购、调拨、退货入库单，含易仓侧单号、状态、失败原因；可用于跟踪退货签收。

**易仓在积加中的能力**：积加三方仓名单首行即「易仓」，支持推单、取消、取回实际运费、取回轨迹、库存同步；买家备注与客服备注不传给易仓。同步频率：出库状态与单号推送后 1 天内每小时、2–4 天每 2 小时、5–30 天每天一次；实际运费每天 02:15（次日可见）；易仓真实库存每天凌晨同步一次，开放接口读到的是积加账面库存。

**可行性（第三版）**
- 读订单：可行。
- 读物流轨迹：部分可行（只有单号、承运商、发货时间；积加内部能取易仓轨迹但开放接口读不到）→ **轨迹继续用 17TRACK**。
- 读易仓库存、出库状态、单号：可行；读实际运费：可行（次日）。
- 经积加创建易仓补发单：部分可行（易仓侧能力已确认，积加补单参数待确认）。
- 取消补发单：部分可行（积加界面可取消，开放接口不能；直接调易仓取消接口是否可用待确认）。

**补发闭环**：建单（自发货订单新增 V2 补单）→ 积加推送易仓 → 回传状态与单号 → 回传运费，文档层面已对上。缺口：补单参数待积加确认；第一期取消靠坐席在积加界面操作；轨迹用 17TRACK。

**易仓自身接口（F-MC-01 备用）**：海外仓给客户开的 OMS 账号自带接口，凭证由海外仓发放，不必向易仓申请；可查库存、建单、取消、按单号查跟踪号与费用明细。建议只用于读取与取消，不直接建单，否则积加账面库存与易仓不一致。

**待问积加方**：补单的店铺来源与单号字段怎么填、能否强制指定易仓、金额能否填 0；直接在易仓取消后积加能否同步为「已取消」；1035 返回的易仓凭证是否脱敏；能否开放轨迹查询接口；开通费用与测试环境。另请 FSH 提供易仓对应的服务商名称与 OMS 地址。

**对其他待办的影响**：「讨论：集成层设计与「MCP 形式」的含义」要考虑易仓 OMS 接口作为取消与费用明细的备用通道；「讨论：第一期报表的数据来源与同步」注意库存为积加账面库存、真实库存每天同步一次，运费次日可得。
