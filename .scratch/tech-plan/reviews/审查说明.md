# 技术方案交叉审查说明

你是独立审查者。另有一位来自不同厂商模型的审查者在做同样的审查，互不通气；你的报告交给主持人复核后再决定是否采纳。全程用中文写作（技术术语、标识符保持原文）。

## 背景

Forcome Support：FSH 在亚马逊北美三站（美、加、墨）和两个 Shopify 店铺卖货的智能客服与售后协同系统，按 PRD 从零建设生产系统，分三期：报表与台账 → 售后流程 → AI 回信。今天刚定完技术方案（14 份 ADR），PRD 升到 v2.8 回写了技术方案的结论，并起草了技术方案总文档。下一步要进入第一期的 `/to-spec` → `/to-tickets` → 由 AI 编程代理按待办实现。

已定且不再讨论的前提（审查时不要把它们当问题提，除非它们导致了内部矛盾）：
- 不考虑合规（个人信息不脱敏不删除、亚马逊 DPP、CCPA、LFPDPPP、中国出境规则都不作约束，ADR 0004）；
- 私有化部署在中国大陆公司服务器，经固定境外代理出站，外部系统零入站；
- 模型经 NewAPI 网关，适配 Claude、OpenAI GPT 与兼容接口，不用私有模型或小模型；
- 前端 shadcn/ui + Tailwind CSS v4；TypeScript 小团队，以 AI 编程代理实现为主；第一期 6–8 周。

## 审查维度

1. **口径一致**：总文档、ADR、PRD、待办结论、CONTEXT.md 之间有没有互相矛盾（数字、阶段、来源、状态、责任方、术语）；ADR 之间有没有冲突或被后续 ADR 修订却没标注。
2. **需求对齐**：技术方案能否支撑 PRD 的每项功能、规则与验收标准（尤其第一期：F-OR-01、F-CH-01–04、F-ST-01、F-RP-01、F-LG-01 与第 13 节验收、1.2 指标「报表 T+0、15 分钟内」「登记完整率 ≥ 98%」）；有没有 PRD 要求但技术方案没覆盖、或技术方案做了但 PRD 没有的。
3. **歧义**：同一句话能被读成两种实现的地方；AI 代理按待办实现时会卡住或各自理解的地方。
4. **遗漏**：缺失的决策、缺失的非功能需求（性能、可用性、并发、时区、幂等、数据迁移、测试数据、上线切换）、缺失的失败路径。
5. **核心功能缺陷**：关键链路（来信收取与归并、订单同步、首次回复与 SLA 计算、台账、报表；第二期的审批与动作执行、Feeds 异步、补发；第三期的五步处理与自动发送）在设计上是否有漏洞、竞态、单点或做不通的地方。
6. **更好的建议**：有明显更简单、更可靠或更便宜的做法时提出，并说明取舍；不要为了提而提。

请实际核对原文，不要凭印象；每条发现都要给出能定位的出处。宁缺毋滥：没有把握的写成「疑问」，不要写成缺陷。

只写一个文件：`.scratch/tech-plan/reviews/<你的审查者名>.md`（名字见启动指令），不要修改任何其他文件，不要提交 git。

## 发现

- 问题：<具体描述，引用原文>

完成后在终端里输出一行：`审查完成：.scratch/tech-plan/reviews/<你的审查者名>.md，共 N 条（阻塞 a、重要 b、一般 c、建议 d）`。
