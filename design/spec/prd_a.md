## 0 本版关键调整

以下调整影响业务口径、交互或研发实现，逐条说明原因。

| 编号 | 调整 | 原因与依据 | 影响 |
|---|---|---|---|
| D-01 | 动作审批与报备合并为一张「审批单」 | 旧稿里一次补发要分别走「动作审批」和「报备」，同一件事审两次，且审批人不同。合并后一次处理一次审批，审批人按是否含报备决定（R-AP-02） | 审批页只有一个队列；数据对象 Approval 同时含动作、报备、绑定回复 |
| D-02 | 坐席先审草稿、再「提交审批」，批准后自动发送 | 旧稿「待审草稿」上直接放「发送」按钮，但草稿承诺了补发，发出去之后动作可能被驳回，承诺落空 | 工单增加「待审批」状态；绑定回复在动作成功后才发出（R-AP-06） |

| D-04 | 退款分两类：退货退款走动作审批；免退货退款与部分补偿算「额外赔偿」报备 | 客户确认报备只有快递费用和额外赔偿；普通退货退款是冲销销售，不是 FSH 额外支出 | 退款审批的审批人与台账口径清晰 |

| D-09 | 发起人不能审批自己发起的审批单；发起人是唯一有权审批的人时转备用审批人 | 客服主管也会发起补偿，需要避免自审；团队只有一位客服主管时，其自己发起的报备会无人可审，必须有兜底 | R-AP-02；P20 页头增加「备用审批人」设置，王磊（Q-19 已确认） |

## 1 概述

### 1.1 背景与问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 回信工具只能回信 | 现用海帆能起草邮件，不能操作亚马逊、Shopify 后台 | 补发、改地址、退款要在多个后台之间切换 |
| 售后靠手工推进和登记 | 配件补发在邮件、生产厂、良仓、平台后台之间来回，最后人工填表 | 漏登、对账不上，不知道每单成本由谁承担 |
| 报表靠人工导出 | 日常数据从积加导出再整理 | 管理层看不到实时工单量、SLA、售后成本 |

业务范围：亚马逊 US / CA / MX 自发货与良仓海外仓；Shopify 独立站（forcome.com 覆盖 US、CA，forcome.mx 覆盖 MX）；两个平台都是多店铺。客户给出的优先级：报表先行，售后流程其次，AI 回信最后。

### 1.2 目标与指标

| 指标 | 定义与口径 | 现状 | 目标 | 阶段 |
|---|---|---|---|---|
| 报表时效 | 数据产生到可在报表查看 | 人工导出，按周 | T+0，15 分钟内 | 一 |
| 售后登记完整率 | 登记字段齐全的已完成售后单 ÷ 已完成售后单 | 待测 | ≥ 98% | 一 |
| 售后单人工操作次数 | 从售后单创建到完成，人工需要点击确认的环节数 | 待测 | ≤ 2 次（确认、报备审批） | 二 |
| 售后单处理时长 | 售后单创建到单号回复客户 | 待测 | 缩短 50% | 二 |
| 亚马逊 SLA 达标率 | 24 小时内首次回复的亚马逊来信 ÷ 亚马逊来信（R-SL-01） | 待测 | ≥ 99% | 二 |
| 草稿采纳率 | R-SD-04 | 无 | ≥ 80% | 三 |
| 自动发送占比 | 无人工参与即发出的回复 ÷ 全部回复 | 无 | ≥ 40% | 三 |
| 首次回复中位数 | 来信到首次回复的中位时长 | 待测 | ≤ 2 小时 | 三 |

现状值由客户在上线前一个月提供（Q-08 样本同期导出）。

### 1.3 非目标

- 不做面向客户的聊天窗口、电话客服。
- 不替代 ERP（积加）、平台后台与良仓的订单、库存、发货管理；只通过积加与平台官方接口读写必要字段。
- 不做生产厂的生产、库存管理；工厂工作台只处理售后相关任务。
- 第一、二阶段不追求全自动回信；AI 回信在第三阶段替换海帆。

### 1.4 术语表

| 术语 | 定义 |
|---|---|
| FSH | 销售公司（总部运营团队），面向客户销售并承担售后 |
| 生产厂 | 同集团的生产工厂，共两家：FQD（整机、电池、软管、HEPA 滤芯、集尘杯）、FZJ（充电线），负责配件供货、直寄与费用分摊，不是外部供应商；SKU 与生产厂的对应在 P24 工厂账号维护（R-FT-07） |
| 良仓 | 海外仓，有库存时由它发货；本系统经积加读写它的库存与售后出库单，不直连 |
| 积加 | 客户现用的 ERP，已聚合亚马逊与 Shopify 的订单与物流并对接良仓；本系统的订单、物流轨迹、库存与良仓售后出库单都经它读写（Q-25） |
| SP-API | 亚马逊官方卖家接口：本系统用于退款、取消订单（订单与物流信息经积加） |
| 买家消息邮件中转 | 亚马逊官方的买家与卖家沟通方式：买家来信转发到店铺绑定的邮箱，回复发往中转地址即送达买家 |
| 物流查询 | 承运商轨迹；经积加的物流聚合查询，用于判定停滞满 5 天与超预计送达 |
| 店铺 | 平台上的一个销售账号，例如亚马逊 Forcome Direct、Shopify forcome.com；工单、售后单、权限都按店铺区分 |
| 渠道 | 来信进入的途径：亚马逊买家消息（邮件中转到店铺绑定邮箱）、Shopify 与直邮邮件；都经 Gmail API 收发 |
| 直邮 | 客户不经平台消息、直接写到店铺客服邮箱的邮件 |
| 工单 | 一个客户就一笔订单（或无订单时就一个话题）的全部往来；编号 T-日期-序号 |
| 重复联系 | 我方给出结论性回复（方案、承诺或拒绝）后，客户就同一问题再次来信；次数决定升优先级或转人工（R-TK-03） |
| SLA | 对每封客户来信的首次回复时限（R-SL） |
| 工作日、工作小时 | 周一至周五 09:00–18:00（北京时间），不扣节假日；1 个工作日 = 9 个工作小时。生产厂任务、人工操作清单等时限按它计算（R-CL） |
| 意图 | 来信要解决的事，共 12 个，决定处理规则（R-IN） |
| 风险信号 | 命中即转人工的情况（R-RS） |
| 草稿 | AI 生成的回复，一封来信默认 3 版 |
| 审批单 | 需要人批准才能执行的一组内容：动作、报备、绑定回复；编号 AP-日期-序号 |
| 备用审批人 | 发起人恰好是唯一有权审批的人时接收该审批单的人；审批单剩 1 小时仍未处理时也会收到提醒并可审批。由管理员在 P20 指定，默认王磊（R-AP-02、R-AP-03） |
| 动作 | 系统对外部系统的写操作，例如创建售后出库单、退款、改地址 |
| 售后出库单 | 为售后补发在良仓创建的出库单，批准后经积加创建，良仓回传单号与实际运费 |
| 报备 | FSH 现金支出前的审批，只有快递费用、额外赔偿两类（R-FL） |
| 人工操作清单 | 兜底机制：接口连续执行失败、或某项动作暂无接口时生成，由发起人按步骤在后台或积加完成并回填 |
| 钉钉 | 集团统一的组织与协同平台：本系统的成员与部门从钉钉通讯录同步，登录用钉钉，通知推送钉钉工作通知 |
| 售后单 | 一次产生费用或寄件的售后处理；编号 S-日期-序号 |
| 当前环节、等待方 | 售后单卡在哪一步、在等谁；与售后单主状态分开记录（6.5） |
| 处理方式 | 调整安装方式 / 寄配件 / 退款或部分补偿 |
| 责任类型 | 客户使用问题 / 产品质量问题 / 物流问题 / 其他 |
| 承担比例 | FSH 与生产厂对售后费用的分摊百分比，按产品成本、快递物流、其他费用（额外赔偿 + 其他）三组分别记录（R-AS-02） |
| 比例协商 | FSH 与生产厂在工厂工作台上确定承担比例的过程 |
| 内部结算 | FSH 与生产厂按月汇总已确认比例的售后费用 |
| 结算批次 | 每个生产厂每月一个，汇总比例已确认的售后单，双方确认后为已结算；编号 年-月-生产厂-序号，例 2026-09-FQD-A |
| 工厂工作台 | 生产厂对接人使用的独立界面 |
| 登记台账 | 全部售后单的费用、报备、比例、结算登记表 |
