## 0 本版关键调整

以下调整影响业务口径、交互或研发实现，逐条说明原因。

| 编号 | 调整 | 原因与依据 | 影响 |
|---|---|---|---|
| D-01 | 动作审批与报备合并为一张「审批单」 | 旧稿里一次补发要分别走「动作审批」和「报备」，同一件事审两次，且审批人不同。合并后一次处理一次审批，审批人按是否含报备决定（R-AP-02） | 审批页只有一个队列；数据对象 Approval 同时含动作、报备、绑定回复 |
| D-02 | 坐席先审草稿、再「提交审批」，批准后自动发送 | 旧稿「待审草稿」上直接放「发送」按钮，但草稿承诺了补发，发出去之后动作可能被驳回，承诺落空 | 工单增加「待审批」状态；绑定回复在动作成功后才发出（R-AP-06） |
| D-03 | 所有产生 FSH 费用或寄件的处理都生成售后单，两条创建路径 | 旧稿只有产品故障会建售后单，未收到补发、错发换发、免退货退款的费用进不了台账，报表成本不全 | 台账覆盖全部售后成本；责任由规则或 AI 建议、人工确认（R-AS-02） |
| D-04 | 退款分两类：退货退款走动作审批；免退货退款与部分补偿算「额外赔偿」报备 | 客户确认报备只有快递费用和额外赔偿；普通退货退款是冲销销售，不是 FSH 额外支出 | 退款审批的审批人与台账口径清晰 |
| D-05 | 工单按「店铺 + 订单」归并，无订单时按客户 | 旧稿按「客户有未关闭工单就追加」，同一客户两笔订单两个问题会挤进一张工单 | R-TK-01、R-TK-02；示例数据相应调整 |
| D-06 | SLA 以每封来信为对象，终点是对它的第一封回复；「工作日」按统一工作日历计算 | 旧稿未定义 SLA 何时停、等待状态是否计时、工作日是否含节假日，研发无法实现，报表口径不一 | R-SL-01 至 R-SL-07、R-CL-01 至 R-CL-02；承诺类回复需要审批时先发进展回复 |
| D-07 | 售后单主状态只有 4 个，另用「当前环节」「等待方」描述卡点 | 旧稿把流程步骤当状态，状态多且不可枚举 | 列表可按「在等谁」排序；协商与结算是独立维度，不阻塞售后单完成 |
| D-08 | 比例协商最多 3 轮，超时或拒绝转「待升级」由双方负责人商定 | 旧稿没有终止条件，协商可能无限拖延 | R-AS-06；结算只收比例已确认的售后单 |
| D-09 | 发起人不能审批自己发起的审批单；发起人是唯一有权审批的人时转备用审批人 | 客服主管也会发起补偿，需要避免自审；团队只有一位客服主管时，其自己发起的报备会无人可审，必须有兜底 | R-AP-02；P20 增加「备用审批人」设置，默认王磊（Q-19） |
| D-11 | 第 ⑤ 步只输出自动发送、待审草稿、转人工；「待审批」只由坐席主动提交产生。转人工工单提交审批后保持「转人工」 | 若系统直接判为待审批，审批单没有发起人，「不能自审」「驳回退回发起人」「人工操作清单指派给发起人」都无法执行；转人工工单若改成待审批，风险标记会从转人工队列消失，主管看不到 | 5.1、5.2、6.1 迁移表与五张流程图统一；P03 发送进展回复后工单仍为转人工 |
| D-12 | 重复联系次数 = 我方回复后问题仍未解决又来信的次数；1 次升优先级，2 次转人工 | 旧稿混用「第 N 封来信」与「第 N 次」，规则、验收、页面三处数字对不上 | R-TK-03、R-RS、AC-TK-05；P03 显示「重复联系 1 次」 |
| D-13 | 售后单负责人固定为按店铺分配的售后负责人，路径 B 的坐席记为发起人 | 旧稿路径 B 的售后单负责人写成坐席，与「售后负责人推进售后单」冲突，列表「需我处理」口径不一 | 6.5、11.1；P07 负责人列、P11 元信息 |
| D-10 | 视觉方向采用 A「精密工作台」；原型交付形式为静态高保真 + 状态板 + 逐页交互规格 | 客户一直未选方向；A 信息密度最高、最接近成熟客服工作台，研发实现风险最低。交互以规格表加状态板表达，比可点击原型更利于验收逐条对照 | 如需改用其他方向，只替换组件库色板与字体，不影响页面结构（Q-17） |

## 1 概述

### 1.1 背景与问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 回信工具只能回信 | 现用海帆能起草邮件，不能操作积加、Shopify | 补发、改地址、退款要在多个后台之间切换 |
| 售后靠手工推进和登记 | 配件补发在邮件、生产厂、良仓、积加之间来回，最后人工填表 | 漏登、对账不上，不知道每单成本由谁承担 |
| 报表靠人工导出 | 日常数据从积加导出再整理 | 管理层看不到实时工单量、SLA、售后成本 |

业务范围：亚马逊 US / DE / UK 自发货与良仓海外仓；Shopify 独立站；两个平台都是多店铺。客户给出的优先级：报表先行，售后流程其次，AI 回信最后。

### 1.2 目标与指标

| 指标 | 定义与口径 | 现状 | 目标 | 阶段 |
|---|---|---|---|---|
| 报表时效 | 数据产生到可在报表查看 | 人工导出，按周 | T+0，15 分钟内 | 一 |
| 售后登记完整率 | 登记字段齐全的已完成售后单 ÷ 已完成售后单 | 待测 | ≥ 98% | 一 |
| 售后单人工操作次数 | 从售后单创建到完成，人工需要点击确认的环节数 | 待测 | ≤ 2 次（确认、报备审批） | 二 |
| 售后单处理时长 | 售后单创建到单号回复客户 | 待测 | 缩短 50% | 二 |
| 亚马逊 SLA 达标率 | 24 小时内首次回复的亚马逊来信 ÷ 亚马逊来信（R-SL-01） | 待测 | ≥ 99% | 二 |
| 草稿采纳率 | R-SD-04 | 无 | ≥ 80% | 三 |
| 自动发送占比 | 无人工参与即发出的回复 ÷ 全部回复 | 无 | ≥ 40% | 三 |
| 首次回复中位数 | 来信到首次回复的中位时长 | 待测 | ≤ 2 小时 | 三 |

现状值由客户在上线前一个月提供（Q-08 样本同期导出）。

### 1.3 非目标

- 不做面向客户的聊天窗口、电话客服。
- 不替代积加的订单、库存、发货管理，只读写必要字段。
- 不做生产厂的生产、库存管理；工厂工作台只处理售后相关任务。
- 第一、二阶段不追求全自动回信；AI 回信在第三阶段替换海帆。

### 1.4 术语表

| 术语 | 定义 |
|---|---|
| FSH | 销售公司（总部运营团队），面向客户销售并承担售后 |
| 生产厂 | 同集团的生产工厂（首个为东莞生产厂），负责配件供货、直寄与费用分摊，不是外部供应商 |
| 良仓 | 海外仓，有库存时由它发货 |
| 积加 | ERP，同步亚马逊站内信与各店铺订单、库存、发货、费用 |
| 店铺 | 平台上的一个销售账号，例如亚马逊 Forcome Direct、Shopify forcome.com；工单、售后单、权限都按店铺区分 |
| 渠道 | 来信进入的途径：亚马逊站内信（经积加）、邮件（经 Gmail） |
| 工单 | 一个客户就一笔订单（或无订单时就一个话题）的全部往来；编号 T-日期-序号 |
| SLA | 对每封客户来信的首次回复时限（R-SL） |
| 意图 | 来信要解决的事，共 12 个，决定处理规则（R-IN） |
| 风险信号 | 命中即转人工的情况（R-RS） |
| 草稿 | AI 生成的回复，一封来信默认 3 版 |
| 审批单 | 需要人批准才能执行的一组内容：动作、报备、绑定回复；编号 AP-日期-序号 |
| 动作 | 系统对外部系统的写操作，例如创建发货单、退款、改地址 |
| 报备 | FSH 现金支出前的审批，只有快递费用、额外赔偿两类（R-FL） |
| 人工操作清单 | 积加做不了的动作，由坐席按步骤在平台后台完成并回填 |
| 售后单 | 一次产生费用或寄件的售后处理；编号 S-日期-序号 |
| 处理方式 | 调整安装方式 / 寄配件 / 退款或部分补偿 |
| 责任类型 | 客户使用问题 / 产品质量问题 / 物流问题 / 其他 |
| 承担比例 | FSH 与生产厂对一张售后单费用的分摊百分比 |
| 比例协商 | FSH 与生产厂在工厂工作台上确定承担比例的过程 |
| 内部结算 | FSH 与生产厂按月汇总已确认比例的售后费用 |
| 工厂工作台 | 生产厂对接人使用的独立界面 |
| 登记台账 | 全部售后单的费用、报备、比例、结算登记表 |

### 1.5 系统边界

```
客户 ──亚马逊站内信──→ 积加 ──积加 MCP──┐
客户 ──邮件──────────→ Gmail ─Gmail API─┤
                                          ├→ Forcome Support ──统一动作接口──→ 积加 MCP / 人工操作清单（第三阶段：亚马逊 MCP、Shopify MCP）
生产厂 ──工厂工作台（同一系统）──────────┘            └──企业即时通讯──→ 审批人、生产厂对接人
```
