以下调整影响业务口径、交互或研发实现，逐条说明原因。

编号 调整 原因与依据 影响
D-01 动作审批与报备合并为一张「审批单」 旧稿里一次补发要分别走「动作审批」和「报备」，同一件事审两次，且审批人不同。合并后一次处理一次审批，审批人按是否含报备决定（R-AP-02） 审批页只有一个队列；数据对象 Approval 同时含动作、报备、绑定回复
D-02 坐席先审草稿、再「提交审批」，批准后自动发送 旧稿「待审草稿」上直接放「发送」按钮，但草稿承诺了补发，发出去之后动作可能被驳回，承诺落空 工单增加「待审批」状态；绑定回复在动作成功后才发出（R-AP-06）
D-03 所有产生 FSH 费用或寄件的处理都生成售后单，两条创建路径 旧稿只有产品故障会建售后单，未收到补发、错发换发、免退货退款的费用进不了台账，报表成本不全 台账覆盖全部售后成本；责任由规则或 AI 建议、人工确认（R-AS-02）；售后负责人在 P07 手工新建的售后单按路径 A 进入待确认
D-04 退款分两类：退货退款走动作审批；免退货退款与部分补偿算「额外赔偿」报备 客户确认报备只有快递费用和额外赔偿；普通退货退款是冲销销售，不是 FSH 额外支出 退款审批的审批人与台账口径清晰
D-05 工单按「店铺 + 订单」归并，无订单时按客户 旧稿按「客户有未关闭工单就追加」，同一客户两笔订单两个问题会挤进一张工单 R-TK-01、R-TK-02；示例数据相应调整
D-06 SLA 以每封来信为对象，终点是对它的第一封回复；「工作日」按统一工作时间计算 旧稿未定义 SLA 何时停、等待状态是否计时、工作日是否含节假日，研发无法实现，报表口径不一 R-SL-01 至 R-SL-07、R-CL-01 至 R-CL-02；承诺类回复需要审批时先发进展回复
D-07 售后单主状态只有 4 个，另用「当前环节」「等待方」描述卡点 旧稿把流程步骤当状态，状态多且不可枚举 列表可按「在等谁」排序；协商与结算是独立维度，不阻塞售后单完成
D-08 比例协商最多 3 轮；生产厂拒绝、答复超时，或售后负责人在还价后主动升级，都转「待升级」由双方负责人商定 旧稿没有终止条件，协商可能无限拖延 R-AS-06；结算只收比例已确认的售后单
D-09 发起人不能审批自己发起的审批单；发起人是唯一有权审批的人时转备用审批人 客服主管也会发起补偿，需要避免自审；团队只有一位客服主管时，其自己发起的报备会无人可审，必须有兜底 R-AP-02；P20 页头增加「备用审批人」设置，王磊（Q-19 已确认）
D-10 视觉采用 v3：56px 顶栏 + 分段导航、浅灰底上的圆角浮动面板、靛蓝主色，AI 产出用靛蓝→青色渐变 ✦ 标识；原型交付为静态高保真 + 状态板 + 逐页交互规格；研发用 shadcn/ui + Tailwind CSS v4 客户提供参考稿（forcome-support-console.html）并指定技术栈。原型组件与 shadcn 组件一一对应（设计规范第 12 节），令牌可直接写进 globals.css，减少设计到研发的转换 页面结构不变，组件库 spec/ui.py 统一换肤；第一期只做浅色，舒适与紧凑两档密度都上线（Q-24 已确认，见全局状态 G9）；深色令牌预留
D-11 第 ⑤ 步只输出自动发送、待审草稿、转人工；「待审批」只由坐席主动提交产生。转人工工单提交审批后保持「转人工」 若系统直接判为待审批，审批单没有发起人，「不能自审」「驳回退回发起人」「人工操作清单指派给发起人」都无法执行；转人工工单若改成待审批，风险标记会从转人工队列消失，主管看不到 5.1、5.2、6.1 迁移表与五张流程图统一；P03 发送进展回复后工单仍为转人工
D-12 重复联系次数 = 我方给出结论性回复（方案、承诺或拒绝）后，客户就同一问题再次来信的次数；对排查步骤的答复、按要求补充的信息、致谢与确认都不计。1 次升优先级，2 次转人工 旧稿混用「第 N 封来信」与「第 N 次」，规则、验收、页面三处数字对不上；若把排查步骤的答复也计入，路径 A 排查两轮的工单都会被强制转人工，与售后流程冲突 R-TK-03、R-RS、AC-TK-05、AC-TK-15；消息增加「回复类型」字段；P03 显示「重复联系 1 次」，P05 为 0 次

1.3 非目标

  • 不做面向客户的聊天窗口、电话客服。
  • 不替代 ERP（积加）、平台后台与良仓的订单、库存、发货管理；只通过积加与平台官方接口读写必要字段。
  • 不做生产厂的生产、库存管理；工厂工作台只处理售后相关任务。
  • 第一、二阶段不追求全自动回信；AI 回信在第三阶段替换海帆。

5 核心流程

5.1 每封来信的五步处理

第 ⑤ 步只输出三种结果：自动发送、待审草稿、转人工。「待审批」不是第 ⑤ 步的输出，而是坐席审阅含审批项的草稿后主动「提交审批」的结果。

步骤 输入 处理 输出 失败时
① 接收与关联 亚马逊买家消息（亚马逊邮件中转到店铺绑定邮箱）、Shopify 与直邮邮件，均经 Gmail API 收取 去重（Message-ID）；识别店铺（收件邮箱；亚马逊另按发件域 amazon.com / .ca / .com.mx 识别站点）；识别来源（客户、平台通知、已登记生产厂、其他供应商）；在该店铺内关联订单（积加）与客户；按 R-TK-01 归并到工单 工单与消息；SLA 开始计时 店铺识别不出 → 进「未归属店铺」队列（E-13）；订单关联不上 → 继续处理，草稿里一次问全订单信息
② 风险拦截 消息正文、客户历史 对照风险信号清单（R-RS） 命中 → 转人工并写明信号与原文；未命中 → 进入 ③ 模型不可用 → 按关键词规则拦截，其余跳过 ③④，工单标「AI 未处理」进收件箱（E-03）
