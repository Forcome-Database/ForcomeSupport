1 背景与问题

回信工具只能回信现用海帆能起草邮件，不能改 Shopify 订单，不能在积加创建售后发货单。最耗时的操作仍是人工在多个后台之间切换。
售后流程靠手工推进和登记配件补发要在邮件、工厂、良仓、积加之间来回，最后人工把单号、配件号、费用登记进表格，漏登与对账不上是常态。
报表靠人工导出日常数据从积加导出再整理，管理层看不到实时的工单量、SLA 与售后成本。

业务范围：亚马逊 US / DE / UK 自发货与良仓海外仓、Shopify 独立站、工厂配件补发。亚马逊与 Shopify 均为多店铺。接入只有两条线：亚马逊站内信经积加收发，Shopify 客户来信与直邮走 Gmail 客服邮箱；订单、库存、发货、费用统一从积加读取。与工厂的衔接和沟通全部在系统内的工厂工作台完成，不走邮件。客户给出的优先级：报表先行，售后流程其次，AI 回信最后。FSH 是销售公司（总部运营团队），工厂是同一集团的生产厂，不是外部供应商；两者之间是内部协同与内部结算。

5 核心流程

5.1 每封来信的五步处理

1 接收与关联识别来源与店铺；按订单号、亚马逊匿名邮箱、Shopify 邮箱关联该店铺的积加订单；追加或新建工单
→
2 风险拦截对照风险信号清单，命中即转人工并标明原因
→
3 理解与处理识别意图与信息；按处理规则查数据、提出动作；草稿默认 3 版，按解决方案区分；缺信息一次问全
→
4 回复检查事实有来源、不越政策、符合渠道内容能力、语言与客户一致、不泄露内部信息
→
5 发送方式自动发送 / 待审草稿 / 动作审批后发 / 转人工，按意图配置

步骤固定，规则可配置。规则定义只在第 6 节，画布上的"AI Agent 决策逻辑"图与本节一致。

5.2 售后流程

共同入口

产品故障先按故障排查树给步骤。排查不成，AI 建议处理方式（三选一）与责任类型（四选一）并附依据；售后负责人确认或改判后创建售后单，估算四项费用。定义见第 6.5 节。

统一登记台账

所有处理方式写同一张表：售后单号、原工单、客户与站点、处理方式、责任类型与依据、配件号与数量、分支、快递单号、产品成本、运费、额外赔偿、其他、报备类型与状态、承担比例、协商状态、结算状态、登记方式。字段在流程推进中自动填齐，人工只补缺失项。

调整安装方式

草稿给安装或使用指导（待审草稿）→ 等客户 7 天 → 解决则关闭并登记，责任默认客户使用问题、费用 0；未解决改为寄配件

退款 / 部分补偿

金额提案 → 报备额外赔偿 客服主管 → 执行付款（MCP 接入前按操作清单人工完成并回填）→ 回复客户 → 登记 → 进承担比例协商。换新走寄配件线，配件换整机

寄配件 · 良仓无货，工厂直寄

工厂工作台派发询价单并推送即时消息 → 工厂在工厂工作台报价（超 2 个工作日催）→ 报备快递费用 客服主管 → 工厂工作台生成寄件任务并显示完整收件信息，同时发起比例协商 → 工厂回填单号与实际运费（超 3 个工作日催）→ 单号回复客户 → 登记完成

寄配件 · 良仓有货，良仓发货

按积加费率估算运费 → 报备快递费用，附发货单参数 客服主管 → 通过即经积加 MCP 创建售后发货单 → 良仓发出，实际运费从积加读取 → 单号回复客户 → 登记完成 → 进承担比例协商

承担比例协商，与寄件并行

系统按责任类型给建议比例 → 工厂工作台发起分摊提案，附依据与照片 → 工厂在工厂工作台接受、还价或拒绝（超 3 个工作日催）→ 接受即生效，还价由负责人确认 人工 → 月度按比例对账 → 结算后标"已结算"。客户不等协商结果。

三个人工点之外，其余自动

责任与处理方式确认（售后负责人）、报备（客服主管）、协商比例录入（售后负责人）是人工；发货单由报备通过直接触发，不再单独确认；派发工厂工作台任务、催办、写台账、发起协商全部自动；工厂填的是结构化表单，不再解析邮件。谈不拢的比例升级双方负责人。

购买咨询售前站点、目的国促销与物流配置、积加库存无；亚马逊只陈述事实待审草稿
批发与合作售前无无无转销售

6.2 风险信号（第 2 步，命中即转人工）

信号判定优先级
安全事故起火、冒烟、过热、烫伤、电池鼓包最高 人工处理并留档
平台风险提到 A-to-Z、拒付、差评或 feedback 威胁、投诉到平台、律师或法律高
重复联系同一工单第 2 次来信未解决升一级；第 3 次强制人工中
高价值订单金额或客户累计消费超阈值（阈值待定）中
要求真人客户明确要求与人沟通中
无法处理的内容不支持的语言、乱码、只有附件普通

情绪只保留负面、中性、正面三档，用于排序、报表和道歉程度，不做转人工依据。退款申请不在清单里，退款动作走审批。

6.3 发送方式与动作分级

发送方式（第 5 步）
  • 自动发送 置信度 ≥ 意图阈值、依据齐全、意图在白名单、回复不含承诺动作。起步白名单：订单查询、发票与收据。
  • 待审草稿 默认。坐席采纳、修改、拒绝的结果回流；连续 30 天采纳率高于 90% 的意图，由客服主管在设置页切换为自动发送，可随时切回。
  • 动作审批后发 回复承诺了补发、退款、改地址等高风险动作时，先过审批再发出。
  • 转人工 来自风险信号、规则本身、无法识别、检查不过且置信度极低。
  • 亚马逊 SLA 保底：剩 4 小时未处理且无风险信号，自动发一条预审过的进展回复。是否启用待客户运营确认。
动作分级
  • 只读 查订单、库存、物流、费用。自动执行。
  • 低风险写 加备注、写登记台账、向工厂工作台派发任务与催办、向承运商查件。自动执行并留痕。
  • 高风险写 退款、改地址、取消进审批队列，审批人：客服主管或售后负责人；审批时限 4 小时，超时提醒并升级。创建发货单、通知工厂寄出涉及 FSH 快递费用，走报备（第 6.5 节），报备通过即触发，不再单独审批。
  • 人工操作清单 统一动作接口里积加 MCP 做不了的动作（亚马逊与 Shopify 退款、Shopify 改地址、取消），审批通过后生成操作清单，坐席在平台后台完成并回填，第三阶段由 MCP 替换。
  • 熔断：任一意图 24 小时内被拒绝或修改超过 30%，自动降回待审草稿并通知主管。

6.5 售后责任、费用与报备

责任类型AI 建议依据（人工确认才生效）建议承担比例 FSH / 工厂说明
客户使用问题按排查树调整安装或使用方式后解决；照片显示误用100 / 0，或客户付费购买配件无寄件时费用为 0
产品质量问题保修期内失效；照片与已知缺陷一致；排查不成0 / 100最常见，占多数售后单
物流问题轨迹丢失、破损签收、错发漏发由承运或仓端造成100 / 0，FSH 向承运商或良仓索赔不进工厂协商
其他无法归入以上三类人工定，默认 50 / 50逐单协商
处理方式与费用
  • 处理方式三选一：调整安装方式（指导解决，不寄东西）、寄配件（良仓有货或无货两条分支，换新走同一条线）、退款或部分补偿（现金，FSH 支付）。
  • 费用四项：产品成本、运费、额外赔偿、其他。产品成本与运费来自工厂报价或积加费率，其余人工填。
  • 责任由 AI 按上表给建议并附依据，售后负责人确认或改判后才写入售后单。
报备与承担比例
  • 报备只有两类：快递费用、额外赔偿。只要由 FSH 支付就报备，与库存分支无关；审批人客服主管，时限 4 小时，无金额门槛；通过即视为该笔动作的审批。
  • 承担比例由 FSH 与工厂逐单协商：系统按责任类型给建议比例，在工厂工作台发起分摊提案，工厂接受、还价或拒绝并写理由（超 3 个工作日自动催）；接受即生效，还价由负责人确认后写台账。
  • 协商与寄件并行，客户不等协商结果；月度按确认比例向工厂对账，结算后台账标"已结算"。

9.4 多店铺设计

环节设计
原则店铺是工单的一个维度，加一层配置覆盖；五步处理、售后流程、审批只有一套，不按店铺分叉
进线识别亚马逊消息用积加店铺 ID 加站点；邮件用收件地址对应店铺；识别不出的进"未归属店铺"队列由人工指定
订单关联只在该店铺的订单里匹配，避免不同店铺订单号或邮箱撞车
回复与动作回复从来信的同一店铺身份发出（积加店铺会话或该店铺邮箱），使用该店铺的签名与品牌名；动作带店铺 ID，由 MCP 适配器取该店铺凭据；禁止跨店铺发送
客户档案同一客户跨店铺可合并，需人工确认；对客户的回复不提及其在其他店铺的订单
规则与知识三层取值：全局默认 → 平台 → 店铺覆盖。可覆盖项限于签名、退货政策口径、模板、素材与链接白名单、SLA；意图、风险信号、动作分级不允许按店铺改
发送方式与采纳率按意图全局配置与统计，避免单店样本太少；可按店铺查看，个别店铺可单独降回待审草稿
台账与报表工单、售后单、台账都带店铺字段；报表默认汇总，可按店铺、站点下钻
新增店铺在设置页的店铺管理里登记并连通积加或邮箱即可，不需要改流程

10 非功能与合规

可用性与降级
  • 积加或 Gmail 不可用：来信暂存队列，恢复后按到达顺序处理，SLA 从原到达时间计。
  • 模型不可用：跳过第 3、4 步，工单直接进收件箱由人工处理，标"AI 未处理"。
  • 每一步独立任务可重试，失败不丢消息；处理链路目标 5 分钟内出草稿。
数据与合规
  • 亚马逊数据保护政策对买家个人信息有保留期限要求，订单快照中的 PII 按政策期限清除，工单保留脱敏后的业务字段。
  • DE 与 UK 客户受 GDPR 约束：数据最小化、删除请求 30 天内响应、处理记录可导出。
  • 亚马逊回复不含外链、营销、站外联系方式；模板由客户运营预审。
  • 所有 AI 输出、人工操作、动作执行写审计日志，保留不少于 2 年。
  • 生产厂是集团内部角色，按需可见：只见本厂任务与寄件所需的收件信息，不显示客户邮箱与售价。
质量评估
  • 上线前：用至少 500 封历史来信标注意图，验证分布与分类准确率 ≥ 90%；用 100 封抽样人工评分草稿可用性 ≥ 80%。
  • 上线后：每周抽检 50 封自动发送回复；采纳率、拒绝原因按意图看板。
成本
  • 模型费用与来信量线性相关，按每封 2 到 3 次调用估算，缓存后单封成本可控在人工处理成本的 5% 以内（待按实际量核算）。
  • 积加 MCP 自建，封装积加开放接口；没有接口的部分用浏览器自动化兜底，维护成本高，作为过渡方案。
