# 部署说明

适用于**开发测试环境**（待办 03）。生产环境的部署、备份、监控与日志轮转随 28 号待办补进本文。

依据：ADR 0003、0013 及其修订；用户 2026-10-04 口径——服务器与 GitHub 暂未就绪，**先在本机用 Docker 部署与测试**，部署脚本与 Compose 原样搬到 Linux 服务器；内网 HTTPS 先用 caddy 内部 CA（`tls internal`），公司域名与 DNS-01 到位后切换；外部服务只有钉钉企业内部应用已有，开发测试环境默认全部用 Fake。

## 1 组成

一份 Compose（`deploy/compose.yml`）给开发测试与生产两套环境共用，由部署脚本按环境固定项目名：开发测试 `forcome-staging`，生产 `forcome-production`（28 号待办）。容器、数据卷、网络都以项目名为前缀，两套环境互不影响。

| 服务 | 镜像 | 作用 |
|---|---|---|
| caddy | `forcome-web:<版本>` | 内网 HTTPS、托管前端静态文件、把 `/api` 转给 api（`deploy/web/Dockerfile` 的 web 目标与 `Caddyfile`） |
| api | `forcome-server:<版本>` | HTTP 接口 |
| worker | `forcome-server:<版本>` | 后台任务 |
| migrate | `forcome-server:<版本>` | 一次性：只向前执行迁移，先于 api 与 worker |
| seed | `forcome-server:<版本>` | 一次性、只用于非生产：灌示例数据夹具（各加载步骤幂等） |
| postgres | `forcome-postgres:18` | 自建 PostgreSQL 18 镜像（`deploy/postgres/`；WAL-G 随 28 号待办） |
| smoke | `forcome-smoke:<版本>` | 一次性：部署后的 Playwright 冒烟（`deploy/web/Dockerfile` 的 smoke 目标，入口 `deploy/smoke/run-smoke.sh`） |

- **版本**：git 提交号（12 位）；工作区有未提交的改动时加 `-dirty`（只会出现在本机）。
- **数据卷**：`pgdata`（数据库）、`caddy_data`（内部 CA 的根证书与私钥，**不要删**，见第 4 节）、`caddy_config`。
- **端口**（本期本机可用 4510–4520）：

| 端口 | 用途 |
|---|---|
| 4510 | 开发测试环境 HTTPS（`HTTPS_BIND`，本机默认只开在 127.0.0.1） |
| 4511 | 开发测试环境 PostgreSQL（只开在 127.0.0.1，供 `psql` 排查） |
| 4512–4513 | 预留给生产环境（28 号待办） |
| 4514–4515 | 机动 |
| 4516–4520 | 本机开发（见 README「开发」） |

## 2 部署（现在：在本机执行）

前提：Docker（含 compose v2）、git、Node 22 以上。部署脚本只用 Node 自带的模块，不需要 `pnpm install`。

```bash
pnpm deploy:staging            # 等同于 node deploy/deploy.mjs staging
```

第一次运行时，脚本从 `deploy/.env.example` 生成 `deploy/.env.staging`（随机数据库口令，不进 git），以后改这个文件调整配置。各变量的含义写在模板里。

脚本依次执行下列步骤，任一步失败，之后的步骤不再执行、退出码为 1：

| 步骤 | 做什么 |
|---|---|
| 准备 | 读取并校验环境文件（APP_ENV 必须与环境相符、域名、端口、口令格式）；版本取当前提交号 |
| 构建镜像 | `postgres`、`migrate`（后端镜像）、`caddy`（前端镜像）、`smoke` |
| 启动数据库 | 等到 PostgreSQL 健康 |
| 执行迁移 | 单独运行 `migrate`；失败即停，api 与 worker 仍是上一版本 |
| 灌示例数据 | 单独运行 `seed`（只用于非生产；已有的数据跳过，不会重复） |
| 启动 api、worker、caddy | 等到健康，并核对三者运行的都是本次构建的镜像 |
| 内网 HTTPS | 导出 caddy 的根证书，只用它核对证书链与域名，再经 HTTPS 取 `/api/health` 与首页 |
| 冒烟 | 在一次性容器里只信任该根证书，经 Compose 网络按内网域名访问，跑 `apps/web/e2e` 的全部 Playwright 用例（现在是开发登录 → 看到顶栏，HTTPS 下会话 Cookie 带 `Secure`） |

失败时不回滚：开发测试环境停在失败处，方便排查。产物在 `deploy/.state/staging/`（不进 git）：

- `report.md`：部署报告（版本、地址、根证书指纹、各步骤结果与用时、冒烟结果），终端里也会打印；
- `caddy-root.crt`：导出的根证书；`release`：当前运行的版本；
- `smoke-report/`：Playwright 报告（`html/index.html`、`results.json`，失败时另有截图与 trace）。

其他命令：

| 命令 | 作用 |
|---|---|
| `pnpm staging smoke` | 只对当前运行的版本重跑「内网 HTTPS」与冒烟 |
| `pnpm staging cert` | 导出根证书并显示 SHA-256 指纹（发给员工安装） |
| `pnpm staging compose <参数>` | 带上项目名、Compose 文件、环境文件与当前版本执行 `docker compose`，例如 `pnpm staging compose logs -f api` |
| `pnpm staging down` | 停止并删除容器（保留数据卷） |
| `pnpm staging reset-inbound` | 对当前部署的版本重放来信：停 worker → 清空收信与工单 → 起 worker，按当前口径重新回放示例来信（见第 9 节「重放来信」；生产环境拒绝） |
| `pnpm deploy:staging --reset-inbound` | 部署并重放来信：灌示例数据之后、起服务之前清空收信与工单，冒烟在按新口径回放的数据上跑（识别或归并口径变了的版本用它部署） |
| `pnpm staging import-aftersales <登记表> [--mapping <映射表>] [--dry-run]` | 用当前部署的版本导入售后登记表（见第 10 节；`--dry-run` 只报告不写库；生产环境也用） |

`pnpm staging …` 等同于 `node deploy/deploy.mjs staging …`。脚本调用 Compose 时，会把环境文件里写了的变量从子进程环境里去掉：Compose 让 shell 环境变量优先于环境文件，不去掉的话，本机或运行器上设的 `HTTPS_PROXY` 之类会悄悄盖过环境文件。

## 3 本机用浏览器访问

本机没有内网 DNS，需要让 `support-dev.forcome.internal`（模板里的占位域名，`.internal` 是保留给内网用的顶级域）解析到 127.0.0.1，二选一：

- 在 hosts 文件（Windows：`C:\Windows\System32\drivers\etc\hosts`，需要管理员权限）加一行 `127.0.0.1 support-dev.forcome.internal`；
- 不改系统时，用启动参数临时启动 Chrome 或 Edge：`--host-resolver-rules="MAP support-dev.forcome.internal 127.0.0.1"`。

再按第 4 节安装根证书，打开 `https://support-dev.forcome.internal:4510/`，在开发登录页选一位示例成员。部署脚本与冒烟都不依赖 hosts 文件。

## 4 内网 HTTPS 与根证书

**现在**：caddy 用内部 CA（`tls internal`）签发证书。根证书（「Forcome Support Internal Root CA」，有效期 10 年）与私钥存在 `caddy_data` 卷的 `/data/caddy/pki/authorities/local/`；中间证书与网站证书由 caddy 自动续期（网站证书 12 小时）。会话 Cookie 一直带 `Secure`。每套环境有自己的 `caddy_data` 卷，也就有自己的根证书。

- **不要删 `caddy_data` 卷**：删了根证书就变了，所有员工要重新安装。迁移服务器时连同这个卷一起迁移（或备份 `/data/caddy/pki`）。
- **导出与核对**：`pnpm staging cert` 导出到 `deploy/.state/staging/caddy-root.crt` 并显示 SHA-256 指纹；发给员工时附上指纹，安装前比对。命令行核对：

  ```bash
  curl --cacert caddy-root.crt https://support-dev.forcome.internal:4510/api/health
  # Windows 自带的 curl 走 schannel，要加 --ssl-no-revoke（内部 CA 没有吊销列表）
  ```

- **员工浏览器安装根证书**：
  - Windows（Chrome、Edge 用系统证书库）：双击 `caddy-root.crt` →「安装证书」→ 存储位置选「当前用户」→「将所有的证书都放入下列存储」→「受信任的根证书颁发机构」。批量下发用组策略：计算机配置 → Windows 设置 → 安全设置 → 公钥策略 → 受信任的根证书颁发机构 → 导入。
  - macOS：钥匙串访问 →「系统」钥匙串 → 导入 → 双击该证书 →「信任」→「使用此证书时」选「始终信任」。
  - Firefox（有自己的证书库）：设置 → 隐私与安全 → 证书 → 查看证书 → 证书颁发机构 → 导入，勾选「信任由此证书颁发机构来标识网站」；或在 `about:config` 把 `security.enterprise_roots.enabled` 设为 `true`，改读系统证书库。
- **以后切到 DNS-01**（公司域名与 DNS 服务商的 API 令牌到位后）：
  1. 定内网子域名（如 `support-dev.<公司域名>`），内网 DNS 加 A 记录指向服务器内网地址；公网 DNS 区不需要 A 记录，只需要令牌能写 `_acme-challenge` 的 TXT 记录。
  2. `deploy/web/Dockerfile` 加一个构建阶段，用 `caddy:2.11-builder` 的 `xcaddy build --with github.com/caddy-dns/<服务商>` 编出带 DNS 插件的 caddy，最终阶段用它替换 `/usr/bin/caddy`。
  3. `deploy/web/Caddyfile` 加片段 `(tls_dns) { tls { dns <服务商> {env.DNS_API_TOKEN} } }`，全局选项加 `email <运维邮箱>`；`deploy/lib/env-file.mjs` 的 `TLS_MODES` 加 `dns`。
  4. `deploy/compose.yml` 给 caddy 传 `DNS_API_TOKEN` 与代理变量（caddy 要访问 Let's Encrypt 与 DNS 服务商的 API；`NO_PROXY` 必须含 `api`，否则转给 api 的请求也会走代理）。
  5. 环境文件改 `SITE_HOST`、`TLS_MODE=dns`，加 `DNS_API_TOKEN`。
  6. 部署脚本的「内网 HTTPS」与冒烟现在按内部 CA 写（导出根证书、只信任它），切换时一并改为使用系统证书库（Let's Encrypt 默认受信）。
  7. 员工浏览器里的内部根证书可以删掉。

## 5 外部客户端与发信白名单

- **默认全部 Fake**：开发测试环境 `APP_ENV=staging`、不设 `CLIENT_MODE_<系统>`，全局外部客户端（钉钉、汇率）都用 Fake；店铺级客户端（Gmail、订单）按店铺配置的「数据来源」选择（P18，07 号待办）。api 与 worker 启动时，各 Fake 从示例数据夹具装入数据：worker 的 Fake Gmail 回放示例来信，在邮箱开始监听后送达，几秒后归并成 P04 里的「待回复」工单（待办 08；重复部署按 Gmail 消息 ID 去重，不会多出工单）。Gmail 的推送是环境级的全局客户端，按 `CLIENT_MODE_GMAIL_PUSH` 选择（不设时开发测试环境为 Fake）。P18 的 Gmail 卡与店铺表「状态」按每个邮箱的同步记录（待办 09）：worker 启动时与之后每 5 分钟给每个邮箱同步一次，所以部署后几秒内为「已连接」，超过 10 分钟没同步成功为「同步延迟」，连续 3 次失败为「连接异常」（全站红色横幅，管理员与客服主管收到通知）。连真实 Gmail 的配置与切换见第 12 节。Shopify 订单（待办 11）：店铺的「数据来源」为模拟数据时，worker 的 Fake Shopify 从示例数据回放第一阶段工单与台账引用的 5 笔订单（`#0991`、`#1049`、`#1052`、`#1057`、`#1063`），worker 启动时与之后每分钟给每个 Shopify 店铺增量同步一次，P18 的 Shopify 卡几秒内为「已连接」；回放的订单是历史订单，增量拉不到，来信提到它们时按订单名补拉（待办 14 起），90 天回补随待办 13。连真实 Shopify 的配置与切换见第 13 节。外部接口开通后，各集成的待办会在 `deploy/compose.yml` 与 `deploy/.env.example` 加上凭据与 `CLIENT_MODE_<系统>=real`，逐个切换。钉钉（待办 05）：开发测试环境默认 Fake，worker 的 Fake 钉钉从示例数据回放通讯录（示例成员与两家生产厂负责人），启动时对账一次、之后每个整点一次，P18 钉钉卡随之为「已连接」；登录页 `/login` 画示意二维码，开发登录照常。钉钉开放平台的配置、凭据与切换步骤见第 11 节。
- **汇率**（待办 20）：全局客户端 `exchange_rate`，开发测试环境用 Fake——worker 启动时同步一次，Fake 从 2025-01-01 起每个工作日都是演示汇率（1 USD = 18.00 MXN、1.36 CAD），之后每天北京时间 06:00 再同步；生产环境默认真实现，经出站代理读欧洲央行，取不到时改用 Frankfurter，两者都不需要凭据。生产库第一次同步会装入欧洲央行 1999 年起的全量历史（约 8 MB 的 XML，历史导入也能按原日期折算）。开发测试环境要改用真实来源时，在 `deploy/compose.yml` 的 `x-app` 环境里加 `CLIENT_MODE_EXCHANGE_RATE: real`（并配好代理）；只改环境文件不生效，因为 Compose 只传登记过的变量。
- **发信白名单**：`MAIL_SEND_ALLOWLIST_ONLY`（模板里留空，按环境取默认：非生产环境为 `true`、生产为 `false`）打开时，只能向 `MAIL_SEND_ALLOWLIST` 里的地址发信（逗号分隔的完整地址或 `@域名`；`@域名` 不含子域名；白名单为空即一封也不发）。会发信的真实现（第二期的 Gmail 发信）发出前必须经 `integration` 的 `MailRecipientGuard` 检查；第一期不发信。api 与 worker 的启动日志带 `mailSendAllowlistOnly`，可以在 `pnpm staging compose logs api` 里核对。

## 6 出站代理与运维清单

### 6.1 代理变量

环境文件里的 `HTTPS_PROXY`、`HTTP_PROXY`、`NO_PROXY` 传给 api 与 worker（Compose 同时给出小写写法，免得 Docker 客户端注入的代理变量盖过环境文件），启动时校验代理地址格式（必须是 `http://` 或 `https://` 开头）。外部调用经 HTTP 客户端工厂（undici `EnvHttpProxyAgent`，随第一个真实现加入）按这组变量走代理或直连（ADR 0003）。

现在没有可用的代理：变量留空，没有实测经代理出站。代理到位后填上 `HTTPS_PROXY`（和 `HTTP_PROXY`），重新部署即可。

### 6.3 `NO_PROXY` 清单（直连，不经代理）

```
localhost,127.0.0.1,postgres,api,caddy,.dingtalk.com
```

- `postgres`、`api`、`caddy` 是 Compose 网络里的服务名，内部调用不能走代理。
- 境内服务从公司固定 IP 直连：第一期钉钉 `.dingtalk.com`（`api.dingtalk.com`、`oapi.dingtalk.com`、`login.dingtalk.com` 与 Stream 长连接；Stream 的 WebSocket 经同一个出站连接，同样按 `NO_PROXY` 直连）；员工浏览器另要能直接访问 `login.dingtalk.com` 与 `g.alicdn.com`（扫码登录框，第 11 节）；第二期加积加 `.gerpgo.com` 与易仓的 OMS 域名（待 FSH 提供）；NewAPI 若部署在境内也加进来。
- 域名一律写成带前导点的形式：undici、curl、Go 都把 `.example.com` 当作「这个域名的子域名」匹配，不带点的写法各家规则不一。

### 6.4 内网 DNS 与网络

- A 记录：开发测试 `support-dev.<公司域名>` → 服务器内网地址；生产 `support.<公司域名>`（28 号待办）。现在本机测试用占位域名 `support-dev.forcome.internal`。
- 访问端口：开发测试 4510。若要用 443，生产与开发测试同机时需要分到不同的内网地址，或在前面再放一层反向代理（28 号待办定）。
- 服务器防火墙只对内网放行 HTTPS 端口；PostgreSQL 端口只开在 127.0.0.1。
- 服务器要能解析境内直连的域名（钉钉等）；境外域名由代理解析。

## 7 迁移到 Linux 服务器

部署脚本与 Compose 不含 Windows 路径，原样可用。

1. 安装 Docker Engine 与 compose 插件、git、Node 22 以上；按 6.2 配好 Docker 的代理或镜像源。
2. 建部署用的系统用户（上 GitHub 后就是运行器用户，见第 8 节），取代码：`git clone <仓库> /opt/forcome/support`。
3. 环境文件放在工作区以外，例如 `/etc/forcome/staging.env`：按 `deploy/.env.example` 填写——`APP_ENV=staging`；`SITE_HOST` 为真实内网域名；`HTTPS_BIND=0.0.0.0`（或内网网卡地址）；`POSTGRES_PASSWORD` 用 `openssl rand -hex 24` 生成；代理变量。`chmod 600`，属主为部署用户。
4. 部署：`FORCOME_ENV_FILE=/etc/forcome/staging.env node deploy/deploy.mjs staging`。
5. 配内网 DNS 与防火墙（6.4），把 `pnpm staging cert`（或 `node deploy/deploy.mjs staging cert`）导出的根证书按第 4 节发给员工安装。
6. 本机的开发测试数据不用迁：示例数据由 seed 重建。只有想沿用本机的根证书时，才把 `caddy_data` 卷打包迁过去。
7. 用 rootless Docker 时（第 8 节推荐），默认的端口转发拿不到客户端真实地址，审计的来源 IP 会变成内部地址；设 `DOCKERD_ROOTLESS_ROOTLESSKIT_PORT_DRIVER=slirp4netns` 保留客户端地址。

## 8 上 GitHub 后启用自动部署

工作流 `.github/workflows/deploy-staging.yml` 已写好并经 actionlint 校验：main 上的 CI（云端运行器）通过后，在开发测试运行器上执行同一个部署脚本，部署报告写进作业摘要，`deploy/.state/staging/`（含冒烟报告）作为产物上传。PR 的 CI 不触发部署。启用步骤：

1. 仓库推到 GitHub 私有仓库，按 README「开发」设分支保护（必需检查「CI 通过」、至少 1 个批准）。
2. 在服务器上建系统用户（如 `gh-staging`，不进 docker 组、没有 sudo），为它安装 rootless Docker（`dockerd-rootless-setuptool.sh install`，并 `loginctl enable-linger gh-staging`）。这个用户只能操作自己 Docker 里的开发测试 Compose 项目，碰不到生产；生产运行器用另一个用户与标签（28 号待办）。
3. 在 GitHub 仓库 Settings → Actions → Runners → New self-hosted runner 取得注册命令，以该用户执行 `./config.sh --url <仓库地址> --token <令牌> --labels forcome-staging --unattended`；在运行器目录的 `.env` 写 `DOCKER_HOST=unix:///run/user/<uid>/docker.sock` 与运行器连 GitHub 用的代理变量；`sudo ./svc.sh install gh-staging && sudo ./svc.sh start`。
4. 环境文件 `/etc/forcome/staging.env`（第 7 节第 3 步），属主改为 `gh-staging`，权限 600。
5. Settings → Environments 新建 `staging`（可限制只允许 main 部署）。
6. 合并一个 PR 到 main，确认 CI 通过后部署工作流运行，作业摘要里是部署报告，冒烟通过。

本机命令照样可用，用于排查。

## 9 排查

- 日志：`pnpm staging compose logs -f api`（worker、caddy、postgres 同理）。
- 重跑 HTTPS 核对与冒烟：`pnpm staging smoke`；看报告：`pnpm --filter @forcome/web exec playwright show-report ../../deploy/.state/staging/smoke-report/html`。
- 端口被占用：改环境文件的 `HTTPS_PORT`、`PG_PORT`（本机在 4510–4520 之内）。
- 迁移失败：报告里「执行迁移」失败，api 与 worker 仍是上一版本；修好后重新部署（迁移只向前，ADR 0013）。
- 连数据库：`psql -h 127.0.0.1 -p 4511 -U forcome forcome`（口令在环境文件里）。
- 停止：`pnpm staging down`（保留数据卷）。`pnpm staging compose down -v` 会连数据库与根证书一起删掉，慎用。
- **重放来信**（待办 10 起，ADR 0013 修订）：来源、渠道、站点的识别或归并口径改了以后，已入库的示例来信不会回头重新识别，P04 上还是旧口径的工单。这样的版本用 `pnpm deploy:staging --reset-inbound` 部署：灌示例数据之后多一步「重放来信」——停 worker，用本次构建的镜像清掉收取的邮件、各邮箱的增量游标、工单与客户，工单编号从 0001 重新发号；随后起服务，worker 重新 watch 各邮箱，Fake Gmail 按新口径重新回放示例来信，几十秒内重新归并成工单，冒烟在新数据上跑。已部署的版本要重放时执行 `pnpm staging reset-inbound`（停 worker → 清空 → 起 worker），再 `pnpm staging smoke` 核对。成员、店铺、来源规则、会话、审计与根证书都不动。只用于非生产环境：部署脚本、镜像入口与清理函数三处都拒绝生产环境。本机开发库同理：先停 `dev:worker`，执行 `pnpm db:reset-inbound`，再启动 `dev:worker`。
- 旧版本镜像不会自动删除（每次部署多一个 `forcome-server`、`forcome-web`、`forcome-smoke`），定期用 `docker image ls "forcome-*"` 查看后删掉不再用的版本；自动清理与日志轮转随 28 号待办。

## 10 售后登记表导入（上线前一次性）

客户现有的售后登记表一次性导入台账（PRD 第 14 节，待办 27，不用模型）：每行成为一张创建路径「历史导入」的售后单，编号 `S-原登记日期-全局序号`，金额按原表的费用发生日（没有时取原登记日期）的汇率折算美元；缺的字段留空，台账照常标「待回填」「缺 N 项」、售后负责人可补登，但不计当月登记完整率。原表没有币种的行按美元导入，与「原表没有费用发生日，取原登记日期」一起记在导入记录里、写进导入报告（P13 不另加标识）。每张导入的单在 P27 有一条「历史导入」（操作人「系统」）。

- **映射表**：`apps/server/src/modules/aftersales/history-mapping.json`，随镜像打包，格式见同目录的 `history-mapping.ts`——`columns` 写原表的列名（表头比较不看空白与大小写），`values` 写原表的写法对应的取值（店铺写店铺名、生产厂写代码、负责人写成员姓名，固定取值写中文叫法），`defaults.status` 是原表没写状态时的状态，`rowKey` 是能唯一认出一行的列（重跑据此跳过已导入的行），`headerRow`、`sheet` 是表头所在行与工作表。现在按合成样本（`apps/server/test/fixtures/history-import/register-sample.xlsx`）写；**拿到客户的真实登记表后只改这个文件**，不改代码（待办 32 上线前事项）。临时换一份可用 `--mapping`。
- **表格**：`.xlsx`，或另存为「CSV UTF-8」的 `.csv`（Excel 默认另存的 ANSI / GBK 会报错）。
- **步骤**：
  1. 改好映射表，提交并部署到开发测试环境（`pnpm deploy:staging`）。
  2. 试运行：`pnpm staging import-aftersales <登记表> --dry-run`。报告逐行写「将导入 S-…」与标注、「缺：…」、「注意：…」（如负责人对不上已留空），以及「未导入 · …」的原因；认不出的取值在映射表 `values` 里加别名，或改正原表，再试运行，直到报告无误。映射表里的列在表头里找不到时整体报错，一行也不导入。
  3. 正式导入：去掉 `--dry-run` 再执行一次；在 P13 把费用发生日筛到历史月份核对条数与金额。重跑是幂等的：已导入的行跳过（报告写当时的单号），改好的行补导。
  4. 生产环境：同一版本、同一份映射表与表格再执行一次。生产环境随 28 号待办加入部署脚本（之后是 `node deploy/deploy.mjs production import-aftersales …`）；在那之前在生产机上执行 `docker compose -p <生产项目> -f deploy/compose.yml --env-file <生产环境文件> run --rm --no-deps -v <登记表的绝对路径>:/import/<文件名>:ro migrate node dist/import-aftersales.mjs /import/<文件名> --dry-run`，去掉 `--dry-run` 正式导入。
- **汇率**：从库里的汇率表按日期取（当天没有取此前最近一个有汇率的日期）。生产库由 worker 第一次同步装入欧洲央行 1999 年起的全量历史；还没同步完时，外币的行报「费用发生日及之前没有汇率」、不导入，等同步完重跑即可。
- **本机开发库**：`pnpm --filter @forcome/server import:aftersales <登记表> --dry-run`（相对路径从 `apps/server` 算，先 `pnpm db:migrate`）。
- 退出码：全部导入（或跳过）为 0，有未导入的行为 1（其余行照常导入）。
- **导入期间新建登记要等**：一次导入（含试运行）在一个事务里，期间 P13 的「新建登记」保存会等导入结束才拿到单号（几千行约几秒）。正式导入安排在上线前或无人登记的时段（ADR 0006 修订）。

注意事项：

- **watch 与订阅的对应**：每个邮箱的 `watch` 只能推到一个主题；几个环境同时连同一批真实邮箱时，推送会被后一个 `watch` 改走，另一个环境靠每 5 分钟的兜底仍能收全，只是慢一点。所以真实邮箱只让一个环境连（生产），开发测试环境用 Gmail 测试邮箱（规格 User Story 98）。
- **只读范围**：全域委派只给 `gmail.readonly`；换令牌时若返回 `unauthorized_client`，多半是委派的范围或客户端 ID 填错，P18 Gmail 卡会在连续 3 次失败后显示「访问失败……请检查全域委派范围与邮箱状态」。
- **出站**：`oauth2.googleapis.com`、`gmail.googleapis.com`、`pubsub.googleapis.com` 经代理（第 6.2 节已列）。

### 12.2 切换到真实 Gmail

只在生产环境，或专门联调用的环境（用 Gmail 测试邮箱）切换；共用的开发测试环境（`forcome-staging`）默认保持 Fake。

1. 完成 12.1 的配置。
2. 把 JSON 密钥放到服务器上工作区以外的目录（权限 600，不进 git），环境文件里填：`GOOGLE_KEY_DIR=<该目录>`（只读挂进容器的 `/run/forcome-keys`）、`GOOGLE_SERVICE_ACCOUNT_KEY_FILE=/run/forcome-keys/<文件名>.json`、`GMAIL_PUBSUB_TOPIC`、`GMAIL_PUBSUB_SUBSCRIPTION`（本环境的订阅）。三项要么都填、要么都不填：只填一部分时 api 与 worker 拒绝启动并列出缺的变量名，密钥文件读不到或不是服务账号密钥同样拒绝（不回显密钥）；三项都不填时照常启动（生产环境也一样，Google 资质到位前就这样上线），P18 的 Gmail 与各店铺为「未连接」，不出横幅、不发通知。非生产环境另填 `CLIENT_MODE_GMAIL_PUSH=real`。
3. 店铺邮箱按店铺选择：生产环境的店铺都是真实接口；非生产环境在 P18 把要联调的店铺「数据来源」改为「真实接口」（其余店铺仍是模拟数据，推送只能二选一，另一类靠每 5 分钟的兜底）。
4. 部署（开发测试 `pnpm deploy:staging`；生产随 28 号待办）。
5. 核对：
   - worker 日志有「拿到独占持有权，开始拉取」（Gmail 推送独占，多个 worker 时只有一个拉）、每个邮箱「邮箱已开始监听」；
   - P18 的 Gmail 卡几秒内为「已连接」并写最近同步时间（取各邮箱中最旧的一次）；点「测试连接」浮层「连接正常 · Gmail：4 个邮箱均可访问」（测试不改状态，测完立即同步一次）；
   - 给一个店铺邮箱发一封测试信，几秒后在 P04 归并成工单；从该邮箱回一封，「已发送」也入库（方向为我方，回复识别随待办 16）；
   - 调用记录：`pnpm staging compose exec postgres psql -U forcome -d forcome -c "select started_at, system, operation, outcome, status from integration.call_record order by started_at desc limit 20"`（每次外部调用一行：系统、动作、店铺、耗时、状态码、请求与响应摘要；访问令牌不入库）。
   完整的真实环境验收（推送到达、游标过期补拉、断线恢复）见待办 29。

### 12.3 连接异常与恢复

- 某个邮箱的 `watch`、续订或同步连续 3 次失败：P18 Gmail 卡转「连接异常」并列出该邮箱与恢复指引，店铺表该店铺的状态为「Gmail 连接异常」，全站顶部出现红色横幅（不可关闭；管理员另有「查看渠道状态」），管理员与客服主管收到站内通知「Gmail 连接异常」与钉钉工作通知，P27 记「连接异常」（操作人系统）。来信留在 Gmail 里，不会丢。
- 处理：按卡上的指引检查全域委派的范围与客户端 ID、邮箱是否停用或改名、密钥是否被删除；改好后点卡底「重新检测」（立即重测并同步），或等下一次自动同步（每 5 分钟）。同步成功即恢复：断开期间的来信自动补拉，横幅消失，管理员与客服主管收到「Gmail 已恢复 · 补拉 N 封来信」，P27 记「恢复连接」。
- 超过 10 分钟没同步成功（还没连续 3 次失败）显示「同步延迟」，只在卡上与店铺表显示，不出横幅；我们自己的错误（例如一封解析不了的邮件）不算连接失败，但会让该邮箱停在这封之前、显示同步延迟，查 worker 日志。

## 13 Shopify 订单：自建应用与主密钥（待办 11）

Shopify 店铺的订单经 **Admin GraphQL API** 准实时读进本地订单镜像（ADR 0011）：worker 每分钟按平台更新时间（`updated_at`）给每个 Shopify 店铺增量拉一次，新增或编辑店铺后立即拉一次；来信里提到的订单名（如 `#1063`）镜像里没有时按订单名补拉，Shopify 来信按客户邮箱在本店铺内反查订单（待办 14 起用）。访问令牌由 Shopify 自建应用的**客户端凭据**按店铺换取（client credentials，24 小时过期），系统每 20 小时提前换新，令牌用主密钥加密存进数据库（`integration.credential`，库里没有明文）。全部是主动连出，不需要公网回调（ADR 0003）。开发与测试一律用 Fake：开发测试环境的店铺默认模拟数据，生产环境的店铺都是真实接口。上线前的 90 天回补与每天夜间对账随待办 13。

### 13.1 在 Shopify 侧要做的配置（上线前，Shopify 组织的管理员完成）

| 项 | 在哪里配 | 怎么配 | 用途 |
|---|---|---|---|
| 组织与店铺 | Shopify Dev Dashboard（dev.shopify.com） | 两个 Shopify 店铺（forcome.com、forcome.mx）都在同一个 Shopify 组织里 | client credentials 只对与应用同一组织的店铺有效 |
| 自建应用 | Dev Dashboard →「Apps」→ 新建应用（例 `forcome-support`） | 访问范围：`read_orders`、`read_customers`（第一期只读；第二期退款、改地址、取消再加写权限）；61–90 天的历史订单另申请 `read_all_orders`（回补随 13，拿不到时回补 60 天、报表注明） | 读订单、客户邮箱、收件地址、履约单号 |
| 受保护客户数据 | 应用的「API access」→「Protected customer data access」 | 申请邮箱、姓名、地址字段（第一期用邮箱反查订单、用收件国家定站点） | 不申请时订单的邮箱与地址为空 |
| 安装到店铺 | 应用的「Distribution / Install」 | 安装到两个店铺 | 换令牌时店铺要已安装该应用 |
| 客户端凭据 | 应用的「Settings」→「Credentials」 | 记下 Client ID 与 Client secret | 填进环境文件（13.2） |
| 店铺域名 | P18「编辑店铺」 | 平台标识填 `<名字>.myshopify.com`（不是自定义域名） | 按它连店铺；填错时连续 3 次失败转连接异常 |

注意事项：

- **出站**：各店铺的 `<店铺>.myshopify.com` 经代理（第 6.2 节已列）；换令牌（`/admin/oauth/access_token`）与订单查询（`/admin/api/2026-07/graphql.json`）都是这个域名。
- **API 版本**：代码里固定 `2026-07`（`integration/shopify-real.ts` 的 `SHOPIFY_API_VERSION`），Shopify 每个版本至少支持 12 个月，升级时改常量并对照官方变更说明。
- **限流**：Admin GraphQL 按查询成本限流，超了返回 `THROTTLED`，算一次失败，下一分钟再拉；每分钟一次的增量远低于上限。

### 13.2 切换到真实 Shopify

只在生产环境，或专门联调用的环境切换；共用的开发测试环境（`forcome-staging`）默认保持模拟数据。

### 13.3 连接异常与恢复

- 某个店铺的订单同步连续 3 次失败（每分钟一次，约 3 分钟）：P18 Shopify 卡转「连接异常」并列出该店铺与恢复指引，店铺表该店铺的状态为「Admin API 连接异常」，全站顶部出现红色横幅「Shopify 订单同步中断」（不可关闭；管理员另有「查看渠道状态」；与 Gmail 同时异常时各一条），管理员与客服主管收到站内通知「Shopify 连接异常」与钉钉工作通知，P27 记「连接异常」（操作人系统，对象「Shopify · 店铺」）。来信照常收取，只是订单暂时对不上。

- 超过 10 分钟没同步成功（还没连续 3 次失败）显示「同步延迟」，只在卡上与店铺表显示，不出横幅；我们自己的错误（例如写镜像出错）不算连接失败，但水位不前进、显示同步延迟，查 worker 日志。
