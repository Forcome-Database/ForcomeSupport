# 部署说明

适用于**开发测试环境**（待办 03）。生产环境的部署、备份、监控与日志轮转随 28 号待办补进本文。

依据：ADR 0003、0013 及其修订；用户 2026-10-04 口径——服务器与 GitHub 暂未就绪，**先在本机用 Docker 部署与测试**，部署脚本与 Compose 原样搬到 Linux 服务器；内网 HTTPS 先用 caddy 内部 CA（`tls internal`），公司域名与 DNS-01 到位后切换；外部服务只有钉钉企业内部应用已有，开发测试环境默认全部用 Fake。

## 1 组成

一份 Compose（`deploy/compose.yml`）给开发测试与生产两套环境共用，由部署脚本按环境固定项目名：开发测试 `forcome-staging`，生产 `forcome-production`（28 号待办）。容器、数据卷、网络都以项目名为前缀，两套环境互不影响。

| 服务 | 镜像 | 作用 |
|---|---|---|
| caddy | `forcome-web:<版本>` | 内网 HTTPS、托管前端静态文件、把 `/api` 转给 api（`deploy/web/Dockerfile` 的 web 目标与 `Caddyfile`） |
| api | `forcome-server:<版本>` | HTTP 接口 |
| worker | `forcome-server:<版本>` | 后台任务 |
| migrate | `forcome-server:<版本>` | 一次性：只向前执行迁移，先于 api 与 worker |
| seed | `forcome-server:<版本>` | 一次性、只用于非生产：灌示例数据夹具（各加载步骤幂等） |
| postgres | `forcome-postgres:18` | 自建 PostgreSQL 18 镜像（`deploy/postgres/`；WAL-G 随 28 号待办） |
| smoke | `forcome-smoke:<版本>` | 一次性：部署后的 Playwright 冒烟（`deploy/web/Dockerfile` 的 smoke 目标，入口 `deploy/smoke/run-smoke.sh`） |

- **版本**：git 提交号（12 位）；工作区有未提交的改动时加 `-dirty`（只会出现在本机）。
- **数据卷**：`pgdata`（数据库）、`caddy_data`（内部 CA 的根证书与私钥，**不要删**，见第 4 节）、`caddy_config`。
- **端口**（本期本机可用 4510–4520）：

| 端口 | 用途 |
|---|---|
| 4510 | 开发测试环境 HTTPS（`HTTPS_BIND`，本机默认只开在 127.0.0.1） |
| 4511 | 开发测试环境 PostgreSQL（只开在 127.0.0.1，供 `psql` 排查） |
| 4512–4513 | 预留给生产环境（28 号待办） |
| 4514–4515 | 机动 |
| 4516–4520 | 本机开发（见 README「开发」） |

## 2 部署（现在：在本机执行）

前提：Docker（含 compose v2）、git、Node 22 以上。部署脚本只用 Node 自带的模块，不需要 `pnpm install`。

```bash
pnpm deploy:staging            # 等同于 node deploy/deploy.mjs staging
```

第一次运行时，脚本从 `deploy/.env.example` 生成 `deploy/.env.staging`（随机数据库口令，不进 git），以后改这个文件调整配置。各变量的含义写在模板里。

脚本依次执行下列步骤，任一步失败，之后的步骤不再执行、退出码为 1：

| 步骤 | 做什么 |
|---|---|
| 准备 | 读取并校验环境文件（APP_ENV 必须与环境相符、域名、端口、口令格式）；版本取当前提交号 |
| 构建镜像 | `postgres`、`migrate`（后端镜像）、`caddy`（前端镜像）、`smoke` |
| 启动数据库 | 等到 PostgreSQL 健康 |
| 执行迁移 | 单独运行 `migrate`；失败即停，api 与 worker 仍是上一版本 |
| 灌示例数据 | 单独运行 `seed`（只用于非生产；已有的数据跳过，不会重复） |
| 启动 api、worker、caddy | 等到健康，并核对三者运行的都是本次构建的镜像 |
| 内网 HTTPS | 导出 caddy 的根证书，只用它核对证书链与域名，再经 HTTPS 取 `/api/health` 与首页 |
| 冒烟 | 在一次性容器里只信任该根证书，经 Compose 网络按内网域名访问，跑 `apps/web/e2e` 的全部 Playwright 用例（现在是开发登录 → 看到顶栏，HTTPS 下会话 Cookie 带 `Secure`） |

失败时不回滚：开发测试环境停在失败处，方便排查。产物在 `deploy/.state/staging/`（不进 git）：

- `report.md`：部署报告（版本、地址、根证书指纹、各步骤结果与用时、冒烟结果），终端里也会打印；
- `caddy-root.crt`：导出的根证书；`release`：当前运行的版本；
- `smoke-report/`：Playwright 报告（`html/index.html`、`results.json`，失败时另有截图与 trace）。

其他命令：

| 命令 | 作用 |
|---|---|
| `pnpm staging smoke` | 只对当前运行的版本重跑「内网 HTTPS」与冒烟 |
| `pnpm staging cert` | 导出根证书并显示 SHA-256 指纹（发给员工安装） |
| `pnpm staging compose <参数>` | 带上项目名、Compose 文件、环境文件与当前版本执行 `docker compose`，例如 `pnpm staging compose logs -f api` |
| `pnpm staging down` | 停止并删除容器（保留数据卷） |

`pnpm staging …` 等同于 `node deploy/deploy.mjs staging …`。脚本调用 Compose 时，会把环境文件里写了的变量从子进程环境里去掉：Compose 让 shell 环境变量优先于环境文件，不去掉的话，本机或运行器上设的 `HTTPS_PROXY` 之类会悄悄盖过环境文件。

## 3 本机用浏览器访问

本机没有内网 DNS，需要让 `support-dev.forcome.internal`（模板里的占位域名，`.internal` 是保留给内网用的顶级域）解析到 127.0.0.1，二选一：

- 在 hosts 文件（Windows：`C:\Windows\System32\drivers\etc\hosts`，需要管理员权限）加一行 `127.0.0.1 support-dev.forcome.internal`；
- 不改系统时，用启动参数临时启动 Chrome 或 Edge：`--host-resolver-rules="MAP support-dev.forcome.internal 127.0.0.1"`。

再按第 4 节安装根证书，打开 `https://support-dev.forcome.internal:4510/`，在开发登录页选一位示例成员。部署脚本与冒烟都不依赖 hosts 文件。

## 4 内网 HTTPS 与根证书

**现在**：caddy 用内部 CA（`tls internal`）签发证书。根证书（「Forcome Support Internal Root CA」，有效期 10 年）与私钥存在 `caddy_data` 卷的 `/data/caddy/pki/authorities/local/`；中间证书与网站证书由 caddy 自动续期（网站证书 12 小时）。会话 Cookie 一直带 `Secure`。每套环境有自己的 `caddy_data` 卷，也就有自己的根证书。

- **不要删 `caddy_data` 卷**：删了根证书就变了，所有员工要重新安装。迁移服务器时连同这个卷一起迁移（或备份 `/data/caddy/pki`）。
- **导出与核对**：`pnpm staging cert` 导出到 `deploy/.state/staging/caddy-root.crt` 并显示 SHA-256 指纹；发给员工时附上指纹，安装前比对。命令行核对：

  ```bash
  curl --cacert caddy-root.crt https://support-dev.forcome.internal:4510/api/health
  # Windows 自带的 curl 走 schannel，要加 --ssl-no-revoke（内部 CA 没有吊销列表）
  ```

- **员工浏览器安装根证书**：
  - Windows（Chrome、Edge 用系统证书库）：双击 `caddy-root.crt` →「安装证书」→ 存储位置选「当前用户」→「将所有的证书都放入下列存储」→「受信任的根证书颁发机构」。批量下发用组策略：计算机配置 → Windows 设置 → 安全设置 → 公钥策略 → 受信任的根证书颁发机构 → 导入。
  - macOS：钥匙串访问 →「系统」钥匙串 → 导入 → 双击该证书 →「信任」→「使用此证书时」选「始终信任」。
  - Firefox（有自己的证书库）：设置 → 隐私与安全 → 证书 → 查看证书 → 证书颁发机构 → 导入，勾选「信任由此证书颁发机构来标识网站」；或在 `about:config` 把 `security.enterprise_roots.enabled` 设为 `true`，改读系统证书库。
- **以后切到 DNS-01**（公司域名与 DNS 服务商的 API 令牌到位后）：
  1. 定内网子域名（如 `support-dev.<公司域名>`），内网 DNS 加 A 记录指向服务器内网地址；公网 DNS 区不需要 A 记录，只需要令牌能写 `_acme-challenge` 的 TXT 记录。
  2. `deploy/web/Dockerfile` 加一个构建阶段，用 `caddy:2.11-builder` 的 `xcaddy build --with github.com/caddy-dns/<服务商>` 编出带 DNS 插件的 caddy，最终阶段用它替换 `/usr/bin/caddy`。
  3. `deploy/web/Caddyfile` 加片段 `(tls_dns) { tls { dns <服务商> {env.DNS_API_TOKEN} } }`，全局选项加 `email <运维邮箱>`；`deploy/lib/env-file.mjs` 的 `TLS_MODES` 加 `dns`。
  4. `deploy/compose.yml` 给 caddy 传 `DNS_API_TOKEN` 与代理变量（caddy 要访问 Let's Encrypt 与 DNS 服务商的 API；`NO_PROXY` 必须含 `api`，否则转给 api 的请求也会走代理）。
  5. 环境文件改 `SITE_HOST`、`TLS_MODE=dns`，加 `DNS_API_TOKEN`。
  6. 部署脚本的「内网 HTTPS」与冒烟现在按内部 CA 写（导出根证书、只信任它），切换时一并改为使用系统证书库（Let's Encrypt 默认受信）。
  7. 员工浏览器里的内部根证书可以删掉。

## 5 外部客户端与发信白名单

- **默认全部 Fake**：开发测试环境 `APP_ENV=staging`、不设 `CLIENT_MODE_<系统>`，全局外部客户端（钉钉、汇率）都用 Fake；店铺级客户端（Gmail、订单）按店铺配置的「数据来源」选择（P18，07 号待办）。api 与 worker 启动时，各 Fake 从示例数据夹具装入数据。外部接口开通后，各集成的待办会在 `deploy/compose.yml` 与 `deploy/.env.example` 加上凭据与 `CLIENT_MODE_<系统>=real`，逐个切换；钉钉企业内部应用的凭据由用户上线时自己填进环境文件（05 号待办）。
- **发信白名单**：`MAIL_SEND_ALLOWLIST_ONLY`（模板里留空，按环境取默认：非生产环境为 `true`、生产为 `false`）打开时，只能向 `MAIL_SEND_ALLOWLIST` 里的地址发信（逗号分隔的完整地址或 `@域名`；`@域名` 不含子域名；白名单为空即一封也不发）。会发信的真实现（第二期的 Gmail 发信）发出前必须经 `integration` 的 `MailRecipientGuard` 检查；第一期不发信。api 与 worker 的启动日志带 `mailSendAllowlistOnly`，可以在 `pnpm staging compose logs api` 里核对。

## 6 出站代理与运维清单

### 6.1 代理变量

环境文件里的 `HTTPS_PROXY`、`HTTP_PROXY`、`NO_PROXY` 传给 api 与 worker（Compose 同时给出小写写法，免得 Docker 客户端注入的代理变量盖过环境文件），启动时校验代理地址格式（必须是 `http://` 或 `https://` 开头）。外部调用经 HTTP 客户端工厂（undici `EnvHttpProxyAgent`，随第一个真实现加入）按这组变量走代理或直连（ADR 0003）。

现在没有可用的代理：变量留空，没有实测经代理出站。代理到位后填上 `HTTPS_PROXY`（和 `HTTP_PROXY`），重新部署即可。

### 6.2 放行域名（交运维，在代理侧按域名放行）

运行期，经代理（境外）：

| 阶段 | 服务 | 域名 |
|---|---|---|
| 第一期 | Gmail（服务账号换令牌、收信、Pub/Sub 拉取） | `oauth2.googleapis.com`、`gmail.googleapis.com`、`pubsub.googleapis.com` |
| 第一期 | Shopify Admin API | 各店铺的 `<店铺>.myshopify.com` |
| 第一期 | 亚马逊 SP-API（北美）、LWA 令牌、SQS | `sellingpartnerapi-na.amazon.com`、`api.amazon.com`、`sqs.us-east-1.amazonaws.com` |
| 第一期 | 汇率（欧洲央行主源、Frankfurter 备用，20 号待办定稿） | `www.ecb.europa.eu`、`api.frankfurter.app` |
| 第二期 | 17TRACK | `api.17track.net` |
| 第二期 | 模型网关 NewAPI | 按网关部署位置定（境内则加进 `NO_PROXY`） |
| 切 DNS-01 后 | Let's Encrypt、DNS 服务商 API（caddy） | `acme-v02.api.letsencrypt.org`、服务商的 API 域名 |

构建与部署期（服务器上构建镜像、拉镜像；上 GitHub 后还有运行器）：

| 用途 | 域名 |
|---|---|
| Docker Hub（node、postgres、caddy 基础镜像） | `registry-1.docker.io`、`auth.docker.io`、`production.cloudflare.docker.com` |
| 微软镜像仓库（Playwright 镜像） | `mcr.microsoft.com`、`*.data.mcr.microsoft.com` |
| npm（pnpm 安装依赖、corepack 取 pnpm） | `registry.npmjs.org` |
| Ubuntu 软件源（冒烟镜像装 certutil） | `archive.ubuntu.com`、`security.ubuntu.com` |

Docker 拉镜像走 Docker 守护进程的代理设置（Linux：systemd 的 `docker.service.d/http-proxy.conf`）；构建时的 `pnpm install`、`apt-get` 走 Docker 客户端配置 `~/.docker/config.json` 的 `proxies`（它也会往容器里注入代理变量，Compose 已显式给出，以环境文件为准）。用国内镜像源代替时，相应域名换成镜像源。

### 6.3 `NO_PROXY` 清单（直连，不经代理）

```
localhost,127.0.0.1,postgres,api,caddy,.dingtalk.com
```

- `postgres`、`api`、`caddy` 是 Compose 网络里的服务名，内部调用不能走代理。
- 境内服务从公司固定 IP 直连：第一期钉钉 `.dingtalk.com`（`api.dingtalk.com`、`oapi.dingtalk.com`、`login.dingtalk.com` 与 Stream 长连接）；第二期加积加 `.gerpgo.com` 与易仓的 OMS 域名（待 FSH 提供）；NewAPI 若部署在境内也加进来。
- 域名一律写成带前导点的形式：undici、curl、Go 都把 `.example.com` 当作「这个域名的子域名」匹配，不带点的写法各家规则不一。

### 6.4 内网 DNS 与网络

- A 记录：开发测试 `support-dev.<公司域名>` → 服务器内网地址；生产 `support.<公司域名>`（28 号待办）。现在本机测试用占位域名 `support-dev.forcome.internal`。
- 访问端口：开发测试 4510。若要用 443，生产与开发测试同机时需要分到不同的内网地址，或在前面再放一层反向代理（28 号待办定）。
- 服务器防火墙只对内网放行 HTTPS 端口；PostgreSQL 端口只开在 127.0.0.1。
- 服务器要能解析境内直连的域名（钉钉等）；境外域名由代理解析。

## 7 迁移到 Linux 服务器

部署脚本与 Compose 不含 Windows 路径，原样可用。

1. 安装 Docker Engine 与 compose 插件、git、Node 22 以上；按 6.2 配好 Docker 的代理或镜像源。
2. 建部署用的系统用户（上 GitHub 后就是运行器用户，见第 8 节），取代码：`git clone <仓库> /opt/forcome/support`。
3. 环境文件放在工作区以外，例如 `/etc/forcome/staging.env`：按 `deploy/.env.example` 填写——`APP_ENV=staging`；`SITE_HOST` 为真实内网域名；`HTTPS_BIND=0.0.0.0`（或内网网卡地址）；`POSTGRES_PASSWORD` 用 `openssl rand -hex 24` 生成；代理变量。`chmod 600`，属主为部署用户。
4. 部署：`FORCOME_ENV_FILE=/etc/forcome/staging.env node deploy/deploy.mjs staging`。
5. 配内网 DNS 与防火墙（6.4），把 `pnpm staging cert`（或 `node deploy/deploy.mjs staging cert`）导出的根证书按第 4 节发给员工安装。
6. 本机的开发测试数据不用迁：示例数据由 seed 重建。只有想沿用本机的根证书时，才把 `caddy_data` 卷打包迁过去。
7. 用 rootless Docker 时（第 8 节推荐），默认的端口转发拿不到客户端真实地址，审计的来源 IP 会变成内部地址；设 `DOCKERD_ROOTLESS_ROOTLESSKIT_PORT_DRIVER=slirp4netns` 保留客户端地址。

## 8 上 GitHub 后启用自动部署

工作流 `.github/workflows/deploy-staging.yml` 已写好并经 actionlint 校验：main 上的 CI（云端运行器）通过后，在开发测试运行器上执行同一个部署脚本，部署报告写进作业摘要，`deploy/.state/staging/`（含冒烟报告）作为产物上传。PR 的 CI 不触发部署。启用步骤：

1. 仓库推到 GitHub 私有仓库，按 README「开发」设分支保护（必需检查「CI 通过」、至少 1 个批准）。
2. 在服务器上建系统用户（如 `gh-staging`，不进 docker 组、没有 sudo），为它安装 rootless Docker（`dockerd-rootless-setuptool.sh install`，并 `loginctl enable-linger gh-staging`）。这个用户只能操作自己 Docker 里的开发测试 Compose 项目，碰不到生产；生产运行器用另一个用户与标签（28 号待办）。
3. 在 GitHub 仓库 Settings → Actions → Runners → New self-hosted runner 取得注册命令，以该用户执行 `./config.sh --url <仓库地址> --token <令牌> --labels forcome-staging --unattended`；在运行器目录的 `.env` 写 `DOCKER_HOST=unix:///run/user/<uid>/docker.sock` 与运行器连 GitHub 用的代理变量；`sudo ./svc.sh install gh-staging && sudo ./svc.sh start`。
4. 环境文件 `/etc/forcome/staging.env`（第 7 节第 3 步），属主改为 `gh-staging`，权限 600。
5. Settings → Environments 新建 `staging`（可限制只允许 main 部署）。
6. 合并一个 PR 到 main，确认 CI 通过后部署工作流运行，作业摘要里是部署报告，冒烟通过。

本机命令照样可用，用于排查。

## 9 排查

- 日志：`pnpm staging compose logs -f api`（worker、caddy、postgres 同理）。
- 只重跑冒烟：`pnpm staging smoke`；看报告：`pnpm --filter @forcome/web exec playwright show-report ../../deploy/.state/staging/smoke-report/html`。
- 端口被占用：改环境文件的 `HTTPS_PORT`、`PG_PORT`（本机在 4510–4520 之内）。
- 迁移失败：报告里「执行迁移」失败，api 与 worker 仍是上一版本；修好后重新部署（迁移只向前，ADR 0013）。
- 连数据库：`psql -h 127.0.0.1 -p 4511 -U forcome forcome`（口令在环境文件里）。
- 停止：`pnpm staging down`（保留数据卷）。`pnpm staging compose down -v` 会连数据库与根证书一起删掉，慎用。
- 旧版本镜像不会自动删除（每次部署多一个 `forcome-server`、`forcome-web`、`forcome-smoke`），定期用 `docker image ls "forcome-*"` 查看后删掉不再用的版本；自动清理与日志轮转随 28 号待办。
