# 按记账方选择外部数据来源：履约与订单经积加，资金写动作走官方平台

> 2026-09-24 修订：「订单读取」一行及相关理由与后果已由 ADR 0011 改为平台直读，见文末「修订」。

外部数据与动作按「哪个系统是这类数据的记账方就找哪个系统」分工，而不是全部经积加或全部直连官方平台（2026-09-24 用户同意）：

| 数据或动作 | 来源 |
|---|---|
| 补发、出库、易仓库存、实际运费 | 积加（补发走「自发货订单新增 V2」补单，积加按订单策略推送易仓）；易仓 OMS 接口仅作只读与取消的备用通道 |
| 订单读取（亚马逊、Shopify） | ~~积加~~ → 平台直读，积加只补充亚马逊收件人（ADR 0011） |
| 退款、取消、改地址 | 亚马逊 SP-API（Feeds 异步）、Shopify Admin API |
| 物流轨迹 | 17TRACK（主动轮询） |
| 来信收发 | Gmail（亚马逊买家消息经邮件中转） |

积加是 FSH 履约与库存的记账方，绕过它直接在易仓建单会造成积加账面库存与财务不一致；订单经积加读取可避开亚马逊受限数据（买家 PII）的数据保护义务，并与客户现有的积加报表口径一致；积加开放接口做不了退款、取消与轨迹，这些走官方平台或专门服务。

## Considered Options

- 全部经积加：积加开放接口无退款、取消、轨迹，且只能轮询，关键动作不能只依赖它。
- 全部直连官方平台：要承担亚马逊受限数据合规（交付后 30 天删除、全员 MFA、日志 12 个月等）、易仓直连建单导致积加账实不符、订单双数据源对账；只换来订单从分钟级到秒级的实时性，对客服场景不划算。

## Consequences

- 积加成为订单与履约的单点依赖：中断时订单查询、库存查询、补发暂停，按 PRD E-01 转人工操作清单兜底。
- 补单参数待积加确认（`.scratch/tech-plan/积加技术问题清单.md` 第 1–4 条）；若不可行，退路为系统生成补发任务、坐席在积加界面手工建补单，其余环节照常自动。
- 取消补发单第一期由坐席在积加界面操作；订单数据有 1–5 分钟同步延迟；实际运费次日可得。
- 服务器需固定出口 IP 以登记积加 IP 白名单。
- 依据见 `research/jijia-api`、`research/sp-api`、`research/tracking-source` 分支的调研报告。

## 修订（2026-09-24，交叉审查复核，见 `.scratch/tech-plan/reviews/复核结论.md`）

- 「订单读取」一行及相关理由与后果已由 ADR 0011 修订：积加中断时订单查询不受影响；「订单数据有 1–5 分钟同步延迟」不再适用；积加只是履约、库存与亚马逊收件人的记账方，订单以平台为准。
