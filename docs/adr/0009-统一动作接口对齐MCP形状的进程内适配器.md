# 「MCP 形式」落为形状对齐 MCP 的进程内统一动作接口，不拆独立 MCP 服务

PRD F-AP-02 与 11.3 写的「适配器（MCP 形式）」定义为（2026-09-24 用户同意）：适配器在后端进程内实现（ADR 0005 的 `integration` 模块），动作定义的形状对齐 MCP 工具规范（名称、描述、JSON Schema 形式的输入与输出），以后可随时包一层成为真正的 MCP 服务器。第三期只把只读动作（查订单、查物流、查库存）作为工具交给模型；写动作由模型提议，走审批。

**统一动作接口**
- 只有 PRD 的 9 个动作走这个接口。每个动作一份定义：名称、分级、输入与输出的 zod 模式、`execute(上下文, 输入)`；上下文含店铺、幂等键、截止时间、操作人。
- 结果为 `succeeded`、`pending`（已受理、等待回执，带外部引用，如亚马逊 feed ID）、`failed_retryable`、`failed_permanent`、`unknown`（结果不明，先查询再决定，见 ADR 0008）。
- Gmail 收信、钉钉同步、17TRACK 轮询不是动作，是 `integration` 里的普通客户端，由业务模块直接调用。

**映射与凭据**：适配器在代码中注册，「动作 × 平台 → 适配器」映射存在数据库里，由 P22 编辑；每次调用必须带店铺，凭据只在 `integration` 内按店铺 ID 取用，业务模块拿不到凭据（R-ST-03）。

**能力缺口**：平台不支持、适配器未接通（积加补单参数待确认、取消补发单无开放接口），或发起人在执行失败后选择转人工时，按「动作 × 平台」的步骤模板生成人工操作清单。亚马逊改地址不生成清单，由草稿引导买家取消后重新下单。

**出站**：所有外部调用经同一个 HTTP 客户端工厂，出站代理读取环境变量 `HTTPS_PROXY`（undici `EnvHttpProxyAgent`；gRPC 与钉钉 Stream 读同一组变量），分流在代理侧完成（ADR 0003）；按外部系统限流（积加每秒 2 次、17TRACK 每秒 3 次）；每次调用写调用记录，用于排错并支撑 P18 的连接状态。

**假适配器**：每个适配器配一个 Fake 实现，能模拟成功、失败、超时和异步回执；按店铺配置选择真实现还是假实现。开发测试环境和 Playwright 测试默认用 Fake。

## Considered Options

- 每个适配器一个独立的 MCP 服务器进程，后端作为 MCP 客户端：审批、幂等、重试要跨进程协调，还多出几个要部署和监控的服务，换来的只是协议上的「正宗」。
- 额外对外提供只读 MCP 服务器，供员工在 Claude 桌面版等工具里查询：目前没有这个需求，因为接口形状已经对齐 MCP，以后可以再加。

## Consequences

- PRD 中「MCP 形式」的措辞需要回写，改为「形状对齐 MCP 的统一动作接口」。
- 积加开放接口和 SP-API 开通之前，功能可以用 Fake 端到端开发和测试；开通后逐个店铺切换成真实现。
- 亚马逊动作以 `pending` 结束，最终结果由 feed 回执轮询（ADR 0008）回写。

## 修订（2026-09-24，交叉审查复核，见 `.scratch/tech-plan/reviews/复核结论.md`）

- 「第三期只把只读动作作为工具交给模型」已由 ADR 0014 修订：`draft` 不开放工具，数据由代码按意图预取。
- 积加补发的成功边界见 ADR 0008 修订（`pending` 直到易仓确认）；限流按接口分别配置（积加补单与配货单列表均为每秒 1 次）。
- **Fake 覆盖**：不只动作适配器，Gmail、钉钉、订单同步、17TRACK 等客户端也都配 Fake；另有只在非生产环境启用的开发登录；把原型示例数据 `design/spec/data.py` 转成 JSON 夹具，供种子数据、Fake 回放与 Playwright 共用。
- **回复客户的幂等**：发信前生成并保存自己的 `Message-ID`；结果不明时用 `rfc822msgid:` 在「已发送」中查询确认，再决定是否重试。
- **订单按需补拉**：镜像中没有的订单按订单号补拉（亚马逊 `getOrder`；Shopify 在取得 `read_all_orders` 后按订单名查询，订单名在店铺内匹配）。
- （2026-10-03）出站分流以 ADR 0003 修订为准：系统设 `NO_PROXY`，境内流量不经代理。后果中「PRD 中『MCP 形式』的措辞需要回写」已由 PRD v2.8（D-21）完成。
