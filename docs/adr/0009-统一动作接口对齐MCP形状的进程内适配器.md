# 「MCP 形式」落为形状对齐 MCP 的进程内统一动作接口，不拆独立 MCP 服务

PRD F-AP-02 与 11.3 写的「适配器（MCP 形式）」定义为（2026-09-24 用户同意）：适配器在后端进程内实现（ADR 0005 的 `integration` 模块），动作定义的形状对齐 MCP 工具规范（名称、描述、JSON Schema 形式的输入与输出），以后可随时包一层成为真正的 MCP 服务器。第三期只把只读动作（查订单、查物流、查库存）作为工具交给模型；写动作由模型提议，走审批。

**统一动作接口**
- 只有 PRD 的 9 个动作走这个接口。每个动作一份定义：名称、分级、输入与输出的 zod 模式、`execute(上下文, 输入)`；上下文含店铺、幂等键、截止时间、操作人。
- 结果为 `succeeded`、`pending`（已受理、等待回执，带外部引用，如亚马逊 feed ID）、`failed_retryable`、`failed_permanent`、`unknown`（结果不明，先查询再决定，见 ADR 0008）。
- Gmail 收信、钉钉同步、17TRACK 轮询不是动作，是 `integration` 里的普通客户端，由业务模块直接调用。

**映射与凭据**：适配器在代码中注册，「动作 × 平台 → 适配器」映射存在数据库里，由 P22 编辑；每次调用必须带店铺，凭据只在 `integration` 内按店铺 ID 取用，业务模块拿不到凭据（R-ST-03）。

**能力缺口**：平台不支持、适配器未接通（积加补单参数待确认、取消补发单无开放接口），或发起人在执行失败后选择转人工时，按「动作 × 平台」的步骤模板生成人工操作清单。亚马逊改地址不生成清单，由草稿引导买家取消后重新下单。

**出站**：所有外部调用经同一个 HTTP 客户端工厂，出站代理读取环境变量 `HTTPS_PROXY`（undici `EnvHttpProxyAgent`；gRPC 与钉钉 Stream 读同一组变量），分流在代理侧完成（ADR 0003）；按外部系统限流（积加每秒 2 次、17TRACK 每秒 3 次）；每次调用写调用记录，用于排错并支撑 P18 的连接状态。

**假适配器**：每个适配器配一个 Fake 实现，能模拟成功、失败、超时和异步回执；按店铺配置选择真实现还是假实现。开发测试环境和 Playwright 测试默认用 Fake。

## Considered Options

- 每个适配器一个独立的 MCP 服务器进程，后端作为 MCP 客户端：审批、幂等、重试要跨进程协调，还多出几个要部署和监控的服务，换来的只是协议上的「正宗」。
- 额外对外提供只读 MCP 服务器，供员工在 Claude 桌面版等工具里查询：目前没有这个需求，因为接口形状已经对齐 MCP，以后可以再加。

## Consequences

- PRD 中「MCP 形式」的措辞需要回写，改为「形状对齐 MCP 的统一动作接口」。
- 积加开放接口和 SP-API 开通之前，功能可以用 Fake 端到端开发和测试；开通后逐个店铺切换成真实现。
- 亚马逊动作以 `pending` 结束，最终结果由 feed 回执轮询（ADR 0008）回写。

## 修订（2026-09-24，交叉审查复核，见 `.scratch/tech-plan/reviews/复核结论.md`）

- 「第三期只把只读动作作为工具交给模型」已由 ADR 0014 修订：`draft` 不开放工具，数据由代码按意图预取。
- 积加补发的成功边界见 ADR 0008 修订（`pending` 直到易仓确认）；限流按接口分别配置（积加补单与配货单列表均为每秒 1 次）。
- **Fake 覆盖**：不只动作适配器，Gmail、钉钉、订单同步、17TRACK 等客户端也都配 Fake；另有只在非生产环境启用的开发登录；把原型示例数据 `design/spec/data.py` 转成 JSON 夹具，供种子数据、Fake 回放与 Playwright 共用。
- **回复客户的幂等**：发信前生成并保存自己的 `Message-ID`；结果不明时用 `rfc822msgid:` 在「已发送」中查询确认，再决定是否重试。
- **订单按需补拉**：镜像中没有的订单按订单号补拉（亚马逊 `getOrder`；Shopify 在取得 `read_all_orders` 后按订单名查询，订单名在店铺内匹配）。
- （2026-10-03）出站分流以 ADR 0003 修订为准：系统设 `NO_PROXY`，境内流量不经代理。后果中「PRD 中『MCP 形式』的措辞需要回写」已由 PRD v2.8（D-21）完成。

## 修订（2026-10-04，待办 02 落地）

- **Fake 框架**：外部客户端在 `integration` 里用 `defineClient` 定义——同一个接口、一个真实现、一个 Fake——并登记在 `integration/registry.ts`；业务代码一律经 `IntegrationClients` 取。店铺级客户端（Gmail、订单）用 `forStore(定义, { id, adapterMode })` 按店铺配置给真实现或 Fake；全局客户端（钉钉、汇率）用 `global(定义)`，按环境变量 `CLIENT_MODE_<系统>=real|fake` 选择，不设时非生产用 Fake、生产用真实现。`adapterMode` 的取值（`real`、`fake`）在 `contracts`，店铺表的「真实 / Fake」字段随 07 号待办。
- **生产环境不给 Fake**：配置里写了 `fake` 拒绝启动；店铺配置为 Fake 时抛 `FakeNotAllowedError`，不退回真实现；`fake(定义)` 在生产环境同样拒绝。没登记的客户端取不到；`CLIENT_MODE_` 写了没登记的系统名或店铺级客户端，拒绝启动。
- **一个进程一份 Fake**：`IntegrationClients` 按定义各建一个 Fake 实例，服务全部店铺（Fake 自己按店铺分开数据）。测试经 `clients.fake(定义)` 往里放数据、注入故障，被测代码取到的就是同一个实例；`resetFakes()` 全部重置。api 与 worker 是两个进程，各有一份 Fake，开发测试环境里需要两边一致的数据从示例数据夹具回放。
- **故障注入与错误**：Fake 在每个操作开头 `await faults.check('操作名')`（`FaultInjector`）；测试可安排失败（可带状态码、限定操作与次数）、超时、游标过期、断线与恢复，并读到调用记录以断言重试次数。超时不真的等待。真实现与 Fake 抛同一套错误：`ExternalCallFailedError`（带状态码；限流与 5xx 可重试，其余 4xx 不可）、`ExternalTimeoutError`、`CursorExpiredError`（调用方改为按区间全量补拉）、`ConnectionLostError`。
- **示范与后续**：`integration/fake-framework.test.ts` 用一个示范客户端演示定义、按店铺选择与各种故障，各集成在自己的待办里照此实现（钉钉 05、Gmail 08/09、Shopify 11、SP-API 12、汇率 20）。真实现需要的出站 HTTP 客户端工厂、限流与调用记录，随第一个真实现的待办加入。
- **示例数据夹具**：`scripts/fixtures/export_demo_fixture.py` 把 `design/spec/data.py` 转成 `packages/fixtures/data/demo.json`（`pnpm fixtures:generate`；产物进仓库，CI 与 `pnpm ci:local` 用 `pnpm fixtures:verify` 核对与 data.py 一致），`@forcome/fixtures` 加载时按 zod 模式校验。第一期的转换规则：工单取 `p1_tickets()`（16 张）；台账取 `p1_ledger_rows()`（丢弃待确认的单，创建路径记「手工登记」，登记人取负责人）；P05 时间线取 `P1_OLIVER`；Fake 汇率固定为 1 USD = 18.00 MXN、1.36 CAD。成员与店铺的 id 用 UUIDv5 从 key 派生，重复生成不变；时间写成带 +08:00 的 ISO 8601，金额写成两位小数的字符串；业务取值保留中文，由各模块的加载步骤映射到枚举。订单、未归属店铺来信等其余数据，由需要的待办补充转换规则。`getDemoFixture()` 第一次取用时才解析与校验，生产环境的进程不会因夹具出错。
- **加载器**：`core` 的 `defineFixtureStep` 与 `loadFixtures`。各模块定义自己的加载步骤（可声明先后依赖），从模块的 `index.ts` 导出并登记到 `apps/server/src/fixture-steps.ts`；按依赖顺序在一个事务里执行，任一步失败全部回滚；步骤要幂等；生产环境拒绝。`pnpm db:seed`（镜像里 `node dist/seed.mjs`）、Playwright 的 e2e api 与测试工具的 `t.loadFixtures()` 共用。
- **Fake 回放**：加载器只写库；Fake 里的数据由各 Fake 自己提供从夹具装入的方法（例如 Fake Gmail 按夹具的来信建邮件），测试里经 `t.clients.fake(定义)` 调用，开发测试环境里在进程启动时调用（随 03 号待办与各集成的待办）。

## 修订（2026-10-04，待办 03 落地）

- **Fake 回放的时机**：`FakeClient` 可选实现 `replay(fixture)`，从示例数据夹具装入数据；`IntegrationClients.replayFixtures(fixture)` 让登记的、有回放方法的 Fake 装入数据（生产环境拒绝）。进程入口用的 `createIntegrationClients(config)` 在非生产环境（本机开发、开发测试环境、Playwright 的 e2e api）组装时自动回放，生产环境不回放、也不解析夹具；测试工具（`startTestHarness`）不自动回放，测试需要时自己调用。api 与 worker 各回放一份，靠同一份夹具保持一致。
- **真实现的构造参数**：`RealClientContext` 增加 `mailRecipientGuard`（发信白名单，ADR 0013 修订）。

## 修订（2026-10-05，待办 07 落地）

- **店铺的数据来源**：`channel.store.adapter_mode`（`real` / `fake`），店铺级客户端经 `forStore(定义, { id, adapterMode })` 按它选择。P18 抽屉只在非生产环境显示「数据来源：真实接口 / 模拟数据」：非生产环境新建店铺不选时为模拟数据（与外部客户端默认 Fake 一致），编辑时不传保持原值；生产环境不显示，接口收到模拟数据返回字段错误「生产环境不能使用模拟数据」，不传时一律真实接口。示例数据的 4 个店铺为模拟数据。
- **全局客户端的模式**：`IntegrationClients.globalMode(系统)` 返回按 `CLIENT_MODE_<系统>` 选择的实现（只读配置、不建客户端，所以不要求已登记），P18 钉钉卡据此标「模拟数据」。
- **连接状态的过渡口径**：各客户端与同步记录（钉钉 05、Gmail 09、Shopify 11、SP-API 12）接上之前，P18 的连接状态只由数据来源决定——模拟数据视为已连接、卡头另标「模拟数据」，真实接口为未连接；实现集中在 `channel/connections.ts` 的 `statusOf`，由这些待办按同步记录替换（同步延迟、连接异常、最近同步时间）。渠道卡显示最差的状态，先后为 连接异常 > 未连接 > 同步延迟 > 已连接（`contracts` 的 `worstConnectionStatus`）。

## 修订（2026-10-05，待办 08 落地）

- **Gmail 是两个客户端**：邮箱 `gmail`（店铺级，按店铺的数据来源选择；`watch`、`listHistory`、`getMessage`——取 format=raw 的 RFC 822 原文，解析在 `channel`）与推送 `gmail_push`（全局，按 `CLIENT_MODE_GMAIL_PUSH` 选择；`pull`、`acknowledge`）。推送是环境级的（一个 Pub/Sub 订阅服务全部邮箱），不能按店铺选；同一环境里店铺有的接真实、有的接模拟数据时推送只能二选一，另一类店铺靠 09 的每 5 分钟 history.list 兜底。两者的真实现在 08 是占位：调用即以「尚未接入」失败（不可重试），不会悄悄退回 Fake；服务账号 + 全域委派、Pub/Sub 订阅、出站代理与调用记录随 09。
- **Fake 之间的联动**：`createFake(context)`，`context.fake(定义)` 取同一个 `IntegrationClients` 里的另一个 Fake——Fake 邮箱被 watch 后把通知发进 Fake 推送，真实世界里 Gmail 与 Pub/Sub 的联动在 Fake 里同样成立。客户端的定义与约定拆到 `integration/definition.ts`：`clients.ts` 引用登记清单 `registry.ts`，清单又引用各客户端定义，放在一个文件会循环引用。
- **Fake Gmail**：按邮箱存邮件与 history；测试用 `deliver`（发给几个邮箱时各收一份、Message-ID 相同，返回各邮箱的 Gmail 消息 ID）、`redeliver`（同一封再出现在 history，E-15）、`isWatched`；被 watch 的邮箱每到一封信发一条推送；推送拉走但没确认的，下次拉取重投。邮件原文由 `integration/gmail-mime.ts` 拼成 RFC 822（非 ASCII 的头字段写 UTF-8 encoded-word，正文 base64），解析走生产同一条路。
- **Fake Gmail 的回放**：从示例数据夹具回放来信（`integration/gmail-replay.ts`：每张示例工单一封，到达时间取「最近来信」，有订单号的在正文另起一行写出；P1_OLIVER 按时间线的三封来信；夹具没有客户邮箱，亚马逊用按站点的买家消息中转域名、其余用 example.com，地址由客户名推出；Message-ID 与 Gmail 消息 ID 由工单号推出，重启后回放的是同样的信），在邮箱开始监听（watch）之后送达——演示环境里它们是系统上线后到达的来信。重复部署时邮箱已有游标、不再 watch，回放的信不会再送达；即使续订 watch（09）后再送达，也按 Gmail 消息 ID 去重。我方回复、标记无需回复与关闭随 09、16、17 补进回放。
- **邮件解析用 postal-mime**（维护活跃、无依赖）：RFC 822 → 头字段、地址、Message-ID / In-Reply-To / References、纯文本与 HTML 正文，处理 encoded-word 与字符集。全部头字段按出现顺序存进 `channel.message.headers`，供来源规则、自动回复标记、Delivered-To 等识别用（10、15、16）；附件随用到它的待办。

## 修订（2026-10-05，待办 20 落地）

- **出站 HTTP 客户端工厂**（第一个真实现，汇率）：`integration/http.ts` 的 `createHttpClient(系统)`，整个进程共用一个 undici `EnvHttpProxyAgent`（读 `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY`，大小写都认，ADR 0003）；每次调用有时限（默认 30 秒，到点抛 `ExternalTimeoutError`）；非 2xx 抛带状态码的 `ExternalCallFailedError`（429、5xx 可重试），网络错误抛不带状态码、可重试的 `ExternalCallFailedError`——与 Fake 同一套错误。测试经参数换成 undici 的 `MockAgent`，按 URL 回放录好的返回，不连外网。按「系统 × 接口」的限流与调用记录随 09 号待办（Gmail，第一个高频、要支撑 P18 连接状态的真实现）加在这个工厂里；汇率每天一次，不需要限流。
- **汇率客户端** `exchange_rate`（全局，`CLIENT_MODE_EXCHANGE_RATE`；不设时非生产 Fake、生产真实现）：两个来源——欧洲央行的公开参考汇率文件（按要取的区间挑最小的：只差最近一天且中间没缺工作日用 `eurofxref-daily.xml`，近 90 天内用 `eurofxref-hist-90d.xml`，更早或第一次同步用 1999 年起的全量 `eurofxref-hist.xml`），与 Frankfurter `api.frankfurter.dev/v2/rates`（`providers=ECB`，数据同样来自欧洲央行）。都给出 1 EUR 兑 USD、CAD、MXN；返回内容不认识（不是参考汇率文件、缺币种）是不可重试的失败。XML 解析用 fast-xml-parser。
- **接口定义在使用方**：汇率的同步与入库在 `core`（规格 core「汇率」），`core` 不能依赖 `integration`，所以两个来源的接口 `ExchangeRateSource` 定义在 `core`，`integration` 的客户端实现它（`ExchangeRateClient = ExchangeRateSource`），由入口（`apps/server/src/jobs.ts`）把 `deps.clients.global(exchangeRateClient)` 交给 `core` 的任务处理器。
- **Fake 汇率**：`publish(日期, { MXN, CAD })` 按「1 USD = x 原币」公布某天的汇率（换成 1 EUR = 1.10 USD 的 EUR 基准，交叉计算后正好还原），两个来源给同一份数据，`faults` 用操作名 `ecb`、`frankfurter` 分别注入故障。回放示例数据时从 2025-01-01 起每个工作日都是演示汇率（1 USD = 18.00 MXN、1.36 CAD），开发测试环境里新登记的比索、加元金额也能折算；示例台账的冻结值由加载步骤按夹具写入，不依赖 Fake。
