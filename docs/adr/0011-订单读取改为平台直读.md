# 订单读取改为平台直读（亚马逊 SP-API 非受限角色、Shopify Admin API），积加只补充收件人与履约

修订 ADR 0002 中「订单读取（亚马逊、Shopify）｜积加」一行（2026-09-24 用户同意）。用户了解到积加开放接口拿到的订单是隔天（T+1），满足不了第一期「报表 T+0、15 分钟内」和按订单归并来信（R-TK-01）；SP-API 的受限数据（PII）角色又难以申请。订单改为按字段拆分来源：

| 数据 | 来源 |
|---|---|
| 亚马逊订单（状态、商品行、MFN/AFN、承诺时效、城市/州/国家、MFN 快递单号） | SP-API Orders v2026-01-01，只用非受限角色 Inventory and Order Tracking（退款、取消 feed 本来就要这个角色）；`ORDER_CHANGE` 通知投递到我方 AWS us-east-1 的 SQS 队列，经代理长轮询，另按 `lastUpdatedAfter` 每 3～5 分钟增量兜底 |
| Shopify 订单（含客户邮箱、收件地址、履约单号） | Shopify Admin GraphQL API，与退款、取消共用一个自建应用，按 `updated_at` 每 1～2 分钟增量 |
| 亚马逊买家姓名与收件地址（补发时用） | 积加订单详情（订购一个月内）；取不到时由坐席补填 |

补发、出库、易仓库存、实际运费、退款、取消、改地址、物流轨迹、来信收发仍按 ADR 0002。本地由新增的 `order` 模块维护订单镜像（上线时回补 90 天、每天夜间对账），以平台订单号（`AmazonOrderId`、Shopify 订单 ID）为关联键，积加数据只补充收件人与履约记录。

## Considered Options

- 继续全部经积加：实际时效与积加文档「1 分钟 / 5 分钟」对不上（用户反馈为隔天），在问清之前不能作为报表与归并的唯一来源。
- 申请 SP-API 受限角色、全部直连：受限角色难以申请；买家邮箱也用不上（亚马逊来信里已有匿名邮箱与订单号）。
- 第三方聚合平台（Veeqo 等）：会回写平台、同步库存，与积加冲突；只留作备选。
- 用领星替代积加或作补充数据源：读不到亚马逊收件人、订单时效未公布，补不上积加的短板（见 `research/lingxing`）。

## Consequences

- 需要开一个 AWS 账户与 SQS 标准队列（免费额度内），SQS 与 SP-API 都经境外代理出站（ADR 0003）。
- 积加中断时，订单查询不受影响，只影响补发、库存、运费与亚马逊收件地址。
- 报表口径以平台为准，可能与积加报表有差异，报表页需要注明。
- 积加回传亚马逊的 MFN 快递单号能否在 v2026-01-01 的 `packages[]` 里读到，开通后要实测；读不到时单号退回积加「查询订单发货信息」。
- 美国站非受限角色拿不到邮编，只有城市、州、国家。
- 依据见 `research/order-source`、`research/lingxing` 分支的调研报告。

## 修订（2026-09-24，交叉审查复核，见 `.scratch/tech-plan/reviews/复核结论.md`）

- 「上线时回补 90 天」：Shopify 默认只能读 60 天，61–90 天依赖 `read_all_orders`，申请不下来则回补 60 天并在报表注明；镜像缺失的订单按订单号按需补拉（亚马逊 `getOrder`，Shopify 按订单名）。回补在上线前几天开始，与增量同步共享 SP-API 令牌桶（ADR 0008 修订）。

## 修订（2026-10-06，待办 11 落地）

- **Shopify 的访问令牌**：用 Shopify 自建应用（Dev Dashboard，应用与两个店铺同一组织）的客户端凭据按店铺以 client credentials 换令牌（`POST https://<店铺>.myshopify.com/admin/oauth/access_token`，`expires_in` 恒为 86399 秒），令牌用主密钥加密存进 `integration.credential`（ADR 0013 修订），换到后满 20 小时提前换新，被拒（401）立即换新再试一次。没用 `@shopify/shopify-api`：它的请求不经我们的出站工厂（代理分流、限流、调用记录，ADR 0009），而我们只用一个换令牌接口与一个 GraphQL 端点，自己写的只有查询文本、zod 校验与错误翻译。Admin API 版本固定 `2026-07`（`SHOPIFY_API_VERSION`），升级时改常量。
- **增量同步**：定时任务 `order.shopify_poll` 每分钟（规格「每 1–2 分钟」，worker 启动时也一次）给每个 Shopify 店铺排 `order.shopify_sync`；同步从水位（已写进镜像的订单里最晚的平台更新时间）前 2 分钟起按 `updated_at:>=` 分页（`sortKey: UPDATED_AT`，每页 100 笔）取订单，重叠一段，平台搜索索引的延迟与两边时钟偏差都不漏；第一次同步从此刻起，之前的历史订单由回补导入（13）。新增或编辑 Shopify 店铺后立即同步一次；改了平台、平台标识或数据来源时，该店铺的同步记录清掉、按新配置从头算（之前那个数据源的「最近同步成功」不算数）。
- **镜像只进不退**：`order.platform_order` 按「店铺 + 平台订单号（Admin API 的全局 ID）」upsert，只有平台更新时间比镜像里新的版本才改，重复拉取、回补与增量交错都不产生重复行、不会用旧版本盖掉新版本；订单名只建普通索引（平台保证店铺内唯一；库里不加唯一约束，撞名不卡同步，按名查取最新的一笔），邮箱存小写。每页在一个事务里写，全部页写完后才在一个事务里推进水位并记同步成功（水位只在持久化成功后推进）。
- **对外接口**（`order/index.ts`；`order` 不依赖 `channel`，店铺由调用方给出）：`findOrder(运行时, 客户端, 店铺范围, 店铺, { name } | { platformOrderId })`——先查镜像，镜像没有、给的是订单名、店铺是 Shopify 时按订单名补拉（只写数字的补上 `#`，GraphQL `name:` 搜索后只认完全一致的那笔）并入库；没配置 Shopify 凭据时只查镜像；补拉的外部调用失败照常抛出，调用方（14 的归并）决定稍后重试。`findOrdersByEmail(库, 店铺范围, { storeId, email })` 只在指定店铺内按邮箱（不分大小写）反查、只查镜像（R-ST-03）。`orderSyncHealths(库)` 给出各店铺的最近同步成功与连续失败（P18 与报表「更新于」用）。
- **连接状态**：同 Gmail（ADR 0009「待办 09 落地」）：按店铺的同步记录 `order.order_sync`，外部调用失败（没配置凭据的 `ClientNotConfiguredError` 除外）各记一次，同步任务不重试——下一分钟的同步就是重试，约 3 分钟的故障满 3 次；连续第 3 次通知管理员与客服主管（另排钉钉工作通知）、记审计「连接异常」，恢复时发「Shopify 已恢复 · 补拉 N 笔订单」（N 为恢复那次写入或更新的订单数）、记审计「恢复连接」。P18 Shopify 卡取各店铺中最差的状态并列出延迟与异常的店铺，最近同步取各店铺中最旧的一次；全站横幅 `kind: 'shopify'`，与 Gmail 同时异常时各一条。亚马逊仍由数据来源决定（12）。
