# 订单读取改为平台直读（亚马逊 SP-API 非受限角色、Shopify Admin API），积加只补充收件人与履约

修订 ADR 0002 中「订单读取（亚马逊、Shopify）｜积加」一行（2026-09-24 用户同意）。用户了解到积加开放接口拿到的订单是隔天（T+1），满足不了第一期「报表 T+0、15 分钟内」和按订单归并来信（R-TK-01）；SP-API 的受限数据（PII）角色又难以申请。订单改为按字段拆分来源：

| 数据 | 来源 |
|---|---|
| 亚马逊订单（状态、商品行、MFN/AFN、承诺时效、城市/州/国家、MFN 快递单号） | SP-API Orders v2026-01-01，只用非受限角色 Inventory and Order Tracking（退款、取消 feed 本来就要这个角色）；`ORDER_CHANGE` 通知投递到我方 AWS us-east-1 的 SQS 队列，经代理长轮询，另按 `lastUpdatedAfter` 每 3～5 分钟增量兜底 |
| Shopify 订单（含客户邮箱、收件地址、履约单号） | Shopify Admin GraphQL API，与退款、取消共用一个自建应用，按 `updated_at` 每 1～2 分钟增量 |
| 亚马逊买家姓名与收件地址（补发时用） | 积加订单详情（订购一个月内）；取不到时由坐席补填 |

补发、出库、易仓库存、实际运费、退款、取消、改地址、物流轨迹、来信收发仍按 ADR 0002。本地由新增的 `order` 模块维护订单镜像（上线时回补 90 天、每天夜间对账），以平台订单号（`AmazonOrderId`、Shopify 订单 ID）为关联键，积加数据只补充收件人与履约记录。

## Considered Options

- 继续全部经积加：实际时效与积加文档「1 分钟 / 5 分钟」对不上（用户反馈为隔天），在问清之前不能作为报表与归并的唯一来源。
- 申请 SP-API 受限角色、全部直连：受限角色难以申请；买家邮箱也用不上（亚马逊来信里已有匿名邮箱与订单号）。
- 第三方聚合平台（Veeqo 等）：会回写平台、同步库存，与积加冲突；只留作备选。
- 用领星替代积加或作补充数据源：读不到亚马逊收件人、订单时效未公布，补不上积加的短板（见 `research/lingxing`）。

## Consequences

- 需要开一个 AWS 账户与 SQS 标准队列（免费额度内），SQS 与 SP-API 都经境外代理出站（ADR 0003）。
- 积加中断时，订单查询不受影响，只影响补发、库存、运费与亚马逊收件地址。
- 报表口径以平台为准，可能与积加报表有差异，报表页需要注明。
- 积加回传亚马逊的 MFN 快递单号能否在 v2026-01-01 的 `packages[]` 里读到，开通后要实测；读不到时单号退回积加「查询订单发货信息」。
- 美国站非受限角色拿不到邮编，只有城市、州、国家。
- 依据见 `research/order-source`、`research/lingxing` 分支的调研报告。

## 修订（2026-09-24，交叉审查复核，见 `.scratch/tech-plan/reviews/复核结论.md`）

- 「上线时回补 90 天」：Shopify 默认只能读 60 天，61–90 天依赖 `read_all_orders`，申请不下来则回补 60 天并在报表注明；镜像缺失的订单按订单号按需补拉（亚马逊 `getOrder`，Shopify 按订单名）。回补在上线前几天开始，与增量同步共享 SP-API 令牌桶（ADR 0008 修订）。
