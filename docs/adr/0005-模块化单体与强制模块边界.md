# 模块化单体，模块边界由 lint 强制，跨模块联动走领域事件

生产系统采用模块化单体（2026-09-24 用户同意）：一个仓库、一个后端代码库，内部按领域分模块；同一个后端镜像分 `api`、`worker` 两个入口，在 Docker Compose 里是两个容器。

**模块**：`org` 组织、`channel` 渠道与收件、`ticket` 工单、`approval` 审批与动作、`aftersales` 售后（含登记台账、比例协商、内部结算）、`factory` 工厂、`ai` AI 处理、`knowledge` 知识库、`report` 报表、`order` 订单（本地订单镜像，2026-09-24 由 ADR 0011 增补）；另有基础设施层 `integration`（全部外部适配器）和 `core`（审计、工作日历、编号、通知、配置）。设置页的配置归各自所属的模块，不单设模块。

**边界规则**：
- 模块只通过自己 `index.ts` 导出的服务和类型被调用，不能跨模块读写别的模块的表。唯一的例外是 `report` 可以只读各模块的表。
- 一个模块的状态变化需要另一个模块响应时，发领域事件，经事务性发件箱交给 `worker` 处理。
- 边界由 dependency-cruiser 或 eslint-plugin-boundaries 在 CI 中强制检查。

**仓库结构**：pnpm workspace，包括 `apps/web`、`apps/server`、`packages/contracts`（前后端共享的 zod 模式与类型，含状态枚举的中英对照）、`packages/config`；暂不引入 Turborepo 或 Nx。

**命名**：标识符用 PRD 11.1 的英文对象名；状态、枚举、表名、列名用英文 snake_case；注释、提交信息、文档用中文，并在注释里标注业务规则编号。

## Considered Options

- 微服务：团队小、以 AI 代理开发为主、用 Docker Compose 部署，分布式事务、服务间调用和多套部署都是纯成本。
- 模块边界只靠约定：AI 代理按待办实现时，容易为了图省事跨模块直接查表，边界会很快被侵蚀；强制检查的成本只是 CI 里的一条规则。
- 单进程：轮询、feed 回执、模型调用这些慢活会拖慢页面响应。

## Consequences

- 每张实现待办原则上只动一个模块加 `contracts`，代理需要读的上下文限定在模块内。
- 跨模块流程（审批通过 → 售后单推进 → 工厂任务派发）都是最终一致的，要能容忍秒级延迟；发件箱的实现归「讨论：后台任务与流程引擎」。
- 报表直接读各模块的表，模块改表结构时要同步检查报表查询。
- 适配器暂时放在 `integration` 模块内；若「讨论：集成层设计与「MCP 形式」的含义」决定做成独立的 MCP 服务，再拆到 `packages/`。

## 修订（2026-09-24，交叉审查复核，见 `.scratch/tech-plan/reviews/复核结论.md`）

- **`channel` 与 `ticket` 的分工**：`channel` 只做接入与规范化（去重、店铺与来源识别、订单号抽取），处理完发出「来信已接收」事件；归并（R-TK-01、R-TK-02）、消息、SLA 与回复识别归 `ticket`，避免跨模块读写。「第一期 `ticket` 只读」指界面没有人工写操作（两个例外见 PRD D-22），系统照常写工单与消息。
- 后果中「发件箱的实现归『讨论：后台任务与流程引擎』」已由 ADR 0008 定下；「若决定做成独立的 MCP 服务」已由 ADR 0009 定为不拆。

## 修订（2026-10-04，待办 01 落地）

- **边界检查**：用 eslint-plugin-boundaries（v7 的 `boundaries/dependencies`），规则集中在 `packages/config/eslint-boundaries.js`，`pnpm lint` 与 CI 执行；`apps/server/test/module-boundaries.test.ts` 用仓库真实的 ESLint 配置固化判定。规则：
  - 模块之间只能引用对方的 `index.ts`，类型引用也一样；`report` 另可引用各模块的 `schema.ts`；
  - `core` 不依赖任何模块；`integration` 只依赖 `core`；
  - 模块不能引用 `apps/server/src` 下的入口与组装代码（`app.ts`、`jobs.ts` 等），入口只经各模块 `index.ts` 使用模块；
  - 模块的 `index.ts` 要逐个列出导出项（禁止 `export *`），不能直接转出本模块的 `schema.ts`；先 import 表再按名字导出的写法 lint 查不到，由评审把关；
  - `packages/*` 不依赖应用代码；前端不引用后端代码。
- **report 只读**：`report` 读别的模块的表一律经 `runReportQuery`（只读事务 + 只读数据库角色，见 ADR 0006 修订），不在别处直接查询；数据库层面写入会被拒绝，评审时检查调用方式。
- **模块目录**：`apps/server/src/modules/<模块>/`，`index.ts` 是唯一对外入口，`schema.ts` 放本模块的表。12 个模块（含第二、三期才有内容的 `approval`、`factory`、`ai`、`knowledge`）都已建好空目录、入口与 schema，后续待办只往里加。
- **任务处理器总表**：各模块的后台任务处理器在 `apps/server/src/jobs.ts` 汇总，worker 据此订阅、migrate 据此建队列。
- **共享包**：`packages/contracts`、`calendar` 以 TypeScript 源码被引用（`exports` 指向 `src/index.ts`），由 Vite 与 tsdown 打进前后端产物，不单独产出构建结果；它们的 `build` 只做类型检查。
