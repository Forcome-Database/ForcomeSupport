# 邮箱服务商抽象：进线邮箱按邮箱选 Gmail 或 163 企业邮箱，163 企业邮箱经 IMAP 收信、SMTP 发信

用户 2026-10-15 决定新增「163 企业邮箱」（网易企业邮箱）通道（PRD D-28）：与 Gmail 并存，每个进线邮箱各自选服务商；第一期只收信（收件箱与「已发送」，连接状态、告警、近 90 天回放与 T0 切换与 Gmail 同口径），发信随第二期；客户端授权码由管理员在 P18 店铺抽屉里填写。本 ADR 定下收信层怎么做到与服务商无关、163 企业邮箱怎么收，是待办 35（后端）、36（P18 界面）与第二期发信的依据；35 实现时可按技术判断调整，调整写回本 ADR 的「修订」。

**分层：服务商只到「取信」为止。** 进线邮箱多一个属性「服务商」（`gmail` / `qiye163`，取值在 `contracts`）。`channel` 里把「从一个邮箱取信」做成按服务商分派的两种实现——Gmail（ADR 0008、0009 已有的 watch、history、区间补拉）与 IMAP（本 ADR）——它们都只负责：开始监听、取上次同步位置之后的信（收件箱与「已发送」）、位置失效时按到达时间区间补拉、按到达时间列出一段区间（历史回放）、探测能否访问（测试连接）。取到的每封信都交给同一段入库路径（原文 RFC 822 → `postal-mime` 解析 → 去重 → 店铺与来源识别 → 「来信已接收」/「我方发信已同步」事件），之后的归并、回复识别、SLA、时限扫描、报表、通知不知道信来自哪个服务商。同步记录（`channel.mailbox_sync`）、连接状态、横幅、通知、P27 记录、按时关闭的「同步到了哪里」（ADR 0008「待办 33 落地」）都按邮箱记、与服务商无关。

**163 企业邮箱只有 IMAP / SMTP**（没有公开的收信 REST 接口与推送），所以：

- **连接与登录**：服务器与端口按邮箱登记（默认 `imap.qiye.163.com:993`，SSL；企业所在机房不同地址不同，例如 `imaphz.qiye.163.com`、海外 `hwimap.qiye.163.com`），登录名是完整邮箱地址，口令是**客户端授权码**（不是登录密码）。网易要求客户端登录后先发 IMAP `ID` 命令（RFC 2971）报出客户端名称，否则选文件夹时报「Unsafe Login」——客户端库用 `imapflow` 的 `clientInfo` 发。网易后台要由管理员开启 IMAP 与客户端登录，可能开了登录 IP 限制（报 `ERR.LOGIN.IPDENY`）：这些是上线前的先决条件（待办 32），不是代码能解决的。
- **只读、不改邮件状态**：一律用 `EXAMINE`（只读选中文件夹）与 `BODY.PEEK[]` 取原文，不置「已读」、不移动、不删除——客服可能还在网易的客户端里看这些信。Gmail 的 API 本来就不改已读状态，两边一致。
- **文件夹**：只同步收件箱（`INBOX`）与「已发送」。「已发送」按 `LIST` 返回的特殊用途标记 `\Sent`（RFC 6154）识别，没有标记时按名字兜底（「已发送」、`Sent Messages`、`Sent`），找到的名字记进同步记录；找不到时测试连接报「找不到「已发送」文件夹」，同步照常收收件箱并记同步成功（收件箱的来信没有暂存，不计连接失败、不出横幅），只记警告日志——我方回复要等管理员在网易里确认「已发送」后才收得到，真实环境核对见待办 29。草稿、垃圾邮件与其他文件夹不收——被网易的收信规则移到其他文件夹的信收不到（PRD Q-27，上线前核对，进线邮箱不设这类规则）。
- **增量游标**：收件箱与「已发送」各一组 `UIDVALIDITY` + 已收到的最大 `UID`。同步时 `UID FETCH <上次 UID + 1>:*` 取新信（`INTERNALDATE` 与原文），全部入库后在**同一个事务**里推进两组位置（比较旧值、只往前）并记同步成功——与 Gmail「水位只在持久化成功后推进」同一口径。`UIDVALIDITY` 变了（文件夹被重建、服务端迁移）等同 Gmail 的游标过期：从上次同步成功前 1 小时起按到达时间区间补拉（IMAP `SEARCH SINCE` 只到日期，取回后按 `INTERNALDATE` 再筛），全部入库后换上新的 `UIDVALIDITY` 与位置；补拉完成前「最近同步成功」不前移。
- **常驻连接 + 轮询兜底**：worker 用一个独占的常驻拉取（ADR 0008 的 `defineFeed(…, { exclusive: true })`，咨询锁选主）给每个 163 企业邮箱开一条 IMAP 连接、在收件箱上 `IDLE`；收到 `EXISTS` 就排一次该邮箱的同步任务（队列 stately + `singletonKey` 为邮箱，同 `channel.gmail_sync`），连接断了按 1 分钟起翻倍、最多 30 分钟重连。「已发送」不另开 IDLE 连接（每个文件夹要单独一条连接），由每次同步一起取、加上每 5 分钟的轮询任务给每个邮箱排一次同步——所以我方回复最多约 5 分钟后被识别，首次回复时长按 `INTERNALDATE` 算、不受影响。每 5 分钟的轮询同时是 IDLE 不可用或掉线时的兜底，也让没有新信的邮箱「最近同步成功」照样前进（同 `channel.gmail_poll`）。常驻连接断开后重连成功不算连接失败；登录与同步的失败照 6.9 计数。
- **认证失败不连环重试**：授权码错、客户端登录被关、IP 被限制属于要管理员处理的错误（`ExternalServiceError` 的一类，带原因：`auth_failed`、`login_denied_ip`、`unreachable`、`no_sent_folder`、`timeout`），常驻连接遇到它们就停下该邮箱的重连，只靠每 5 分钟的轮询再试——网易对连续登录失败可能锁定账号。凭据被管理员改过（P18 保存）后立即重连。
- **消息标识与去重**：服务商的消息标识统一成一列（实现时把 `channel.message.gmail_message_id`、`mail_replay_item.gmail_message_id` 改为与服务商无关的名字或加列；改名也不一次到位，同 ADR 0006 加列的三步——加新列并回填、读写切到新列、删旧列，唯一键随之重建，手写 SQL 用 `--custom`，做法写回 ADR 0006）：Gmail 为消息 ID，163 企业邮箱为「文件夹角色 : UIDVALIDITY : UID」（例 `inbox:1700000001:4521`）。「邮箱 + 服务商消息标识」唯一（R-TK-07、E-15）。`UIDVALIDITY` 变化后同一封信的标识也变了，所以 IMAP 入库前另按「同一邮箱 + 方向 + Message-ID」查是否已收过，收过的跳过（不当成「同时发送到」的副本）；没有 Message-ID 的信按「INTERNALDATE + 大小 + 发件人 + 主题」的摘要代替。跨邮箱的同一封信仍按 R-TK-07 的 Message-ID 规则处理，不分服务商。
- **到达时间与方向**：到达时间取 `INTERNALDATE`（对应 Gmail `internalDate`），SLA、回放顺序、T0 边界都用它。方向按文件夹：收件箱为来信，「已发送」为我方发出（Gmail 按 SENT 标签）。同一封既在收件箱又在「已发送」（自己发给自己、店铺邮箱互发）时两份各按方向入库，同 Gmail。
- **回复识别**：163 企业邮箱没有线程标识，我方回复只按 `In-Reply-To`、`References` 匹配工单（R-SL-08 的前两顺位），其余（乱序时的等待表、24 小时延后、自动回复不算回复）不变。
- **识别店铺的收件地址**：照 `recipientsOf` 的现有口径（`Delivered-To`、`To`、`Cc`，落到的邮箱自己不算）。网易是否写 `Delivered-To`、别名与转发怎么落箱待真实环境核对（PRD Q-27、待办 29）；没有 `Delivered-To` 时按 `To` / `Cc` 识别，与 Gmail 上写 `To` 的那类来信一样。
- **历史回放与 T0**（ADR 0008「待办 26 落地」）：「开始监听」对 163 企业邮箱是第一次记下两个文件夹的 `UIDVALIDITY` 与 `UIDNEXT`（写 `watched_at`），之后到达的信都在增量里。回放清单按邮箱列 `[T0 − 90 天, T0)`：`SEARCH SINCE <起始日> BEFORE <T0 次日>` 后取 `INTERNALDATE` 再筛，两种服务商的邮箱合在一张清单里按 `(到达时间, 邮箱, 服务商消息标识)` 升序回放。切换前（待切换、回放中）IMAP 同步同 Gmail 什么也不做——不登录、不记成败，常驻连接也不开。
- **凭据按邮箱保管**：现有动态凭据（ADR 0013 修订）的键是「外部系统 × 店铺」，一个店铺可以有几个 163 企业邮箱，不够用。客户端授权码按**邮箱地址**加密保存（`CREDENTIAL_MASTER_KEY`，`integration` 的 `sealSecret`，AES-256-GCM，附加数据为「qiye163:邮箱地址」，密文搬到别的行就解不开），与进线邮箱行分开存、按地址关联（编辑店铺时进线邮箱整行替换，同 `mailbox_sync` 的做法）。只有 `integration` 的 IMAP 真实现读得到明文；接口只收不回：店铺详情只返回「已保存」与否。保存店铺时：带了授权码就替换，没带就沿用；行被删掉或服务商改成 Gmail，保存时一并删除该地址的授权码。改授权码记审计：前后值与摘要里只写「进线邮箱 <地址>：客户端授权码已重新填写」，不记内容（其余字段照常记前后值）。主密钥换了或密文被改，解密失败当作没有授权码，该邮箱为「未连接」，要管理员在 P18 重新填写。
- **出站网络**：网易企业邮箱是境内服务，按 ADR 0003 的分流规则从公司固定 IP **直连**，不经境外代理。IMAP / SMTP 是 TCP 直连，不读 `HTTPS_PROXY`（`imapflow` 不配代理），防火墙要放行到 IMAP 服务器 993、第二期 SMTP 服务器 465 的出站；`NO_PROXY` 模板同样列出 `.qiye.163.com`，免得以后有 HTTP 调用误走代理。登录 IP 限制要放行这个出口 IP（待办 32）。
- **客户端与 Fake**（ADR 0009 的框架）：`integration` 新增店铺级的 IMAP 客户端（`defineClient`，真实现用 `imapflow`，按店铺的 `adapterMode` 选真实现或 Fake，生产环境拒绝 Fake），接口按上面的需要定：登录探测、列文件夹、取 `UIDVALIDITY` / `UIDNEXT`、按 UID 取信、按日期搜索、等待新信（IDLE）。Fake IMAP 按邮箱存收件箱与「已发送」、维护 `UIDVALIDITY` 与 UID，测试用 `deliver`、`send`（放进「已发送」）、`resetUidValidity`、按操作注入故障（认证失败、IP 限制、连不上、超时、IDLE 掉线）。**示例回放与 Fake Gmail 同一套**：`gmail-replay.ts` 的 `fixtureMails` 抽成与服务商无关的示例邮件，按落到的邮箱的服务商分给 Fake Gmail 或 Fake IMAP，原型示例数据里服务商为 163 企业邮箱的邮箱（Forcome Auto 的 `amz-auto@forcome.com`）的信由 Fake IMAP 回放，回放出的工单与原型一致。
- **P18 接口**：店铺的进线邮箱带服务商、IMAP 服务器与端口、可选的授权码（只写）；按服务商的渠道卡（`ChannelCard`）加 163 企业邮箱；测试连接两种——渠道卡测该服务商全部邮箱（同 Gmail 的 `connection-tests`），店铺抽屉里按一行测（不保存：用这一行当前填的地址、服务器、端口与授权码，授权码没填时用已保存的），都只给管理员、不记同步记录、不改连接状态，按原因返回可读的写法（PRD P18 与 K8）；同一个地址同时只跑一个测试，免得连续登录失败触发网易锁定。
- **第二期发信**（写进第二期规格）：163 企业邮箱经 SMTP（默认 `smtp.qiye.163.com:465`，同一个授权码）发出，发信前生成并保存自己的 `Message-ID`；网易是否把 SMTP 发出的信自动存进「已发送」要实测，不存时发完用 IMAP `APPEND` 放进「已发送」；结果不明时在「已发送」里按 `HEADER Message-ID` 搜索确认再决定是否重试（Gmail 为 `rfc822msgid:`）。

## Considered Options

- **把 163 企业邮箱的信转发到 Gmail**：不用改代码，但到达时间变成转发时刻（SLA 失真）、我方从 163 发出的回复看不到（「已发送」不在 Gmail）、第二期回复的发件身份不对；用户要求两者并存、按邮箱选服务商。
- **只轮询、不用 IDLE**：实现更简单，但来信最多晚 5 分钟才建工单；IDLE 是 IMAP 的标准扩展、`imapflow` 原生支持，常驻连接的选主已有现成框架。保留 5 分钟轮询作兜底。
- **「已发送」也开 IDLE**：每个邮箱两条常驻连接，换来我方回复早几分钟被识别；首次回复时长按 `INTERNALDATE` 算，不受这几分钟影响，不值得多一倍连接（网易对单账号并发连接数有限制）。
- **自己写 IMAP 协议**：不用现成的。`imapflow`（Nodemailer 作者维护）覆盖 IDLE、SPECIAL-USE、UID 增量、`ID` 命令与 TLS，已装的 `postal-mime` 解析原文；第二期发信用 Nodemailer（同一作者）。
- **授权码放环境文件**：和其他静态凭据一样由运维配置。但授权码按邮箱、会被管理员在网易后台重新生成，用户要求在 P18 里填；所以按邮箱加密存库、只写不读。

## Consequences

- 新增一种外部依赖（网易企业邮箱 IMAP），先决条件见待办 32：管理员开启 IMAP / SMTP 与客户端登录、为各进线邮箱生成授权码、确认机房地址、登录 IP 限制放行服务器出口 IP。
- 常驻连接数 = 163 企业邮箱数；邮箱多时注意网易的并发连接上限，必要时退回只轮询。
- 已上线的 Gmail 行为不变，但 `gmail_*` 命名的列、唯一键、回放清单要改成与服务商无关（迁移按 ADR 0006 分三步），回归测试必须全过。
- 去重在 `UIDVALIDITY` 变化时依赖 Message-ID，没有 Message-ID 的信靠摘要兜底，极少数情况下可能重复或漏判，记日志可查。
- 网易的投递细节（`Delivered-To`、别名、收信规则）与 IDLE 可用性未经真实环境验证（PRD Q-27），结论记入待办 29，不满足时调整识别规则或改为只轮询。

## 修订（2026-10-15，待办 35 落地）

- **列改名而不是加 IMAP 专用列**（三步，ADR 0006「待办 35 落地」）：`channel.message.gmail_message_id` → `provider_message_id`（必填，「邮箱 + 它」唯一，唯一键 `message_mailbox_provider_id_key`）、`gmail_thread_id` → `thread_id`（**可空**：163 企业邮箱没有线程，为空；回复识别、等待表与咨询锁在线程为空时只按 `In-Reply-To` / `References`）；`channel.mail_replay_item.gmail_message_id` → `provider_message_id`（主键随之）；`ticket.pending_reply.gmail_thread_id` → `thread_id`（可空，索引随之）。另加索引「邮箱 + 方向 + Message-ID」供 UIDVALIDITY 变化后的去重。
- **进线邮箱与游标**：`channel.store_mailbox` 加 `provider`（必填）、`imap_host`、`imap_port`，约束「Gmail 两者为空，163 企业邮箱两者都有、端口 1–65535」。IMAP 游标存成 `channel.mailbox_sync.imap_cursor`（jsonb：`{ inbox: { uidValidity, uid }, sent: { uidValidity, uid } | null, sentFolder }`，`uid` 为已入库的最大 UID，开始监听时为 UIDNEXT − 1）与补拉时的新游标 `imap_backfill_cursor`（补拉起点沿用 `backfill_from`）；`watched_at`、同步记录各列与 Gmail 共用。「已开始监听」按服务商判断：Gmail 看 `history_id`、163 企业邮箱看 `imap_cursor`（`mailbox-health.ts` 的 `listening`）。**服务商改了**（P18 在 Gmail 与 163 企业邮箱之间改）的邮箱，保存时删掉它的同步记录：同新加的邮箱一样重新开始监听、不回放之前的信。
- **去重的摘要**：没有 Message-ID 的信按「到达时间 + 发件人 + 主题」认出已收过的（库里不存大小，ADR 原文的「大小」一项去掉）；只对 163 企业邮箱做，Gmail 不变。
- **任务与常驻拉取**（ADR 0008 修订）：任务 `channel.imap_sync`（stately + `singletonKey` 邮箱，并发 5，同 Gmail 60 秒起翻倍重试 5 次——但认证失败、IP 受限这类要管理员处理的错误只记进同步记录、任务正常结束，不按任务重试连环登录；没保存授权码为「未连接」，不登录、不记失败）；定时 `channel.imap_poll` 每 5 分钟（启动时一次）；独占常驻拉取 `channel.imap_idle`：每次拉取先给还没开始监听的 163 企业邮箱开始监听（**上线切换前也做**，同 Gmail「T0 前启动 watch」；失败按 1 分钟起翻倍、最多 30 分钟退避，服务器、端口或授权码改了立即再试），再在切换完成后按当前的邮箱与配置开、关、重连各条 IDLE 连接：配置指纹为服务器、端口、授权码最近一次填写的时刻与数据来源，变了立即重连；连上或重连上先排一次同步（断开期间到的信不等轮询）；掉线按 1 分钟起翻倍、最多 30 分钟重连，不记失败；登录失败记失败，要管理员处理的停下重连，等配置变了或轮询同步成功（最近同步成功晚于停下的时刻）再开。切换前不开 IDLE、同步不登录不记成败。
- **同步的细节**：两个文件夹的信合起来按到达时间（同一时刻收件箱在前）逐封入库；推进游标时按旧值比较（jsonb 相等）、每个文件夹只往前；「已发送」刚找到（或换了名字）时从此刻起收、不补之前的；补拉在两个文件夹各 `SEARCH SINCE <起点前一天>` 后按 INTERNALDATE 筛、只取新游标之前的 UID（之后的留给增量），补拉中途 UIDVALIDITY 又变了重新记位置再补一次。

- **评审后的补充（2026-10-15，待办 35 code-review）**：
  - **取信层没有做成统一接口**：上文「分层」说把取信做成按服务商分派的两种实现；落地时两种服务商的调用方式差得太多（Gmail 是 watch + historyId + 逐封 messages.get，IMAP 是会话里按文件夹的 UID 与 SEARCH），硬套一个接口要么丢掉 IMAP 的会话复用、要么让 Gmail 多一层空转，所以只统一了「取到之后」（`mail-ingest.ts` 的入库路径、同步记录与连接状态、通知与审计），开始监听、增量、补拉、回放列清单、测试连接按服务商各写在 `gmail-sync.ts` / `imap-sync.ts`，调用方（`mail-replay.ts`、`routes.ts`、`jobs.ts`）按服务商分支。再加一种服务商时照这两个文件再写一份，入库之后不用动。
  - **改了服务器或端口要重填授权码**（协调者 2026-10-15 决定，PRD P18「校验」已回写）：没带授权码的行只在「这个店铺里该地址原来就是 163 企业邮箱、保存过授权码、IMAP 服务器与端口都没改」时沿用已保存的（`stores.ts` 的 `reusesSavedAuthCode`，比较规范化后的值）；按行测试连接同一条规则。否则改成别的主机就能让系统把已保存的授权码发过去，违背「只写不读」。
  - **原文到入库前才取**：`fetchAfter` 与区间补拉只列 UID 与 INTERNALDATE，入库前逐封 `fetch` 原文、已入库的不取——长时间断线后一次几千封也不会把原文都读进内存。
  - **补拉只补 UIDVALIDITY 变了的文件夹**：没变的文件夹照常按旧游标取增量（到达时间早于补拉起点、UID 却在游标之后的信——例如客户端离线后补存进「已发送」的回信——也收到）。补拉期间 UIDVALIDITY 又变、重补一次也没补成时不记连接失败，任务稍后重试。
  - **游标没推进就不记同步成功**：推进游标按旧值比较，0 行（同步期间同步记录被重置或服务商改了）时不记这次同步成功。
  - **重连的时机**：店铺保存后常驻连接在下一次拉取时（worker 的长轮询最多 20 秒）按新的配置指纹重连，不跨进程唤醒。
  - **回复识别的空条件**：163 企业邮箱没有线程，没有 Message-ID 的来信归并时不去查等待表，没有 `In-Reply-To` / `References` 的回复不列候选（条件全空时 drizzle 的 `where(undefined)` 会取出整张表）。
- **历史回放**：清单的消息标识即 `provider_message_id`；回放时一个 163 企业邮箱用一条会话（`ReplaySessions`，不逐封登录），按 UID 取信，列清单后文件夹被重建的那几封跳过（记日志）。
- **Fake IMAP 与示例回放**：`gmail-replay.ts` 改名 `fixture-mails.ts`，`fixtureMailsFor(夹具, 服务商)` 按信落到的邮箱的服务商分给 Fake Gmail 或 Fake IMAP（夹具的店铺带 `provider`）。Fake IMAP 在「取过位置的会话关闭时」才送达回放的示例邮件（开始监听先记下两个文件夹的位置），都排在记下的位置之后；UIDVALIDITY 从 1700000001 起按邮箱递增；`continueFrom` 让 Fake 接上库里的游标（进程重启后投验收夹具用，同 Fake Gmail 的 `continueHistoryFrom`）；故障注入另有 `rejectLogin` / `acceptLogin`（一直登录不上直到恢复）、`dropIdle`、`removeSentFolder`、`redeliver`，一次性的用 `faults`（`FaultSpec` 加 `mailbox_access`）。灌示例数据时，加服务商之前就灌进库、没被人改过（`updated_by_name` 为空）的示例店铺的进线邮箱按夹具改服务商（同时清掉同步记录）。

- **「能不能沿用已保存的授权码」挪进 contracts**：`reusesSavedAuthCode`（原 `apps/server/src/modules/channel/stores.ts`）移到 `packages/contracts/src/channel.ts`，后端保存店铺与按行测试连接、前端抽屉判断这一行写「已保存」还是要填授权码，用同一条规则（地址按店铺里原来的进线邮箱找，服务器去空白转小写、端口转数字后比较）。前端不要另写一份比较，以后改规则只改这一处。
