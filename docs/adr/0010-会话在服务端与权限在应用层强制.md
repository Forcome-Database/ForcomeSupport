# 服务端会话，角色固定在代码里，店铺范围与生产厂隔离在应用层强制（不用 RLS）

身份与权限的实现（2026-09-24 用户同意）：

- **会话**：服务端会话存在 PostgreSQL，浏览器只持有 httpOnly、Secure 的 Cookie；无操作 7 天过期，有操作自动续期。钉钉扫码登录与钉钉内免登都换出同一种会话。主应用与工厂工作台的 Cookie 各自独立。
- **同步与停用**（D-16）：钉钉 Stream 变更事件实时同步，外加每小时全量对账。成员停用时，立即失效会话、释放他持有的锁；他负责的工单与售后单转入「待分配」并通知客服主管；他是备用审批人时提醒管理员重新指定。
- **角色**：6 个角色固定在代码里；PRD 10.1 能力矩阵是 `packages/contracts` 中的常量，前端据此显示，后端据此强制；一个成员可有多个角色，权限取并集。「只能看自己发起或负责的」由能力校验加归属校验完成。
- **店铺范围**（R-ST-06）：各模块的仓储查询必须接收带授权店铺列表的上下文参数（缺了编译不过），并由测试覆盖越权场景。
- **生产厂隔离**（R-FT-02）：工厂接口集中在 `/api/factory/*`，使用只含必要字段的输出结构；生产厂 ID 只从会话取；客户姓名、地址、电话只在寄件任务中出现，寄件完成 30 天后对生产厂隐藏（只限制可见性，不删除数据）。
- **审计**：服务层在写事务内记录，系统操作记为「系统」；登录、登出、强制接手、导出也记录；只读查询不记。客服主管与管理员可查全部，其他角色只看自己的。
- **钉钉通知**：每条通知带对象编号与时间，避免被「同内容一天一条」静默吞掉；同一人的提醒 5 分钟内合并发送；统计每月调用量，接近配额时告警。

## Considered Options

- JWT：无状态，但停用成员后无法立即踢下线。
- PostgreSQL 行级安全（RLS）作第二道防线：每个连接要设置会话变量，和连接池、Drizzle、pg-boss worker 配合容易出错、难调试；按现在的规模，应用层强制加测试已经足够。
- 角色可在界面自定义：PRD 的角色与能力是固定的，自定义角色只会增加测试面。

## Consequences

- 新增的查询只要漏掉范围参数就无法编译；但原生 SQL 与报表查询（`report` 只读角色）需要在评审和测试中单独检查范围过滤。
- 集团钉钉的版本待确认；如果是标准版，配额会限制通知量，需要持续监控。

## 修订（2026-09-24，交叉审查复核，见 `.scratch/tech-plan/reviews/复核结论.md`）

- **成员停用分两条路径**：管理员手工停用前须先改派未处理的工单与售后单（P20、AC-ST-02）；钉钉离职自动停用时立即失效会话、释放锁，负责对象进入主管改派队列（AC-ST-05）。「待分配」是归属标记，不改变工单与售后单的业务状态。
- **财务字段能力**：成本、承担比例、结算金额只对客服主管、售后负责人可见（PRD 10.3），生产厂只见本厂部分；报表聚合、导出、下钻与审计输出都按此过滤，只有「查看报表」能力的管理员、知识库负责人看不到这些字段。
- **审计补充**：越权访问（E-24）也写审计。
- （2026-10-03）**审计可见范围**：店铺范围受限的客服主管只看到授权店铺的对象记录与没有店铺属性的记录（成员、设置、登录等），按 PRD 10.2（D-27）。

## 修订（2026-10-04，待办 02 落地）

- **会话的第一版**：`org.session` 存会话；浏览器只持有 Cookie `forcome_session` 里的 32 字节随机令牌，库里只存它的 SHA-256。Cookie 为 httpOnly、SameSite=Lax、Path=/；生产与开发测试环境（HTTPS）加 Secure，本机开发与自动化测试（http）不加。受保护的接口挂 `org` 的 `requireSession`，没有有效会话返回 401（`{ error: 'unauthenticated', message: '未登录或会话已失效，请重新登录' }`）；业务写操作用 `sessionActor(c)` 取审计的操作人。第一版在会话行里存登录时成员的姓名与角色快照；04 号待办引入成员表后改为引用成员、实时读取角色，并加上无操作 7 天过期与续期（`last_active_at` 已留）与退出登录。
- **开发登录**：只在非生产环境、`DEV_LOGIN_ENABLED=true` 时开启。生产环境配置了就拒绝启动（`loadConfig`），接口层再判断一次，生产环境不挂 `/api/dev/*`，OpenAPI 文档里也没有。后端镜像只有一个（开发测试环境的冒烟要用开发登录），「生产构建禁用」因此按运行环境落实，不靠分开构建。`GET /api/dev/members` 列出可选成员（第一版取自示例数据夹具，不列第一期不能进入的生产厂对接人；04 号待办改为成员表，并连同登录被拒 G12 一起把他们加回来），`POST /api/dev/login { memberId }` 换出与扫码登录相同的会话，审计记 `auth.login`（对象类型「登录」，对象「开发登录」）。前端只在后端提供开发登录时把未登录的访问带到开发登录页。
- **来源 IP**：审计取 `X-Forwarded-For` 的第一段。生产与开发测试环境里 api 只在 caddy 之后可达，caddy 默认用真实客户端地址改写这个头、不信任客户端自带的值，03 号待办配置 caddy 时保持这个默认（不设 `trusted_proxies`）；直连（本机开发）时取连接的对端地址。

## 修订（2026-10-04，待办 04 落地）

- **会话引用成员**：成员表 `org.member`（姓名、钉钉部门、角色、店铺范围、所属生产厂、状态、密度偏好；05 号待办接上钉钉同步前由示例数据夹具灌入），会话只存 `member_id`（外键），角色、店铺范围与状态每次请求从成员表读取，P20 改了下一次请求即生效。迁移 `0003_clear_sessions` 先清掉待办 02 存快照的旧会话（已登录的人重新登录一次）。
- **7 天无操作过期**：每次受保护的请求都算一次操作并续期（`last_active_at`）；距上次续期不到 1 分钟不写库，过期判断因此最多早 1 分钟。带请求头 `x-forcome-background: 1`（`contracts` 的 `BACKGROUND_REQUEST_HEADER`）的后台请求——站内通知轮询（31）、实时推送触发的重新拉取（18）——照常校验但不续期，否则开着页面会话就永远不过期。无操作满 7 天的会话在下一次请求时删除，返回 401 `session_expired`（「7 天未操作，已退出登录」，G12）并清除 Cookie。Cookie 带 `Max-Age=604800`，续期时重发、随之顺延：关掉浏览器不会退出登录。成员停用、没有角色或只剩第一期不能进入的角色（`loginDenial`）时，会话在下一次请求作废（401 `unauthenticated`）。退出登录 `POST /api/logout` 删除会话并记审计 `auth.logout`。
- **能力矩阵**：`packages/contracts/src/capabilities.ts`，一项能力对应 PRD 10.1 的一行（共 29 项），文案、分组与顺序照原型 K17，每项带上线阶段（一起 / 仅一 / 二起 / 三）与各角色的权限种类（● 有权限、○ 只能看自己的并写明范围、文字为部分能力）；`CURRENT_PHASE` 决定哪些已上线。`can(角色, 能力)` 多角色取并集、未上线谁都没有；`grantsFor` 返回各角色的权限种类，「○」的归属与「只读」由业务模块再校验。单元测试直接读 PRD 10.1 表与原型 K17 的数据逐格核对，任一边改了而常量没跟上就失败。角色标识用英文 snake_case（`agent`、`supervisor`、`aftersales_owner`、`knowledge_owner`、`admin`、`factory_contact`），审计的角色快照也存标识，界面显示中文名。
- **导航与默认首页**：`contracts` 的 `navFor`、`homeFor` 按能力与 PRD 4.1 第一阶段表计算，后端放进 `/api/me` 的 `nav`、`home`，前端照它显示；页面需要的能力登记在前端 `src/lib/pages.ts`，没有能力时在原地址显示 G2。
- **访问上下文**：受保护的接口挂 `org` 的 `requireSession(runtime, appEnv)`，处理器用 `c.get('access')` 取访问上下文——`member`、`stores`（店铺范围）、`financeVisible`、`actor`（审计操作人）、`can(能力)`、`requireStores(目标)`、`findOwned(取对象, 对象 → 审计目标)`。需要某项能力的接口再挂 `requireCapability(能力)`，没有则抛 `AccessDeniedError`，返回 403 `forbidden`。
- **店铺范围的编译期约束**：`core` 的 `StoreScope` 是带品牌的类型，仓储查询把它作为必需参数并用 `storeScopeCondition(范围, 店铺列)` 加到 where 上；只有两个来源——`org` 按成员构造（`access.stores`；`memberStoreScope` 只有 `org` 能引用，lint 强制）与 `SYSTEM_STORE_SCOPE`。`SYSTEM_STORE_SCOPE` 只用于后台任务、同步等系统操作，评审检查它的每个调用方；接口里不直接用它——详情接口要先取出对象才知道它属于哪个店铺，用 `access.findOwned(按编号取对象的仓储查询, 对象 → 审计目标)`：它把不受限的范围交给查询，取到后立即校验归属（越权记审计并 403），写法见 `apps/server/test/access-tools.int.test.ts`。受限范围不含店铺为空的行（未归属来信的例外可见由调用方另写条件，PRD I17）。`core` 的 `updateWithVersion` 仍按 id 更新、不带范围：调用方先经带范围的仓储查询取到对象（拿到 version）再更新，各模块仓储的更新函数同样把店铺范围作为参数。
- **越权访问审计（E-24）**：请求点名了范围外的店铺或对象（页面店铺筛选、详情所属店铺、他厂单据）时，调用 `access.requireStores({ storeIds, objectType, objectId, objectLabel })`（详情经 `access.findOwned`）：先在单独的事务里记一条审计 `access.denied`（对象为被访问的对象，`store_id` 为越权的店铺，后值记原因、店铺、请求方法与路径），再抛 `AccessDeniedError`，接口统一返回 403 `forbidden`。E-24 针对的是数据；能力不足的 403 不记审计（界面不给没有能力的人入口，从链接进入无权页面时 G2 是前端画面，不调接口）。
- **财务字段**：输出结构在 `contracts` 里用 `financeField(…)` 标出成本、承担比例、承担金额与结算金额（字段因此可选），输出前按 `access.financeVisible`（`canViewFinance`：要有 `finance.view` 的完整权限，即客服主管、售后负责人；生产厂对接人的「本厂部分」只在第二期工厂工作台的专用输出里给，兼任其他角色也不算）过滤（`access.can('finance.view')` 与之一致；前端决定显不显示财务列也用 `canViewFinance`，不用 `can`）：接口、导出、下钻用 `stripFinanceFields` 去掉字段，审计前后值用 `maskFinanceFields` 换成 `FINANCE_HIDDEN`（界面写「已隐藏」，K18）。报表聚合同样以字段形式输出，按同一结构过滤。过滤不认识的一律不放行：结构里没声明的键去掉；标记外面再包可选、可空、默认值、只读，或加 describe / meta / openapi 都认得出；财务字段只放在对象与列表里，放进联合、交叉、记录等结构时过滤直接报错。
- **登录被拒**：`loginDenial` 判断三种原因——已停用、未分配角色、只有生产厂对接人角色（第一期，AC-P1-21；兼有其他角色的照常进入）；登录接口返回 403 `{ error: 'login_denied', reason, message }`，`message` 是 G12 的原型文案（未分配角色时写出在职管理员）。开发登录列出成员表里的全部在职成员（含会被拒的生产厂对接人），走同一套判断。
- **密度偏好**：存成员表 `density` 列（舒适 / 紧凑），`PUT /api/me/preferences` 保存；只是个人界面偏好，不加版本号（不与管理员在 P20 的修改互相冲突），也不记审计。
- **管理员联系人**：`GET /api/org/admin-contacts` 返回在职管理员，G2 与 G12 写「请联系管理员刘洋」。
