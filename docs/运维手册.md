# 运维手册

生产环境（与开发测试环境）的备份、恢复、密钥与告警处理（待办 28）。部署、环境与各外部系统的配置见 `docs/部署说明.md`（生产部署在第 17 节）。

依据：ADR 0003、0013 及其「待办 28 落地」修订；规格「运维」第 95–99 条；协调者 2026-10-14 决定 Q1–Q4（告警的接收与写法、阈值、提醒频率、维护标记）。

## 1 概览

| 什么 | 怎么做 | 频率 | 出问题时 |
|---|---|---|---|
| WAL 连续归档 | PostgreSQL 的 `archive_command` 经 WAL-G 把每个 WAL 段推到备份目录（NAS），有写入时最多 5 分钟切一段（`archive_timeout`） | 持续 | worker 自检「WAL 连续归档」 |
| 每日备份 | 备份服务 `backup`：WAL-G 物理基础备份 + `pg_dump` 逻辑备份与卷（caddy 的根证书）经 restic 加密去重存进备份目录，执行保留策略 | 每天 02:30（北京时间） | worker 自检「备份」「每日备份」 |
| 迁移前备份 | 生产部署在执行迁移之前做一次完整备份（种类 `pre_migrate`），失败即停、不迁移 | 每次生产部署 | 部署报告「迁移前备份」一步失败 |
| 按时间点恢复 | `restore`：从基础备份恢复，重放 WAL 到指定时点 | 出事时 | 第 3 节 |
| 恢复演练 | `restore-drill`：在临时卷里恢复到指定时点并核对，不碰正在运行的库 | 每季度一次 | 第 4 节 |
| worker 自检 | 每分钟：任务队列、失败任务、各数据源同步、外部调用错误率、钉钉配额、备份与 WAL，异常发运维群的钉钉机器人 | 每分钟 | 第 6 节 |
| 宿主机检查 | 宿主机每分钟（systemd 定时器）看 worker 容器在不在运行、心跳有没有停，异常发同一个机器人 | 每分钟 | 第 6 节 |

目标：RPO 分钟级（WAL 最多 5 分钟一段），RTO 4 小时（规格第 95 条）。命令都在服务器的代码目录执行（生产 `/opt/forcome/support`，环境文件用 `FORCOME_ENV_FILE=/etc/forcome/production.env`），下文写 `node deploy/deploy.mjs production …`；开发测试环境在本机是 `pnpm staging …`。

## 2 备份

### 2.1 组成

- **备份目录**：环境文件的 `BACKUP_DIR`。生产必须是 NAS 挂载到服务器上的目录（部署脚本核对：必填、绝对路径），挂进数据库容器与备份服务的 `/backup`；开发测试环境不填，用本项目的命名卷 `backup`（NAS 的替身）。目录下：
  - `wal-g/`：WAL-G 的基础备份（`basebackups_005/`）与 WAL（`wal_005/`），用 libsodium 加密（`WALG_LIBSODIUM_KEY`）、zstd 压缩；
  - `restic/`：restic 仓库，`pg_dump` 的逻辑备份（快照里的文件名是 `<库名>.dump`，`pg_dump -Fc` 格式）与各卷（`/backup-src/<卷名>/`），用 `RESTIC_PASSWORD` 加密。
- **同一时间只跑一个备份**：备份脚本用备份目录里的锁文件 `.forcome-backup.lock`（`flock`）。NFS v4 与本地盘上可靠；NAS 只能用 SMB 挂载、锁不可靠时，避免在每日备份的时刻（02:30）手动执行 `backup`。
- **NAS 的要求**：备份目录要让 uid 999（容器里的 postgres，WAL-G 写 `wal-g/`）与 root（restic 写 `restic/`）都能写。NFS 要关 root_squash 或把目录属主设成 999 并允许 root；SMB/CIFS 挂载时用 `uid=999,gid=999,file_mode=0700,dir_mode=0700`。NAS 不可用时归档失败、WAL 在数据库卷里越积越多（worker 自检「WAL 连续归档」告警），数据库照常服务；恢复 NAS 后自动补推。
- **哪些卷**：第一期只有 caddy 的 `caddy_data`（内部 CA 的根证书与私钥：删了员工要重新装根证书，部署说明第 4 节）。第二期加附件卷时在 `deploy/compose.yml` 的 `backup` 服务挂到 `/backup-src/<卷名>`，备份脚本自动一起备份。
- **保留策略**（环境文件可调）：restic 近 30 天每天 1 份、近 12 个月每月 1 份（`BACKUP_KEEP_DAILY`、`BACKUP_KEEP_MONTHLY`）；WAL-G 至少 7 份基础备份与近 7 天的全部（`WALG_RETAIN_FULL`），按时间点恢复的窗口因此至少 7 天。每日备份结束时执行（手动与迁移前备份不执行）。
- **记录**：每次备份开始与结束写 `core.backup_run`（种类、起止、成败、摘要或出错的步骤）：

  ```sh
  node deploy/deploy.mjs production compose exec postgres psql -U forcome -d forcome \
    -c "select kind, started_at, finished_at, succeeded, detail from core.backup_run order by started_at desc limit 10"
  ```

### 2.2 命令

| 命令 | 作用 |
|---|---|
| `node deploy/deploy.mjs production backup` | 立即做一次完整备份（种类 `manual`；上线切换前、改大量数据前用） |
| `node deploy/deploy.mjs production backup list` | 列出基础备份（名字、开始与结束、大小）与 restic 快照 |
| `node deploy/deploy.mjs production backup verify-retention` | 核对保留策略（2.3） |
| `node deploy/deploy.mjs production compose logs -f backup` | 备份服务的日志（每次备份的各步与结果） |

### 2.3 核对保留策略

`backup verify-retention` 做两件事：

1. **模拟**：在临时的 restic 仓库里造 400 天的每日快照（到今天），用与每日备份同一组参数执行 `restic forget`，核对留下的正好是「近 30 天每天 1 份 + 近 12 个月每月月末 1 份」（两者重叠的只算一份，共 40 份），不一致时退出码 1；
2. **真实仓库**：按路径分组列出快照数与起止日期，超出保留策略（份数超过 30 + 12、或早于 12 个月以前的月初）的标 ✗、退出码 1；另报告 WAL-G 基础备份的份数与最早一份。

上线后每月看一次，或改了保留参数后执行。

### 2.4 上线切换前的备份

上线切换（部署说明第 16 节）前执行 `backup`，记下输出里的基础备份名与结束时刻（`backup list` 也能看到）；切换出问题要回滚时按第 3 节恢复到切换开始之前的时刻（16.4）。

## 3 按时间点恢复

把数据库恢复到过去某个时刻（误删数据、坏的迁移、上线切换回滚）。**会覆盖现在的数据**：恢复期间 api 与 worker 停着（员工打不开系统），原数据目录改名留在数据卷里，核对无误后再删。

1. **确定目标时点**（带时区，如 `2026-11-01T09:30:00+08:00`）：出问题之前的时刻。看计划：

   ```sh
   node deploy/deploy.mjs production restore --target-time 2026-11-01T09:30:00+08:00
   ```

   列出全部基础备份；恢复会用「结束时刻不晚于目标时点」的最近一份，再重放其后归档的 WAL 到目标时点。要恢复到最新（数据库卷坏了、换服务器）用 `--latest`；要指定基础备份用 `--backup <名字>`。
2. **执行**（同一条命令加 `--confirm`）。部署脚本写维护标记（宿主机检查暂停告警，默认 2 小时，`--maintenance-hours` 调），依次：停 api、worker、备份服务与数据库 → 取回基础备份（`forcome-restore prepare`，原数据目录改名为 `18/docker.before-restore-<时刻>`）→ 起数据库重放 WAL 到目标时点、自动 promote 成新的时间线 → 清恢复参数（`forcome-restore finish`）→ 新时间线的第一份基础备份（`after_restore`）→ 起 api、worker、caddy 与备份服务。每步计时，报告写到 `deploy/.state/production/restore-report.md`（合计即本次的恢复用时，对照 RTO 4 小时）。
3. **核对**：打开系统看目标时点附近的数据；`select max(occurred_at) from core.audit_log` 应早于目标时点。
4. **恢复后对账外部动作**（ADR 0013 修订）：目标时点之后系统对外做过的事不会随恢复撤销，恢复后的库会当作没做过。第一期对外的写动作只有钉钉工作通知：目标时点之后发出过的通知可能再发一次（`core.work_notification` 里 `sent_at` 为空、`created_at` 早于目标时点的行会被每分钟的任务发出），影响很小；需要时在起 worker 之前把这些行标为已发。外部系统的数据（Gmail、订单）由同步自动补上：邮箱游标、订单水位都回到了目标时点，之后的变化会重新同步进来。
5. **删掉留着的原数据目录**（确认不再需要后）：

   ```sh
   node deploy/deploy.mjs production compose run --rm --no-deps restore sh -c 'ls -d /var/lib/postgresql/18/docker.before-restore-* && rm -rf /var/lib/postgresql/18/docker.before-restore-*'
   ```

**只要逻辑备份里的某些数据时**（不覆盖整个库）：从 restic 取出某天的 `pg_dump`，恢复到一个临时库里查：

```sh
node deploy/deploy.mjs production compose run --rm --no-deps backup sh -c \
  'restic snapshots --tag pg_dump && restic dump <快照 ID> /forcome.dump > /tmp/forcome.dump && pg_restore --list /tmp/forcome.dump | head'
```

## 4 恢复演练（每季度一次）

```sh
node deploy/deploy.mjs production restore-drill
```

在一次性容器与临时卷里做，正在运行的库照常服务：

1. 在库里写一行演练标记 `before`，2 秒后取此刻为**目标时点**，再过 2 秒写 `after`；切一个 WAL 段并等它归档；
2. 取回「结束时刻不晚于目标时点」的最近一份基础备份，起一个不归档、只听本地套接字的临时库，重放 WAL 到目标时点并 promote——这就是「从基础备份恢复到其后指定时点」；
3. 核对：演练标记只剩 `before`（目标时点之前写的在、之后写的不在），并列出审计日志、工单、售后单的行数与最新时刻；
4. 删掉临时卷与标记表，报告写到 `deploy/.state/production/restore-drill-report.md`：基础备份、目标时点、取回用时、重放用时、合计。

也可以 `--target-time <时刻>` 指定过去的某个时点（不写标记，只核对行数）。演练报告存档（附到当季的运维记录），合计用时远大于以往时（库变大、NAS 变慢）评估 RTO。开发测试环境的演练记录见待办 28 的 Comments。

## 5 密钥

### 5.1 清单

| 密钥 | 在哪里 | 丢了会怎样 | 离线保管 |
|---|---|---|---|
| 数据库口令 `POSTGRES_PASSWORD` | 环境文件 | 改环境文件、`ALTER USER` 改口令即可 | 是 |
| 主密钥 `CREDENTIAL_MASTER_KEY` | 环境文件 | 库里的 Shopify 访问令牌解不开（系统自动重新换）、SP-API 刷新令牌解不开（要用 `sp-api-token` 逐个卖家重录） | **是，随备份单独保管** |
| WAL-G 密钥 `WALG_LIBSODIUM_KEY` | 环境文件 | **全部物理备份与 WAL 解不开，无法按时间点恢复** | **是，随备份单独保管** |
| restic 口令 `RESTIC_PASSWORD` | 环境文件 | **全部逻辑备份与卷备份（含 caddy 根证书）解不开** | **是，随备份单独保管** |
| 钉钉应用凭据 `DINGTALK_CLIENT_*`、`DINGTALK_AGENT_ID` | 环境文件 | 在钉钉开放平台重新查看 | 否（可重新获取） |
| 钉钉群机器人 `DINGTALK_ROBOT_WEBHOOK`、`DINGTALK_ROBOT_SECRET` | 环境文件 | 在群设置里重新添加机器人 | 否 |
| Google 服务账号密钥、Shopify / SP-API 应用凭据、SQS 访问密钥 | 环境文件与 `GOOGLE_KEY_DIR` | 在各平台重新生成（部署说明第 12–14 节） | 否 |

- **环境文件**：放在工作区以外（生产 `/etc/forcome/production.env`），属主为生产运行器的系统用户、权限 600（`chmod 600`；生产部署时部署脚本核对，不是 600 拒绝部署），不进 git、不进 GitHub。服务器上的副本只此一份。
- **离线保管**（ADR 0013：主密钥丢失会导致全部店铺凭据不可解密，必须随备份单独、离线保管）：上线时把加粗的三项与数据库口令抄到公司的密码管理器（或打印封存），与 NAS 分开放；**不要只存在服务器上**——服务器坏了、NAS 上的备份恢复不出来。换了其中任何一项都要同步更新离线副本。

### 5.2 轮换

- **数据库口令**：维护窗口内 `node deploy/deploy.mjs production maintenance --hours 1 --reason 换数据库口令` → `… compose exec postgres psql -U forcome -c "ALTER USER forcome PASSWORD '<新口令>'"` → 改环境文件 → 重新部署（打同一个版本标签无效，可在运行器上执行 `node deploy/deploy.mjs production`）→ 更新离线副本。
- **主密钥**：一般不换。必须换时：改环境文件、重新部署 → Shopify 令牌自动重新换；用 `sp-api-token` 逐个卖家重录刷新令牌（部署说明 14.2 第 5 步）→ 更新离线副本。
- **WAL-G 密钥、restic 口令**：换了以后旧备份要用旧密钥才能解开。做法：保留旧密钥的离线副本直到旧备份全部过了保留期（restic 12 个月，WAL-G 7 天）；restic 可用 `restic key add` / `restic key remove` 换口令而不重新加密数据（在 `backup` 容器里执行）；WAL-G 换密钥后先做一次 `backup`，新的基础备份用新密钥。
- **SP-API 的 LWA 凭据**（亚马逊要求定期轮换）、钉钉与其他外部凭据：改环境文件、重新部署（部署说明第 11–14 节）。

## 6 告警

### 6.1 通道

- **运维群的钉钉自定义机器人**：群设置 → 智能群助手 → 添加机器人 → 自定义，安全设置选「加签」，把 Webhook（`https://oapi.dingtalk.com/robot/send?access_token=…`）与 SEC 开头的密钥填进环境文件 `DINGTALK_ROBOT_WEBHOOK`、`DINGTALK_ROBOT_SECRET`，重新部署。生产默认用真实接口（`CLIENT_MODE_DINGTALK_ROBOT` 留空）；没填 Webhook 时照常启动，告警只写 worker 日志（协调者 Q1）。钉钉在 `NO_PROXY` 里直连。
- **测试消息**：第一次部署后、换了机器人后执行 `node deploy/deploy.mjs production alert-test`：经 worker 的群机器人客户端（一次性容器）与宿主机检查两路各发一条「【Forcome Support · 生产】告警通道已连通」，群里应收到两条（待办 29 核对）。
- **写法**：一次检查最多一条 markdown 消息，标题「【Forcome Support · 生产】自检发现 N 项异常」（宿主机检查为「worker 已停止」「worker 心跳停止」），正文每项一行，新出现的标「新」、持续的写从什么时候起，恢复的写在「已恢复」下面，末行写检查时刻。同一项按键去重（队列名、邮箱、数据源等），持续异常每 2 小时再提醒一次（`ALERT_REPEAT_HOURS`），恢复时发一条「已恢复」（协调者 Q3）。发送失败下一分钟再试。开发测试环境默认 Fake，只写 worker 日志（`… compose logs worker | grep 自检`）。

### 6.2 worker 自检（每分钟）

worker 的定时任务 `core.self_check` 每分钟先写心跳（`core.worker_heartbeat`），再查下表各项；正在告警的项在 `core.alert`。阈值都是环境文件的 `ALERT_*`（留空取默认值；各数据源的同步阈值是 PRD 6.9 的口径，不可调）。未连接（没配置凭据、还没同步过）的数据源不告警；生产环境上线切换完成前（待切换、回放中）不按 Gmail 告警。

| 项（消息里的写法） | 判断 | 默认阈值 | 处理 |
|---|---|---|---|
| Gmail `<邮箱>` | 超过阈值没同步成功（同步延迟），或连续 3 次失败（连接异常） | 10 分钟（PRD 6.9） | 部署说明 12.3；P18 Gmail 卡有恢复指引 |
| 亚马逊订单 / Shopify 订单 `<店铺>` | 同上 | 10 分钟（PRD 6.9） | 部署说明 13.3、14.3 |
| 钉钉通讯录 | 全量对账超过阈值没成功，或连续 3 次失败 | 2 小时（PRD 6.9） | 部署说明 11.2；查 worker 日志里钉钉返回的错误码 |
| 汇率 | 最近一次同步成功超过 1 天（每天 06:00 同步，多留 1 小时） | 1 天（PRD 6.9） | 看「最近的错误」；欧洲央行与 Frankfurter 都经出站代理，查代理与放行域名（部署说明 6.2）；修好后 `… compose restart worker`（启动即同步） |
| 亚马逊订单通知队列（SQS） | 连续 3 次拉取失败；等待拉取的通知达到 10 条；超过阈值没有检查记录（拉取源没在跑） | 3 次、10 条（PRD）、10 分钟（`ALERT_SQS_CHECK_STALE_MINUTES`） | 部署说明 14.3；订单仍由每 4 分钟的增量补上 |
| 夜间对账 / 订单回补 `<店铺>` | 对账开始超过阈值仍未完成；回补或对账的失败持续 30 分钟以上 | 24 小时（`ALERT_RECONCILE_STALE_HOURS`） | 部署说明 15.3 |
| 任务队列 `<队列>` | 已到点、还没开始的任务最久等了阈值以上 | 10 分钟（`ALERT_QUEUE_WAIT_MINUTES`） | worker 可能卡住或太忙：看 worker 日志与宿主机检查；`… compose restart worker` |
| 任务 `<队列>` | 近一段时间有任务重试用完仍失败（含汇率同步重试 3 次仍失败） | 近 60 分钟（`ALERT_FAILED_JOB_WINDOW_MINUTES`） | 消息里有最近一条错误；worker 日志按任务名查 |
| 外部调用 `<系统>` | 近一段时间调用不少于 N 次、失败（非 2xx、超时、网络错误，含 429 限流）占比达到阈值 | 近 15 分钟、10 次、50%（`ALERT_CALL_ERROR_*`） | `integration.call_record` 按系统看状态码与响应摘要（部署说明 12.2）；429 多为配额，查各平台的限流 |
| 钉钉调用配额 | 本月（北京时间）工作通知的调用次数达到阈值（标准版每月 5,000 次） | 4,000 次（`ALERT_DINGTALK_MONTHLY_CALLS`） | 确认钉钉版本与余量（待办 32）；超额后工作通知发不出，站内通知不受影响 |
| WAL 连续归档 | 最近一次归档失败晚于最近一次成功；或超过 `archive_timeout` 的 2 倍没有归档成功 | 5 分钟 × 2 = 10 分钟（协调者修改 Q2 g） | NAS 挂载与权限（2.1）；`… compose logs postgres` 看 `archive command failed` |
| 备份 / 每日备份 | 最近一次备份失败；最近一次成功超过阈值 | 26 小时（`ALERT_BACKUP_STALE_HOURS`） | `… compose logs backup` 与 `core.backup_run.detail`；修好后 `backup` 手动补一次 |
| 自检项「…」 | 某一项自己执行出错 | — | worker 日志「自检项出错」 |

### 6.3 宿主机检查（每分钟）

不经 worker，由宿主机的 systemd 定时器每分钟执行 `node deploy/deploy.mjs production host-check`：

- **worker 已停止**：worker 容器不在运行（退出、被删、一直重启）；
- **worker 心跳停止**：容器在，但心跳超过 `HOST_CHECK_HEARTBEAT_MINUTES`（默认 3 分钟）没有更新（进程卡死、任务队列取不到任务、容器被暂停）；
- **数据库连不上**：读不到心跳。

上线切换回放中 worker 是被有意停掉的（待办 26）：回放命令写着维护标记，标记有效时不告警（6.4）；标记过期后仍停着照常告警，并注明「上线切换的回放还没完成」（回放卡住或失败了，按部署说明 16.3 处理）。数据库连不上时原来在告警的「心跳停止」照旧算在告警。去重、再提醒与恢复同 worker 自检，状态在 `FORCOME_HOST_CHECK_STATE`（默认 `deploy/.state/<环境>/host-check.json`）。

**启用**（本期不由部署脚本安装，由运维以 root 执行一次）：模板在 `deploy/host/`（`forcome-host-check@.service` 与 `.timer`），按服务器实际改 `User`（生产运行器的系统用户）、`WorkingDirectory`、`DOCKER_HOST`（该用户的 rootless Docker 套接字）后：

```sh
cp deploy/host/forcome-host-check@.service deploy/host/forcome-host-check@.timer /etc/systemd/system/
mkdir -p /var/lib/forcome/production && chown gh-production /var/lib/forcome/production
systemctl daemon-reload && systemctl enable --now forcome-host-check@production.timer
journalctl -u forcome-host-check@production -n 20     # 每次检查的输出
```

**处理**：`worker 已停止` → `… compose ps worker` 与 `… compose logs --tail 200 worker` 看退出原因（配置错误时启动即退出，日志第一行写缺了哪个变量），处理后 `… compose up -d --no-deps worker`；`worker 心跳停止` → 看 worker 日志最后的输出，`… compose restart worker`；`数据库连不上` → `… compose ps postgres` 与日志（磁盘满、pg_wal 积压）。

### 6.4 维护标记（计划内维护期间不告警）

部署、上线切换回放（`mail-replay --confirm`）、恢复（`restore --confirm`）、重放来信时，部署脚本写一个**带到期时间**的维护标记（默认 2 小时，`--maintenance-hours <小时>` 调），宿主机检查见到没到期的标记就不发告警；命令成功或失败退出时都清掉自己写的标记。标记到期仍没清（命令被强杀）时自动失效：异常仍在照常告警，消息里注明「维护标记已过期」（协调者 Q4）。

- 其他计划内停机（换服务器、改 NAS）手动写：`node deploy/deploy.mjs production maintenance --hours 3 --reason 换 NAS`，提前结束 `maintenance --clear`。
- 部署工作流（运行器的工作区）与宿主机检查（`/opt/forcome/support`）不在同一个目录：两边都用 `FORCOME_MAINTENANCE_FILE=/var/lib/forcome/production/maintenance.json` 指到同一个文件（工作流与定时器模板已写好）。
- 维护标记只管宿主机检查。worker 自检照常运行：部署期间 worker 重启一两分钟，不会触发它的阈值；回放期间 worker 停着，自检也不跑。回放预计超过 2 小时时加 `--maintenance-hours`。

### 6.5 开发测试环境的演练

开发测试环境默认 Fake，告警只写日志。要演练「告警确实发出、内容正确」时，用钉钉群机器人的接收替身（`deploy/robot-sink/`，按加签核对每条消息、返回钉钉的 errcode，`GET /messages` 取回收到的）：

1. 环境文件加 `CLIENT_MODE_DINGTALK_ROBOT=real`、`DINGTALK_ROBOT_WEBHOOK=http://robot-sink:8080/robot/send?access_token=drill`、`DINGTALK_ROBOT_SECRET=SEC<随机>`；`pnpm staging compose --profile robot-sink up -d --build robot-sink`，再重新部署（或 `pnpm staging compose up -d --no-deps worker`）。
2. worker 一路：造一个异常（如把 `org.dingtalk_sync.last_success_at` 改到 3 小时前），一两分钟后 `pnpm staging compose logs robot-sink` 里有「自检发现 … 钉钉通讯录」，`signatureValid` 为 `true`。
3. 宿主机一路：替身的端口只开在主机的 127.0.0.1:4514，在主机上执行或经 SSH 隧道转到本机后 `pnpm staging host-check --webhook http://127.0.0.1:4514/robot/send?access_token=drill`；`pnpm staging compose stop worker` → 「worker 已停止」；`pnpm staging compose pause worker` 3 分钟后 → 「worker 心跳停止」；恢复后 → 「已恢复」。
4. 演练完删掉环境文件里的这几行、`pnpm staging compose --profile robot-sink rm -sf robot-sink`，重新部署。

## 7 日志

- api、worker 是 pino JSON，打到标准输出；Docker 的 json-file 驱动按大小轮转：每个容器最多 `LOG_MAX_FILE`（30）个、每个 `LOG_MAX_SIZE`（20m）的文件（`deploy/compose.yml` 的 `x-logging`）。json-file 不能按天数轮转，按第一期的日志量（每天几 MB）30 × 20 MB 能留 30 天以上。
- 看日志：`node deploy/deploy.mjs production compose logs --since 2h worker`；按任务名或关键词：`… compose logs worker | grep '"job":"core.sync_exchange_rates"'`。
- 核对保留天数（每月一次）：`docker inspect -f '{{.LogPath}}' forcome-production-worker-1` 找到日志目录，看最旧的轮转文件第一行的时刻；不到 30 天时调大 `LOG_MAX_FILE` 或 `LOG_MAX_SIZE`、重新部署（只对重新创建的容器生效）。
- 业务追溯不靠日志：审计（P27）、外部调用记录（`integration.call_record`）、站内与工作通知表都在库里，随备份。

## 8 容量与连接

- **PostgreSQL 连接数**（待办 18 的衔接）：api 连接池 10 + pg-boss 3、worker 连接池 10 + pg-boss 10、每个 api 进程另占一条做 LISTEN（`application_name = 'forcome-api-listen'`，有浏览器连着实时推送时才连）、一次性命令各 1–3 条、备份时 pg_dump 1 条与 WAL-G 1 条；默认 `max_connections` 100 够用。看连接：`select application_name, count(*) from pg_stat_activity group by 1`。
- **实时推送 `/api/live`**（SSE 长连接，待办 18）：caddy 已配置不压缩、流式转发；生产前面再加反向代理或负载均衡时，同样要流式转发、不缓冲，空闲超时长于 25 秒（心跳间隔）。
- **磁盘**：数据库卷、`pg_wal`（NAS 不可用时会积压）、Docker 的镜像（部署成功后只留本次与上一次的版本）与日志。`docker system df` 看占用。
